# T6a wrapper 컴파일 재사용 측정

날짜: 2026-09-26. T1 제외 목록에 이미 들어 있는 프로젝트만 사용했다. zkFuzz는 실행하지 않았다. 값 없는 근거는 [evidence.json](evidence.json), 측정 스크립트는 [measure_compile_reuse.py](measure_compile_reuse.py)에 있다.

## 바꾼 것 (커밋 `17eea4c`)

discovery의 `targets` 목록은 이전처럼 **호출 위치마다 한 항목**을 유지한다. 그 대신 wrapper 생성과 컴파일을 **컴파일 단위**로 묶는다.

- **재사용 키:** 다음을 모두 넣은 SHA-256이다.
  - wrapper 원문(소스 경로, 템플릿, 구체 인자)
  - include closure의 파일별 SHA-256과 해석되지 않은 include
  - circom 바이너리 경로와 SHA-256
  - 컴파일 설정(`--inspect`, `-l` 순서)
  - 컴파일 제한시간
- 키가 같은 호출 위치는 wrapper 하나와 컴파일 한 번을 공유한다. 각 호출 위치에는 `compile_unit`(키)과 `compile_reused`(앞선 호출 위치의 결과를 썼는지)가 기록된다.
- **호출 맥락은 합치지 않는다.** 호출 위치마다 identity, 직접 부모(origin), `instance_key`, `parent_instance_key`가 따로 남는다. 보고서의 `root_instance_key`와 함께 호출 그래프를 이루므로, 모든 상위 호출 경로를 이 그래프에서 복원할 수 있다. 호출자가 보장하는 입력 범위가 다를 수 있으므로 입력 계약과 프로젝트 수준 판정은 호출 위치별로 따로 한다.
- 보고서에는 `compile_units`(단위별 키, 의존성 해시, 컴파일러, 설정, 소속 호출 위치, 결과)와 `compile_invocation_count`가 추가된다.
- 테스트를 2개 추가했다. 같은 부품을 여러 곳에서 호출해도 컴파일이 한 번만 일어나고 호출 맥락이 보존되는지, 그리고 의존성·설정·실패 결과가 단위에 올바르게 기록되는지 확인한다. 전체 159개가 통과했다.
- 기존 timeout 테스트가 병렬 실행에서 간헐적으로 실패하는 문제도 고쳤다. macOS는 새로 만든 실행 파일을 처음 실행할 때 지연이 있다(단독 0.17초, 6개 동시 최대 0.73초, 두 번째부터 0.005초). 그래서 가짜 컴파일러가 1초 제한 안에 시작조차 못 하는 경우가 있었다. 가짜 컴파일러를 만든 직후 한 번 미리 실행하도록 바꿨고, 파일 전체를 12번 돌려 실패율이 9/12에서 0/12로 줄었다. 실제 circom은 새로 만든 파일이 아니므로 제품 동작과는 관계없다.

## 측정 방법

측정 전에 대상과 순서를 정했다.

- **대상:** zk-email, Inference, Moonsong의 모든 `component main` 파일 18개. circomlib를 `--library-path`로 줬다.
- **컴파일:** 제한시간 600초, 실제 circom 2.2.3.
- **순서:** 재사용 버전(`17eea4c`)을 먼저 돌리고, 같은 조건으로 재사용 전 버전(`d4f0ea5`)을 돌렸다. 재사용 전 버전의 예상 시간이 3시간을 넘으면 대상을 줄이기로 했지만, 그럴 필요가 없었다.
- **하드웨어:** Apple M5(10코어), macOS 26.2.

- 컴파일 실행 횟수는 83분의 1, 컴파일 시간 합계는 40분의 1로 줄었다.
- 전체 소요시간은 11.6분의 1이다. 탐색 자체에 entrypoint마다 고정 시간이 들어서 컴파일 시간보다 덜 줄었다.
- **호출 위치 5,240개의 컴파일 결과가 전후에 모두 같았다.** 성공 수와 실패 수가 같고, 호출 위치별로 비교해도 불일치가 0건이다. timeout은 양쪽 모두 0건이다.

**컴파일 없이 센 참고값:** 제외된 프로젝트 6개의 entrypoint 191개 전체에서, wrapper가 만들어지는 호출 위치 19,412개가 컴파일 단위 858개로 묶였다. 실제로 컴파일해서 잰 값은 위 표의 18개 entrypoint뿐이다.

## 해석과 한계

- 이번 대상의 wrapper는 대부분 작은 부품이라 컴파일 한 번이 평균 0.03초 정도였다. 그래서 절대적인 절감 시간은 약 2.6분이다. 절감량은 컴파일 단위당 비용에 비례하므로, 큰 템플릿이 반복 호출되는 프로젝트에서는 더 커진다. 다만 그런 경우는 아직 측정하지 않았다.
- 측정한 entrypoint 대부분은 테스트용 회로다. production entrypoint 판정 규칙은 [기준 문서](../../docs/heldout_selection_rubric.md)에 따로 있다.
- 재사용 버전을 먼저 돌렸으므로, 재사용 전 버전은 파일 캐시가 데워진 상태에서 돌았다. 이 순서는 재사용 전 버전에 유리하게 작용하므로 절감량을 과대평가하지 않는 방향이다.
- 중복 제거는 컴파일 작업을 줄일 뿐이다. 퍼징할 독립 타깃이 몇 개인지와 퍼징 비용은 별도 측정(T6) 대상이다.
- 원시 측정 기록과 두 바이너리는 ignored `runs/t6a-compile-reuse-2026-09-26/`에 보존했고, 해시는 근거 파일에 적었다.

## 보완 (2026-09-26)

측정 수치와 원시 기록은 바꾸지 않았다.

- **입력 revision 고정.** 측정 스크립트는 `/private/tmp`의 로컬 checkout을 읽는다. 그래서 측정에 쓴 입력을 [evidence.json](evidence.json)의 `inputs`에 따로 기록했다. zk-email `fc9949763858…`, Inference `d310309c141d…`, Moonsong `27cda6e74492…`이고 세 checkout 모두 변경 사항이 없었다. 의존성은 zkbugs `a0eed744ba1a…`의 `dataset/circom/dependencies`(파일 145개, 목록 SHA-256 `16e69aed…`)다. 이 확인은 측정 뒤에 했다. 측정 스크립트는 이제 revision이 다르거나 checkout이 수정돼 있으면 실행을 거부하고, 다시 돌린 결과는 보존된 원본 기록을 덮어쓰지 않도록 `runs/t6a-compile-reuse-2026-09-26/reproduction/`에 쓴다.
- **필드 이름 변경(커밋 `2f4ad7d`).** 위에서 말한 `compile_invocation_count`는 컴파일러를 띄우지 못한 경우까지 세었다. 그래서 `compile_attempt_count`(컴파일을 시도한 단위 수)와 `compile_process_count`(컴파일러 프로세스가 실제로 시작된 수)로 나눴다. 프로세스 시작 여부는 `ToolCapture.process_started`에 기록되고, 이 필드가 없는 과거 기록은 읽고 다시 써도 바이트가 바뀌지 않는다. 이번 측정의 63회는 모두 프로세스가 실제로 시작된 경우라 수치는 그대로다. 같은 단위의 timeout 결과가 모든 호출 위치에 적용되는지, 컴파일러를 띄우지 못하면 시도만 세고 프로세스는 0으로 세는지 확인하는 테스트 2개를 추가했다(전체 161개 통과).
- **`instance_key`의 뜻.** `instance_key`는 실행 중의 특정 인스턴스가 아니라 소스·템플릿·구체 인자가 같은 **고유 실행 구성**을 가리킨다. 같은 구성이 여러 호출 위치에서 쓰이면, 호출자마다 보장하는 입력 범위가 다를 수 있다. 주 평가는 direct wrapper 자체의 입력 계약으로 판정하고, 호출자별 영향은 프로젝트 수준에서 따로 판정한다([기준 문서](../../docs/heldout_selection_rubric.md) 6단계).
