# 기술적 기여의 위치와 공개 준비

2026-10-01 · 담당 miiz · `contribution-position-v1`.

**판단:** 현재 개발은 자동 분해 시스템이라는 주 기여 가설에 연결돼 있다. 그러나 정상 계산 일치, 컴파일 재사용, 기록·집계 구현만으로 강한 기술적 신규성이나 탐지 우위가 성립했다고 결론내릴 수 없다. 설계가 해결하는 구체적 장애, 그 설계의 필요성, 관측된 효과가 연결돼야 한다. 이 문서는 기여 해석과 문서 공개 준비를 정리하며 N3 결정·N5 미고정 상태를 바꾸거나 새 실행을 지시하지 않는다.

## 1. 문헌을 읽고 확인한 범위

프로젝트의 [N2 읽기 기록 §1](../reports/methodology-review-2026-10-01/REVIEW.md#1-읽은-범위)은 다음과 같다. 모든 문헌 전문을 읽었다는 표기는 사용하지 않는다.

| 문헌 | 기존 기록의 범위 |
|---|---|
| zkFuzz v3 | 본문 §1–9, 부록 B·C와 일부 D·E. 부록 A 복잡도 증명 제외 |
| SoK v1 | 주요 본문·평가·도구 비교 정독. §VI zkVM 형식 검증은 훑어봄 |
| Towards Fuzzing ZKP Circuits | 본문 전문 |
| Wildfire | 본문 전문. 일부 표의 수치 셀 미판독 |
| Picus/QED², CCC-Check, ZEQUAL | 관련 절 부분 정독 |
| CIVER | 본문 미확보. README·초록·다른 논문의 서술로 확인한 범위만 사용 |

이번에는 zkFuzz §VIII, SoK §III-B·V, Towards §3.2·4를 공식 원문에서 다시 확인하고, 관련 문헌의 분해·맥락·재사용 부분을 기존 사본과 대조했다. 모든 문헌을 새로 전문 재독한 것은 아니다. CIVER 본문 미접근은 해소되지 않았다. N2의 과거 귀속·종료 권고를 현재 설계로 자동 채택하지 않고 [N3 보정](scope_decision_final_2026-10-01.md)과 [채택 기록](scope_decision_accepted_2026-10-01.md)을 따른다.

## 2. 선행이 이미 한 일과 남은 문제

| 선행 | 확인한 내용 | 우리 논문의 경계 |
|---|---|---|
| [zkFuzz §VIII](https://arxiv.org/html/2504.11961v3#S8) | 큰 프로그램의 실행 비용과 slicing·부분 실행 개선 가능성 제안 | 분해 아이디어를 새 발상으로 제시하지 않는다. 구체적인 자동 구성 방법과 효과가 필요 |
| [SoK §III-B](https://arxiv.org/html/2607.23752v1) | 알려진 취약 코드의 최소 wrapper와 원본 프로젝트를 비교 | 같은 격차를 재관측하는 것보다 결함 위치 없이 대상을 구성하는 방법과 적용성이 쟁점 |
| [Towards §3.2·4](https://arxiv.org/html/2504.14881v2#S3.SS2) | 부분 회로 퍼징과 전체 맥락 재확인의 필요를 제안. 실제 사례연구는 zk-regex 차등 검사 | 부분 회로 후 전체 확인이라는 발상은 선행. 구체적인 의미·구현·평가를 입증해야 함 |
| [Picus §6](https://veridise.com/wp-content/uploads/2025/01/Automated-Detection-of-Underconstrained-Circuits-for-Zero-Knowledge-Proofs.pdf) | debug 정보를 이용한 분해, 부분 모델 합성, 완전 모델이 아닌 경우 unknown | 자동 분해·결과 합성·unknown 자체를 신규성으로 주장하지 않음 |
| [Wildfire §4·8.2](https://arxiv.org/abs/1903.02981v2) | 조합 퍼징, 호출 맥락 확인, 컴파일 산출물 재사용 | 조합 퍼징·재컴파일 절감 자체는 선행. ZK에서 필요한 설계 차이를 구체화해야 함 |

이 비교는 확인한 범위의 기여 가능성 판단이다. 선행 검색이 망라적이었다거나 같은 시스템이 존재하지 않는다는 증명이 아니다.

## 3. 실제 기여 후보와 현재 구현

주 기여 후보는 **결함 위치 힌트 없이 entrypoint에서 구체 파라미터 인스턴스를 구성하고, 컴파일 공유 단위와 호출 위치별 정보를 분리해 유지하며, 지원 범위와 결과의 의미를 추적할 수 있는 자동 분석 대상 구성 시스템**이다. 아래 설계가 실제 문제를 해결한다는 증거가 붙어야 논문 기여가 된다.

| 필요한 설계 | 단순 처리의 한계 | 현재 근거 | 아직 필요한 증거 |
|---|---|---|---|
| entrypoint에서 도달하는 구체 인스턴스 구성 | 템플릿 이름 목록만으로는 실제 파라미터·조건·반복·의존성을 결정할 수 없음 | 지원 구문에 한정한 [탐색 구현](../src/targets.rs), 구체 파라미터·미지원 기록 | 개발과 분리된 자료의 적용성, 누락/미지원과 수동 준비 비용 |
| 컴파일 단위와 호출 위치의 분리 | 템플릿 이름만으로 공유하면 다른 구성을 섞고, 공유 산출물만 남기면 서로 다른 호출 맥락을 잃음 | `ConcreteFuzzTarget`의 부모/자식·호출 정보와 `CompileUnit`의 별도 구조. 정상 실행에서 반복 인스턴스 비교 | 지원 범위 안의 불변조건 설명, 해당 분리가 결과·비용에 필요한 이유 |
| 원본과 wrapper의 계산·신호 대응 | 컴파일 성공만으로 두 실행의 경계값 대응을 알 수 없음. 최적화에서는 신호가 소실될 수 있음 | O0·scalar·고정 정상 입력의 경계 비교 144/144 | 진행 중인 O0/O1·배열 지원 범위. 일반 의미 동등성은 별도 미입증 |
| 결과의 의미를 보존하는 검토 연결 | 위치 일치·부분 결과를 고유 원인이나 프로젝트 결함으로 바꾸면 과대 주장 | 오프라인 기록/집계의 층·unknown·모순 처리 | 실제 결과의 대응·귀속과 같은 수준 비교. 메타데이터 검사는 의미 인증이 아님 |

`instance_key`는 소스·템플릿·파라미터 구성 식별자이며 그 자체를 모든 호출 위치의 고유 ID로 부르지 않는다. 호출 위치·부모 경로와 함께 해석한다. 컴파일 재사용도 호출 맥락의 안전성이나 프로젝트 수준 판정을 공유한다는 뜻이 아니다.

이 구성요소들을 나열하는 것만으로 충분하지 않다. 원고에는 **장애 → 설계 선택 → 성립 조건 → 효과 → 실패 범위**를 연결한다. 새 암호 이론이나 복잡한 알고리즘 이름은 필수 조건이 아니지만, 비자명한 문제 해결과 검증 가능한 효과는 필요하다.

## 4. 지금 하는 작업이 기여에 얼마나 직접 연결되는가

| 작업 | 기여와의 관계 | 완료 후 넘지 말아야 할 주장 경계 |
|---|---|---|
| NE-01 정상 실행 | 자동 구성 결과가 실행되고 원본 경계에 대응한다는 제한된 기능 증거 | 정상 입력 일치를 모든 입력의 의미 보존으로 확대하지 않음 |
| NE-02·03 컴파일/비용 | 호출 정보를 유지한 재사용의 공학적 효과. 원본 포함 12→8회, 준비 약 39.55% 감소 | 준비+정상 검증 합계는 개선되지 않음. 재사용 원리의 신규성·총비용 우위 미입증 |
| AG-01 오프라인 오류 수정 | 성과를 잘못 세지 않기 위한 평가 기반 | 테스트 수와 구현량을 연구의 주 기여로 제시하지 않음 |
| NC-01 정상 호환성 | 최적화·배열 조건에서 대응의 지원 경계 확인. 현재 실행 작업이 담당 | 결과가 끝나기 전 성공을 가정하지 않음. 지원 범위를 무한히 확대하지 않음 |
| D2 원고 초안 | 해결한 문제와 근거의 연결을 글로 드러내어 빈칸을 확인 | 원고가 완성돼도 기여가 입증되거나 평가가 끝난 것은 아님 |

근거와 수치는 [색인](paper_evidence_index.md)과 [체크포인트](../reports/research-checkpoint-2026-10-01/REPORT.md)에 있다. 기존 P2의 inference 관측은 연구 동기 신호지만, 정답 위치 후보를 새 일반 기준의 확인된 고유 원인으로 승격하지 않는다.

현재 사용할 수 있는 문장:

> 지원하는 Circom 구문 범위에서 entrypoint로부터 구체 컴포넌트 대상을 자동 구성하는 시스템을 구현했다. 컴파일 산출물 공유와 호출 위치별 정보를 분리했으며, 작은 정상 회로의 제한된 입력에서 계산 경계 대응과 컴파일 작업 감소를 확인했다.

아직 달성한 사실로 쓸 수 없는 목표 문장:

> 결함 위치 정보 없이 실제 프로젝트를 자동 분해하여, 전체 분석보다 같은 자원에서 더 많은 검토된 고유 원인을 더 낮은 총비용으로 얻는다.

## 5. 다음 판단 기준

NC-01의 고정 조건표가 끝나면 지원/미지원과 비용을 정리하고 정상 예제를 계속 추가하는 대신 N4의 남은 비교 가능성 조건을 판단한다. 다음 연구 주장을 채택하려면 아래 질문에 근거로 답해야 한다.

1. 어떤 기존 준비·분석 장애를 어느 설계가 해결했는가? 준비 실패와 수동 개입까지 포함해 설명할 수 있는가?
2. 핵심 설계가 없거나 단순한 대안을 썼을 때 무엇이 달라지는가? 같은 지원 조건과 비교 수준에서 그 효과를 분리할 수 있는가?
3. 검토된 성과·적용성·비용 중 실제로 입증한 이득은 무엇이며, 개발 노출과 미판정은 결론을 얼마나 제한하는가?

이 질문에 답하지 못하면 현재 상태는 유용한 구현과 예비 관측으로 기술한다. 강한 기술적 기여로 과장하지 않고 주장 범위나 설계를 재판단한다. 이는 새 평가 실행 지시나 N5 고정이 아니며 기존 작업 순서·상한을 대체하지 않는다.

## 6. 중립 표기와 수동 업로드 준비

공유 대상 문서에서 작업 담당 귀속 5곳을 확인했다. 인계 안내의 제목 2곳을 중립화했다. 고정 정상 실행 문서의 3곳은 원본을 덮어쓰지 않고 아래 공유용 편집본으로 정리했다.

- [실행 보고서 공유판](../reports/n4-1-normal-execution-2026-10-01/REPORT.public-v2.md)
- [실행 범위 공유판](../reports/n4-1-normal-execution-2026-10-01/SCOPE.public-v2.md)
- [편집 출처·해시](../reports/n4-1-normal-execution-2026-10-01/public-v2-provenance.json)

공유판은 담당 표기만 중립화했으며 수치·조건·판정·당시 검사 결과는 같다. 사전 실행 범위를 사후 새로 고정한 것으로 표현하지 않는다. 원본 사본과 해시는 계속 보존한다. 출처 경로·외부 저장소 브랜치명·귀속 금지 규칙을 작성자 표기와 혼동해 지우지 않는다.

**현재 전체 작업 트리는 업로드 준비 완료로 판정하지 않는다.** 확인 시점에 D2 원고와 NC-01 구현·실험이 진행 중이며, 원본 고정 문서에는 당시 담당 표기가 남아 있다. 원본까지 일괄 업로드하면 그 표기도 공개된다. 후속 업로드 점검에서는 공개 파일 목록과 참조 연결을 함께 확정해야 한다. 공유판 생성만으로 저장소 전체의 문자열 제거를 완료했다고 쓰지 않는다.

수동 업로드 시점은 해당 구현·실험의 완료 범위, 그 최종 코드에 대한 필수 검사, 문서와 수치의 일치, 중립 공개판/원본 보존의 파일 선택 및 링크가 함께 확인된 때다. 연구가 모두 끝나야 업로드하는 것은 아니며 검토 가능한 개발 체크포인트면 된다. 결과 확인 시 이 조건의 충족 여부를 명시하고 업로드는 miiz가 수행한다. 자동 commit/push/PR이나 별도 상시 감시는 설정하지 않았다.

## 7. 이번 확인 범위

원문 문헌의 관련 절, N2/N3와 현재 완료 보고서, 자동 구성·컴파일 단위 자료 구조를 읽었다. 코드 변경·회로 실행·퍼징·후보 재현은 하지 않았다. 진행 중인 NC-01 산출물의 결과는 근거로 사용하지 않았다. 고정 문서와 측정 코드의 원본을 보존하며, 변경은 이 위치 기록·중립 공유판·인계 제목·계획의 D3 행에 한정한다.

공유판 두 개의 본문 숫자열이 원본과 동일하고, 참조 원문·측정 코드·읽은 구현 파일 9개의 SHA-256이 작업 전후 동일함을 확인했다. 새 공유판의 파일 해시는 편집 출처 JSON과 일치한다. 변경 문서의 로컬 링크·앵커·공백을 확인했으며 코드 검사나 실험을 다시 실행하지 않았다.
