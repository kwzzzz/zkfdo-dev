# J 보강 설계 2.1 — A 개발 측정 덧붙임

A는 개발 세트다. 이 결과는 J 보강의 성과가 아니다. 설계 2판은 보존한다.

1. **④에도 직접 완성을 허용한다.** 정방향으로 정한 호출 입력을 고정해 국소 모델을 구한 뒤, hint 주입 또는 `constraint_witness`로 전체 witness를 만든다. 두 경로 모두 원본 전체 R1CS·같은 목표·입력 범위를 통과해야 도달이며, L1에는 같은 입력의 정상 계산 대비 최상위 영향 검증이 추가된다. **반박:** ③만 직접 완성을 사용하면 모델 재현 경로의 차이를 정제 효과로 오해한다. **답:** ③과 ④에 동일한 완성·검증 수단을 주고, 정제 사용 여부를 따로 비교한다. 이번에는 ④를 구현하지 않는다.
2. **측정 단위는 고유 요청이다.** `(revision, queue_order, 원래 request SHA)`로 묶고 동일 요청 사본의 내용 일치를 확인한다. 요청마다 세 군을 한 번씩 실행하고, 결과에서 고정된 127사례의 클래스를 찾아 비교한다. 15요청이라는 수는 index에서 다시 확인한다. **반박:** 사례마다 실행하면 요청 내부의 모든 클래스를 중복 판정하고 비용·결론 수를 부풀린다. **답:** 실행 수·전체 클래스 수·선정 사례 수를 각각 보고한다. 2차의 127사례별 372실행 견적은 이번 계획에 사용하지 않는다.
3. 세 군은 **같은 바이너리·seed·요청 상한**을 사용한다. 기본 → 클래스별 sweep 20초 → 같은 sweep+직접 완성 순으로 옵션만 추가한다. 상한은 `ceil(2 × (해당 요청의 v2.2 wall_seconds + 전체 클래스 수 × 20초))`다. 전체 클래스 수는 사례 수나 unknown 부분집합 수로 대신하지 않고 제공된 `result.json` 사본에서 확인한다. **반박:** ①′는 ①보다 총 배제 탐색량이 많을 수 있다. **답:** ①→①′는 배분과 추가 탐색량의 효과이며, 직접 완성의 증거는 ①′→③a로 판단한다. 외부 상한 종료는 미완료로 따로 기록한다.
4. **준비 공유의 범위를 제한한다.** 기존 내용 기반 컴파일 캐시는 같은 요청의 세 군이 공유한다. 판정 instance-store는 군별로 나눠 이전 결론의 재사용을 막는다. 컴포넌트 컴파일·정상 witness 생성 등 캐시되지 않는 준비는 반복하고 실제 시간을 적는다. **반박:** 먼저 실행한 군만 cold compile 비용을 부담한다. **답:** 관측 wall, 컴파일 비용, 준비·판정 단계 비용을 함께 제시하며 warm-cache wall 차이를 알고리즘 속도 향상으로 해석하지 않는다.
5. 직접 완성은 기존 verdict를 바꾸지 않는 별도 결과다. 기존 `unknown`과 검증된 `constraint_witness` 도달이 함께 있으면 두 칸을 보존한다. 목표 매핑·원본 전체 검사·Rust/snarkjs 기록이 빠지면 도달로 합치지 않는다. 같은 클래스가 기존 배제와 직접 완성 도달을 함께 보고하면 충돌로 표시하고 자동 승격하지 않는다. **반박:** 별도 도달을 기존 verdict의 개선으로 합치면 판정 계약이 달라진다. **답:** 원래 판정 변화와 보충 도달을 별도로 집계한다.
6. 국소 반박 재확인은 후보가 강제하지 않는 main 입력을 모두 자유롭게 둔 **원본 전체 O0 exact 후보** 질의다. UNSAT은 명시한 후보·입력 계약 범위의 배제이며 부품의 모든 위반 부재가 아니다. SAT는 `recheck_not_refuted`, timeout은 unknown이다. 먼저 합성 회로에서 고정 해제로 SAT가 되는 경우·해제 후에도 UNSAT인 경우·대응 누락을 시험한다. aq 캐시는 지정된 O0 파일만 읽고, 새 측정에서 만든 O0를 쓰면 기존 O0 R1CS SHA와 일치를 요구한다.
7. **가장 짧은 aq-011 한 요청으로 전체 시간을 낙관적으로 외삽하지 않는다.** 각 요청의 과거 시간·전체 클래스 수를 유지하고 시범에서 관측한 군별 배율과 절대 추가 비용을 적용한다. 24시간 관문은 재계산된 전체 예상에 적용하며, 전 회로의 난도 차이는 여전히 미검증이다. 이미지 관문은 `1.2×관측 peak+보존분`, 부족하면 대기·compact 없이 상태를 저장한다. 작업 공간 정리 전에 결과·진단·직접 완성 증거를 보존한다.

**확인한 것:** 직접 완성은 별도 `j-boost.json` 기록이고, 컴파일 캐시는 존재하지만 witness 생성의 공통 캐시는 없다. 제공된 사례 폴더에는 전체 결과 사본이 있어 클래스 수를 확인할 수 있다.

**추정한 것:** 공정 예산과 직접 완성의 실제 효과, 시범 이후 비용 배율, 24시간 내 전체 완료 가능성은 아직 측정하지 않았다.
