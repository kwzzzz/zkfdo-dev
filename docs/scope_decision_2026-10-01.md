# N3 평가 범위·최소 개발 범위 결정 초안 (2026-10-01)

**상태: 권고 초안 작성 완료, 최종 결정 대기. 담당: miiz. 평가 프로토콜은 미고정이다.** 이 문서는 N1·N2를 통합한 검토안이며 N3 최종 결정이나 N4 착수·N5 고정·평가 실행을 뜻하지 않는다. 아래 수치 상한은 검토를 위한 계획값이지 완료 일정의 약속이 아니다.

**주 기여 가설은 실제 entrypoint에서 결함 위치를 사용하지 않고 분석 대상을 자동 구성하는 분해 시스템이다.** 랭킹은 기존 구현과 RQ2 보조 가설을 유지한다. 맥락 후보배제는 자동 분해 결과의 신뢰성을 검증하는 과제이며 연구 중심을 맥락 오탐 제거로 전환한다는 결정이 아니다. 기술적 차별성·개발과 분리된 평가 성과·신뢰성·총비용의 성립 조건과 재검토 기준은 §8에 둔다.

기준은 [현재 계획](plan_revision_2026-10-01.md)과 [평가 설계](evaluation_plan_2026-10-01.md)다. 근거는 완료된 [N1 감사](../reports/sok-artifact-audit-2026-10-01/REPORT.md)·[사례별 근거](../reports/sok-artifact-audit-2026-10-01/evidence-summary.json), 완료된 [N2 검토](../reports/methodology-review-2026-10-01/REVIEW.md)다. N2는 N1을 보지 않고 독립 검토했으므로 두 보고서의 결론을 그대로 합치지 않고 아래에서 조정했다. 기존 보고서·고정 자료·판정은 수정하지 않았다. 이번 작업은 문서에 한정하며 후보 소스 추가 조사·컴파일·퍼징·재현·코드 변경을 하지 않았다.

## 1. 전체 모수와 지원 가능한 부분집합

**권고 결정.** 주 설계는 공개 벤치마크의 적용성·검토된 결과·총비용 평가로 둔다. 다음 세 층을 분리한다.

| 층 | 현재 근거와 역할 | 보존할 상태 |
|---|---|---|
| 전체 사례 목록 `C` | Circom 70개 사례 ID. 자료 범위와 누락을 감사하는 분모 | 노출, 부재, 미지원, 준비 실패, unknown을 포함한 전 사례 |
| original 선언층 `O` | 70건 중 경로 선언과 공개 original 결과가 있는 56건 | 공개 메타데이터 선언일 뿐 현재 준비·production 성공이 아님 |
| 평가 실행 단위와 지원층 | §3의 실행 단위 `U`를 먼저 정의하고 방식별 준비 상태를 기록. 양쪽 모두 준비된 `U_both`는 조건부 비교층 | 전체 `U`의 양쪽 성공·한쪽 실패·양쪽 실패·미지원·미확인과 비용을 별도 표로 유지 |

사례 ID 수, 실행 단위 수, 검토된 고유 원인 수를 각각 센다. 사례와 실행 단위는 여러 대 여러 대응일 수 있으며 사례 라벨을 검토된 원인으로 자동 승격하지 않는다. `70→56→지원 부분집합`은 사례의 처리 흐름을 보여 주지만, 실행 단위의 분모는 56과 같다고 가정하지 않는다. 적용성은 사례 기준 처리 현황과 중복 제거한 실행 단위 기준 준비율을 함께 보고한다. 확인된 결과를 얻은 비율은 전체 예정 실행 단위와 `U_both`에서 각각 보이되 후자를 전체 성과로 대체하지 않는다.

original 부재 14건은 별도 부재층으로 보존한다. 이번 주 비교에서 임의 wrapper를 만들어 original을 대체하지 않는다. 나중에 entrypoint 근거를 새로 확보하면 버전이 다른 목록과 노출 이력으로 남기고, 70/56 감사 스냅샷은 보존한다. 알려진 탐지 성공, 패치 존재, oracle 적합성만으로 전체 모수에서 삭제하지 않는다. oracle 범위의 사전 메타데이터 분류는 `범위 안/밖/불명` 조건부 분석에만 사용하고 미탐을 본 뒤 재분류하지 않는다.

**근거.** N1 §3·4·7: 70/56/14, 실제 사례 경로 저장소 27개, original이 있는 저장소 23개. original 경로가 빈 14건도 `Compiled Original=true`여서 공개 flag는 준비 성공의 증거가 아니다. N2 M6·D5와 평가 설계 §2는 전체 분모·실패 보존을 요구한다.

**남은 불확실성.** 각 original의 실제 entrypoint 역할·설정·의존성·현재 지원 상태, 14건 각각의 부재 원인, 유일한 실행 단위와 고유 원인의 수는 미확정이다. 공개 결과의 비TP를 확정 FalseNegative로 바꾸지 않는다.

**완료·중단 기준.** N3 최종 결정에는 포함·제외·부재·unknown 처리 규칙을 채택하고 사례↔실행 단위 대응표의 작성 책임을 명시해야 한다. N5 전 실행 단위 키와 예정 분모가 재계산 가능해야 한다. 조건부 성공층만 보고 전체 실패를 누락하는 분석은 중단한다. 비교 가능한 단위가 0개면 적용성 분석만 남긴다(§6).

## 2. 노출 정책과 주장 범위

**권고 결정.** 노출을 단일 exposed 플래그로 압축하지 않고, 날짜·사례/프로젝트 범위·근거·unknown을 가진 별도 이력으로 둔다.

| 이력 | 구분할 의미 |
|---|---|
| 개발 사용 | 타깃 구성·판정·순서·도구 선택을 조정하는 데 사용했는가 |
| 실행 | backend 실행이 있었는가. 실행 사실과 후보/결과를 보았는지도 구분 |
| 준비·컴파일 | 준비 또는 컴파일했으나 퍼징하지 않은 이력 |
| 소스·패치 열람 | 원인 소스·수정 내용을 실제 확인한 이력 |
| 프로젝트 opened/provenance | repo를 열거나 패치 확보를 시도했으나 해당 원인 소스 열람은 unknown일 수 있음 |
| 메타데이터 / 공개 결과 지식 | 이름·위치·commit 등의 지식과 공개 탐지 성패 지식을 각각 기록 |

09-24 제외목록은 역사적 스냅샷으로 보존하고 N1의 T2b·P2 후속 이력을 덧붙인 새 노출 장부를 사용한다. 직접 노출과 같은 프로젝트·계열을 통한 개발 지식은 별도다. 기존 미등재 5건·3repo를 미노출로 복원하지 않는다. 기록이 없는 경우도 `never-exposed` 대신 unknown이다.

70건 전체의 공개 결과 지식을 이미 보았으므로 현재 설계는 **노출을 공개한 공개 벤치마크 평가**다. 개발 사용층을 별도로 보고하고, 개발에 직접 사용한 사실이 확인되지 않는 층도 `개발 사용 미기록/unknown`으로 명명한다. 개발층을 포함한 집계는 개발·벤치마크 기술 결과이며 미노출 일반화의 증거가 아니다. 전체 70건은 자료 감사 분모로 유지하고, 향후 실행 대상에서 개발층을 분리하거나 제외하는 사전 규칙은 이유와 개수를 함께 남긴다. 방법 동결 뒤 벤치마크 실행에서도 대상별 성공을 보고 방법을 조정하면 해당 결과는 개발/탐색 층으로 기록한다.

**근거.** N1 §6: 직접 제외 22건, 프로젝트 제외에 따른 전체 41건, 이후 T2b 조사·P2 실행, 70건의 결과 지식 노출. 5건·3repo에는 소스/패치 검토 또는 같은 프로젝트 opened 이력이 있다. N2 D5와 평가 설계 §2의 노출층 구분을 적용한다.

**남은 불확실성.** 노출 기록의 완전성, 가족관계에 따른 노출 전이, metadata-only로 기록된 자료의 과거 개발 사용 여부는 미확정이다. 미노출 독립 집합은 이번 두 보고서로 확보되지 않았다.

개발·규칙 선택에 사용하지 않은 자료/계열을 방법 동결 뒤 평가하는 **개발과 분리된 평가**와, 소스·메타데이터·공개 결과까지 보지 않은 **미노출 평가**는 다르다. 전자는 노출 이력을 공개한 공개 벤치마크에서도 제한적으로 설계할 수 있으나 해당 층의 개발 미사용 근거가 필요하다. 공개 결과를 알고 규칙을 고른 영향까지 없었다고 보장하지 않는다. 현재 그 독립성은 항목별로 확인할 과제이며, 후자의 일반화 근거는 확보되지 않았다.

**완료·중단 기준.** N3 최종 결정에서 개발층의 실행·보고 위치와 계열 전이 규칙을 채택하고, N5에서 각 단위의 노출 근거와 unknown을 기록한다. 이를 못 하면 노출층별 기술 결과까지만 보고한다. 별도 독립성 근거 없이 미노출 일반화 주장을 하는 것은 중단한다. 새 후보 확보를 자동으로 이어서 진행하지 않는다.

## 3. 프로젝트 계열·실행 단위·entrypoint 역할

**권고 결정.** 실행 단위는 **정규화한 프로젝트 식별자 + 정확한 commit/허용 패치 + entrypoint + 실행을 실제로 바꾸는 설정**으로 정의한다. 설정에는 compiler/backend revision, 의존성·include 해석, 컴파일 옵션, 실행 입력 생성에 반영되는 도메인을 포함한다. 동일 실행의 검토용 속성·predicate·계약 조건·정답 라벨 차이는 별도 검토 열이며 새 실행 단위나 추가 예산 사유가 아니다. 입력 계약이 실행을 바꾸는지 검토만 조건부로 하는지도 구분한다. family ID는 독립성·군집 분석용 열이지 모든 관련 repo를 하나의 실행으로 합치는 키가 아니다. 전체/분할 방식과 반복은 같은 단위의 비교 조건이며 정답 라벨 수만큼 새 예산을 주지 않는다.

- N1의 36개 `(Project, Commit, path)` 묶음은 설정 미검증 **잠재 묶음**이다. 같은 단위에 연결된 여러 사례는 하나의 예산과 여러 검토 라벨로 관리한다. 서로 다른 설정이면 왜 다른지 증거를 남긴다. 준비/컴파일 캐시 공유, 퍼징 실행 재사용, 원인 중복 제거, 호출 위치별 맥락 판정은 별개다.
- Telepathy website ID 별칭과 실제 Project를 구분한다. Darkforest/Panther/Spartan의 관련 repo는 근거별로 alias/fork/후속 코드 후보를 기록한다. 같은 조직만으로 합치거나 다른 URL만으로 독립 선언하지 않는다. 공유 라이브러리·원인이 확인되면 계열과 원인 군집에 반영한다. unknown이면 독립 계열 수를 부풀리지 않고 관련 묶음별 결과를 보여 준다.
- production/test/역할 unknown을 모두 적용성 목록에 남긴다. 역할과 설정을 확인한 test entrypoint도 공개 벤치마크의 별도 층으로 비교할 수 있다. production 일반화는 근거 있는 production층으로 제한한다. `generated`는 생성 방식 정보일 뿐 production/test의 대체 분류가 아니다. 역할 unknown은 전체에 남기고 production 성공으로 세지 않는다.
- root/child는 특정 entrypoint에 상대적으로 기록한다. root 원인을 제외하지 않으며 분할 이득이 없을 수 있는 사례로 보고한다. 해당 root에는 호출자 배제가 적용되지 않으므로 `N/A`로 기록하고 맥락 배제율의 분모에서 따로 설명한다. root 존재 자체로 새 조각·예산을 추가하지 않는다. 탐색 불완전으로 child가 보이지 않는 경우를 root-only나 타깃 0으로 판정하지 않는다.

**근거.** N1 §4·5·7의 ID 불일치·계열 unknown·36개 잠재 묶음·entrypoint 한계, N2 §3.6·4.7 및 D5, [T6a 보고서](../reports/t6a-compile-reuse-2026-09-26/REPORT.md)의 컴파일 재사용과 호출 맥락 구분. N1에 인용된 zkopru 16개 production 경로의 역사적 root/child 판정은 공개 tester 경로로 이전하지 않는다.

**남은 불확실성.** family 경계·정확한 의존성·동일 설정 여부·production 연결·컴파일 최적화 후 신호 대응은 미확정이다. 사이트 ID 접두 28개 문자열을 28개 프로젝트로 세지 않는다.

**완료·중단 기준.** N5 전 사례↔실행 단위↔원인↔호출 위치의 연결과 예산 배정표를 고정한다. 동일 여부를 확인 못 한 묶음에 서로 독립인 것처럼 반복 예산을 주지 않는다. 단위 키가 불명확하면 그 항목은 실행 보류/unknown으로 남긴다. 독립 계열이 확인되지 않으면 계열 일반화와 그 가정에 기댄 통계는 중단한다.

## 4. 동일 검토 수준, 성과 지표와 종료 정책

**권고 결정.** 주 비교의 확인 수준은 양쪽 모두 **사전 속성·입력 전제·고정 원본 제약 전체·같은 원인 귀속을 통과한 컴포넌트 확인**으로 맞춘다. 통째 후보도 같은 귀속과 컴포넌트 증거 의무를 충족해야 하며, 그 연결이 불가능하면 미판정이다. 전체 실행이라는 이유만으로 도구의 경고를 확인된 원인으로 세지 않는다. 컴포넌트 확인, entrypoint 전체의 TCCT 확인, 프로젝트 의미 속성 위반 확인을 별도로 기록하고 합산하지 않는다. 마지막 두 층은 초기에는 사전 범위를 정한 수동 사례연구로 제한한다.

| 지표 | 권고 역할 | 해석 제한 |
|---|---|---|
| entrypoint 실행 단위별 하나 이상 확인 | 주 요약: 같은 검토 수준의 결과를 하나라도 얻었는가 | 최소 성과이며 발견 깊이·원인 수를 대체하지 않음 |
| 최초 확인 대상 시간 | 주 요약: 사후 검토를 통과한 후보의 최초 생성시각. 그 후보의 timestamp만 없으면 연결된 run의 완료시각 상한 | 확인 후보 자체가 없으면 미관측. 사람의 검토 완료시각과 비용은 별도. 첫 경고 시각을 곧 확인 시간으로 쓰지 않음 |
| 검토된 고유 원인 수 | 함께 보고할 수율 지표. 같은 단위·자원·종료정책 아래 파이프라인 결과 비교에 사용 | 순수 oracle 탐지능력이나 분해만의 인과 효과로 해석하지 않음 |
| 적용성·비용·미판정 | 위 세 지표와 함께 해석할 필수 결과 | 한쪽 준비 실패를 양쪽 준비 성공층에서 조용히 삭제하지 않음 |

고유 원인 수 비교가 무조건 무효라는 N2 M2의 강한 해석은 채택하지 않는다. 탐색 배분·종료를 포함한 시스템 수율은 연구 대상이 될 수 있다. 반대로 이진 지표로 바꿔도 첫 미확인 후보에서 종료되면 유효한 후속 후보를 놓치므로 비대칭이 사라지지 않는다. 후보가 나중에 맥락 배제돼도 이미 잃은 탐색 기회는 복구되지 않는다.

**종료·잔여 예산 권고.** 엔진의 첫 후보 종료를 바꾸는 개발은 초기 범위에서 제외한다. N2가 확인한 것은 논문·단일 함수의 동작이며 CLI와 관리층을 포함한 캠페인 상한은 미확인이다. N4에서는 기존 관리층의 지원과 기록 가능 여부만 확인한다. 지원된다면 N5에서 결과 종류·검토 판정에 의존하지 않는 **entrypoint 공통 총예산 내 재시작 정책**을 우선 검토한다. seed·반복 상한·호출 비용·종료 사유 규칙을 사전 고정하고 조각마다 전체 예산을 복제하지 않는다. 같은 규칙을 적용한다는 것이 전체와 분할의 프로세스 호출 수를 강제로 같게 만든다는 뜻은 아니다.

기존 기능으로 지원되지 않으면 평가 결과를 보기 **전에** native-stop 조건을 택한다. 이 경우 확인된 실제 파이프라인 수율과 조기 종료·미사용 잔여 예산·중복 반환을 함께 보고하고, 더 긴 탐색을 공정하게 비교했다거나 실제 사용 자원이 같았다고 주장하지 않는다. 할당 자원 상한과 사용한 CPU/벽시계 시간을 구분한다. 원인 확인·후보 배제·중복 판정을 보고 유리한 쪽만 다시 실행하는 정책은 허용하지 않는다. 환경 장애 재시도는 정상 조기 종료 후 재시작과 별도다. 새 재시작 기능 구현은 이 초안으로 승인된 범위가 아니다.

**알려진 원인과 추가 원인.** 알려진 원인에는 실행 전 정한 사례별 기준을 양쪽에 동일하게 적용한다. 추가 원인에는 사전 일반 TCCT/속성·전제·귀속·검토 상한 규칙을 양쪽에 동일하게 적용한다. 이 기준을 통과하면 둘 다 `추가 확인` 층에 포함하고, 전체 수율을 낼 때는 알려진/추가 내역을 함께 보인다. 사후 새 명세가 필요한 원인은 어느 방식에서 나왔든 탐색적 결과로 분리한다. 분할의 추가 원인만 주 집계에서 제외하는 N2 M2 문구는 채택하지 않는다. 같은 위치·공유 패치·같은 경고명만으로 원인 동일성을 확정하지 않으며, 중복 여부가 불명확하면 별도 미귀속군으로 보존한다.

관측된 확인 0건과 검토 미완료를 구분한다. 양성은 전수 검토하고, 미판정 후보가 남아 결과가 달라질 수 있으면 `확인된 하한 0, 미판정 있음`을 보고하며 완결된 이진 실패로 치환하지 않는다. 준비 실패·timeout·미지원도 실제 상태를 유지한다. 발견하지 못한 실행의 시간을 0초로 쓰지 않는다. 예산 소진에 의한 관측 종료와 조기 종료를 구분하고, 일찍 끝난 실행이 전체 예산 동안 탐색된 것처럼 시간 분석하지 않는다. 반복을 독립 프로젝트로 세거나 성공한 seed만 고르지 않는다.

**근거.** N2 M1·M2·M4·M5·M8, §4.1–4.7·7.3·9; N1 §3의 verdict/TP 차이; 평가 설계 §4·5. N2의 비대칭 관측은 채택하되 비교 자체의 무효화와 이진 지표의 자동 공정성 주장은 제한했다.

**남은 불확실성.** CLI 전체의 종료 동작, 현재 관리층의 재시작 지원, 통째 후보의 동일 수준 귀속, 일반 predicate 적용 범위, 검토 시간 상한·정확한 후보 timestamp와 원인 중복 제거 가능성은 미확정이다.

**완료·중단 기준.** N5 전 종료·잔여 예산 분기 하나를 택하고 양쪽 동일 수준의 검토 예시와 기록 형식을 개발 자료에서 확인한다. 미확인 검토를 음성 처리하거나 수준이 다른 결과를 비교해야만 수치가 나오는 경우 우위 비교를 중단하고 하한·미판정·사례별 증거만 보고한다. 원인 귀속이 확보되지 않으면 고유 원인 수 대신 후보 수로 성과를 대체하지 않는다.

## 5. 특정 후보 배제, 입력 전제와 abort형

**권고 결정.** 초기 맥락 판정은 **특정 후보의 경계값이 특정 호출 위치에서 불가능하다는 배제**로 한정한다. 대상은 출력 차이형의 경계 입력·출력, 계산 abort형의 경계 입력이다. 내부 중간값 전체를 불필요하게 고정한 뒤 얻은 모순을 경계값의 불가능성으로 확대하지 않는다.

근거는 고정 compiler/옵션으로 생성된 entrypoint 제약에서 확인된 부분집합과 검증된 신호 대응이다. 초기 지원은 직접 호출자 범위에서 증거가 확인되는 제약 관계 한 종류로 제한한다(§6). 소스의 `assert`, tag, witness 계산 분기, 정상 실행에서 본 값 자체는 실제 강제되는 제약의 대용물이 아니다. 유한체 범위·최적화·제거 신호를 정확히 처리하지 못하면 미판정이다. 제약 부분집합의 모순은 전체의 모순으로 이어질 수 있지만, 부분집합과의 양립은 전체 양립이나 프로젝트 결함의 증명이 아니다.

호출 위치별 배제·미판정 및 범위를 남기고, **알려진 관련 호출 위치 전부를 완전하게 열거하고 배제했을 때만** 그 후보의 해당 entrypoint 맥락 배제로 집계한다. 누락 위치·unknown·미지원이 하나라도 있으면 부분 결과와 전체 미판정을 보존한다. 컴파일 재사용으로 호출 위치를 지우지 않는다. 후보 배제는 해당 원인 전체의 배제·안전성 증명·경고 삭제·경고 단위 오탐 판정이 아니다. 원래 후보·원인 연결과 배제 증거를 함께 남기며 자동 상위 반례 합성·원인 수준 배제는 보류한다.

| 판정 차원 | 권고 규칙 |
|---|---|
| 일반 속성과 입력 전제 | 알려진/추가 원인 모두에 사전 일반 TCCT 기준을 적용할 수 있게 설계한다. 기본 입력 도메인은 고정 인터페이스·field/shape 등 명시한 범위. 문서·주석·tag·`assert`의 가정을 자동으로 숨은 입력 제한으로 채택하지 않음 |
| 계약 조건부 검토 | 필요한 계약은 출처·범위·채택 시점·강제 여부를 실행 전에 명시하고 별도 층으로 보고. 전제 없는 검토와 계약 조건부 검토의 분모·확인 수를 섞지 않음 |
| 전제 위반 | 후보를 보존하고 어떤 전제를 위반했는지 표시. 그 계약 아래의 컴포넌트 확인은 아니지만, 그 자체로 맥락 배제·원인 안전·경고 오탐을 뜻하지 않음 |
| abort형 | 허용 입력, 고정 제약 전체를 만족하는 후보 증거, 같은 입력에서 정상 계산이 의미상 abort한다는 근거를 요구. 출력이 없는 후보에 가짜 출력을 부여하지 않음. 도구 crash·timeout을 의미상 abort로 세지 않음 |
| 별도 하드코딩 검사 | 출력 차이·abort·추가 검사 종류를 구분. 검사 경고만으로 일반 TCCT 위반을 자동 인정하지 않고 사전 속성 증거를 요구 |
| 미판정 | 대응 실패·지원 밖·시간 초과·불완전 호출 목록·배제 실패는 unknown. 배제 실패는 양립 가능 판정이 아님 |

**근거.** N2 §3.1–3.9, M3·M4·S2·S4. N1 §7의 public-original root/child unknown과 과거 판정 범위. 사전 입력 전제는 검토 속성의 도메인이 될 수 있지만 실제 회로가 강제한다는 주장은 별도의 증거가 필요하다.

**남은 불확실성.** 정확한 신호 대응, 직접 호출자 제약의 확보, 기존 검토 엔진 재사용 범위, 계약별 해석, 일반 TCCT 재검사의 지원 범위는 N4에서 개발 자료로만 확인할 사실이다. 현재 구현됐다고 선언하지 않는다.

**완료·중단 기준.** 개발 자료에서 전체 맥락과 양립하는 근거가 있는 후보를 잘못 배제하지 않는지, 독립 근거로 불가능한 후보를 배제할 수 있는지, 불완전 대응은 unknown으로 남는지 점검한다. 알려진 취약 원인의 모든 후보가 양립해야 한다는 N2 S1의 단순 기대는 채택하지 않는다. 특정 후보는 알려진 원인에 속해도 실제로 불가능할 수 있다. 건전하지 않은 배제나 검증 불가능한 대응이 나오면 자동 배제를 중단한다. 모두 unknown이면 건전성 실패로 단정하지 않되 효용은 미입증으로 보고한다. 수동 판정도 같은 증거 의무를 만족하지 못하면 unknown이다.

## 6. 기존 개발 자료의 최소 작업과 상한

**권고 결정.** N4는 별도 착수 범위를 정한 뒤 기존 개발 자료에서만 수행한다. 초기 대상은 이미 사용한 inference와 zk-email의 기록된 entrypoint·revision 최대 2개 프로젝트다. 의미 판정 통제에 필요한 기존 v1–v3 검토 기록은 재사용할 수 있지만 새 평가 후보를 열거나 부족한 수를 채우기 위해 다른 프로젝트를 추가하지 않는다. N2 D7의 전체 적용성 비중에 따른 선택은 새 후보 조사를 유발하므로, 현재 확인된 P2 개발 병목을 근거로 **외부 의존성 식별·준비 결과 연결 한 종류**를 우선한다.

다음은 **총 40 담당자 작업시간 이내**의 권고 상한이다. 8시간 담당자일로 5일 상당이며 경과일·완료 약속이 아니다. 각 항목은 자기 상한에서도 멈추며 미사용 시간을 이유로 새 기능을 추가하지 않는다. 추가 작업에는 별도 범위 결정 기록이 필요하다.

| 묶음 | 개발 자료에서 확인할 최소 범위 | 작업 상한 | 완료·중단 기준 |
|---|---|---:|---|
| 동작·증거 확인 | 기존 CLI의 첫 후보 종료·관리층 재시작 지원·시간 기록·양쪽 검토 연결 확인 | 4시간 | 동작과 unknown을 문서화. 새 재시작 기능·엔진 수정은 추가하지 않음 |
| 준비 병목 1종 | 외부 의존성의 식별·고정 및 타깃/실패 사유 연결. 기존 동작 보존을 포함한 최소 변경만 후속 범위에서 검토 | 12시간 | 기존 개발 사례의 누락 사유가 설명되고 해결 범위가 검증되면 종료. 함수 계산 파라미터·컴파일 타임 배열 지원까지 필요하면 unsupported를 남기고 중단 |
| 후보 배제 1범위 | 직접 호출자 제약·정확한 신호 대응으로 검증 가능한 관계 한 종류. 관계는 개발 근거와 건전성 검토 후 기록 | 16시간 | §5 통제를 통과하는 범위만 채택. 최적화 역복원·새 solver·전체 맥락 합성이 필요하면 자동 배제 미지원/unknown으로 축소 |
| 검토·정리 | 동일 원인 귀속, known/additional 대칭 규칙, 양쪽 동일 수준 예시, 비용·미판정·N5 기록 형식. 원시 후보 신규 생성 캠페인은 포함하지 않음 | 8시간 | 독립적으로 읽을 수 있는 증거와 미해결 표를 작성. 의미 기준을 맞출 수 없으면 확인 성과 비교 보류 |

함수·배열의 범용 해석기, 옛 Circom 전면 호환, 컴파일러 교체, 새 SMT 통합(N2 S3의 후단 제안), 신규 순위 튜닝, 적응형 배분, 주입 평가, 여러 도구, 원인 전체 배제는 보류한다. 기존 랭킹 구현·RQ2 비교 가설은 유지하며 새 튜닝을 이번 최소 개발에서 제외하는 것이 랭킹 폐기를 뜻하지 않는다. 맥락 판정에 할당한 시간은 타당성 확인의 상한이지 기여의 우선순위나 중심 전환의 근거가 아니다. 위 상한은 구현 허가나 도구 실행 지시가 아니다. 실제 코드 변경을 별도 범위로 진행한다면 기존 AGENTS.md의 필수 코드 검사를 포함해 상한·완료 여부를 판정한다. 기존 계약·판정은 고치지 않고 새 검토가 필요하면 새 버전으로 남긴다.

평가 후보는 N4 개발에 사용하지 않는다. N2 D6의 고정 전 후보 준비 허용은 자동 채택하지 않는다. 평가 대상의 새 소스 열람·준비가 꼭 필요하면 N3 최종 결정에 허용 작업·노출 기록·설정 변경 한계를 별도로 명시해야 한다. 그 전에는 metadata-only를 유지한다. N5에서는 준비 단계 자체를 사전 규칙으로 포함하고, 준비 결과에 따라 방법을 다시 튜닝하지 않는다. 평가 후보 zkFuzz 실행은 계속 N5 고정 전 금지다.

**근거.** [P2 개발 보고서](../reports/dev-rq1-pilot-2026-09-29/README.md)의 두 준비 병목, N1 §6·7의 기존 노출·지원 미확인, N2 D7·D8·§7.3. 과거 P2의 위치 일치·소스 판정을 새로운 검토 통과 성과로 승격하지 않는다. 위 40시간과 묶음별 상한은 근거에서 추정한 성능 수치가 아니라 범위 확장을 막기 위한 이번 권고값이다.

**남은 불확실성.** 외부 의존성 병목만 해결해도 준비가 가능한지, 기존 관리층으로 종료정책을 기록할 수 있는지, 한정 배제가 통제를 통과하는지, 충분한 동일 수준 검토 사례가 있는지는 미확인이다.

**완료·중단 기준과 주장 축소.** 상한 내 통과한 기능·미지원·비용을 그대로 고정 후보로 넘기고 실패한 범위를 자동 확대하지 않는다. 비교 가능한 단위 0개면 적용성 분석만, 단위 1개 또는 독립 계열 경계가 확인되지 않으면 사례연구/기술 비교만 수행한다. 여러 단위가 있어도 독립성·불확실성 근거 없이 일반적 우위로 넓히지 않는다. 기존 원인 5개·프로젝트 3개는 통계적 충분성 조건으로 재사용하지 않는다. 자동 배제가 실패하면 증거를 갖춘 수동 후보 판정과 unknown 보고로 축소하고 자동 판정 성과를 주장하지 않는다. 현재 결과 지식 노출 상태에서는 미노출 일반화 주장은 계속 보류다.

## 8. 자동 분해 시스템의 기여 성립 조건과 방향 재검토

**권고 결정.** 자동 분해 시스템을 주 기여 가설로 유지한다. 그 가설은 단지 기능을 모았다는 사실이 아니라 다음 네 축의 증거로 평가한다. 이 조건을 채웠다고 논문 채택이나 최초성이 보장되는 것은 아니다.

| 축 | 기여를 지지할 조건 | 부족할 때의 해석·재검토 기준 |
|---|---|---|
| 기술적 차별성 | 정답 위치 없이 실제 entrypoint에서 대상을 구성하는 규칙·지원 경계·인스턴스와 호출 맥락 보존·실패 처리의 설계가 설명 가능하고 재검증 가능해야 함. 선행 분해/합성/재사용과 다른 해결 문제와 설계 선택을 구체적으로 보임 | 선행 기능의 나열이나 컴파일 재사용 수치만 남으면 새로운 분석 기법 주장을 보류. 구현·적용성 연구로 기여 범위를 줄이고 차별성이 남는지 재검토 |
| 개발과 분리된 평가 성과 | 방법 동결 뒤 개발·선정 규칙 조정에 쓰지 않은 평가층에서 전체 분모·계열·동일 자원·동일 검토 수준으로 적용성, 확인 여부/시간/수율을 보고. 일반적 실용 이득 주장은 개발 사례 밖에서 뒷받침돼야 함 | 이익이 개발 1건 또는 불명확한 같은 계열에만 있으면 넓은 우위·일반화 주장을 보류. 독립성이 부족하면 공개 벤치마크 기술 비교/사례연구로 제한. 결과 지식 노출은 별도 한계 |
| 신뢰성 | 후보·원인·entrypoint·프로젝트 확인을 구분하고, 같은 검토 기준·원인 귀속·전제·unknown·호출 위치 누락을 보존. 특정 후보 배제의 보장과 비용을 검증 | 자동 배제 실패는 먼저 자동 판정 주장을 축소할 사유. 검토 수준도 맞출 수 없으면 확인 결과의 우위 비교를 보류. 배제율이 높다는 사실만으로 자동 분해의 기여가 성립하지 않음 |
| 비용과 실용성 | 준비·컴파일·탐색·맥락 판정·사람 검토·캐시 조건을 포함한 총비용과 자원 상한을 보고. 자동 구성의 이득이 어디서 비용으로 상쇄되는지 보임 | 준비된 상태에서만 빨라지거나 수동 보완 비용을 숨겨야 이득이 나면 총비용 개선 주장을 하지 않음. 제한된 조건의 이익/손실을 보고하고 적용 범위·운영 가치를 재검토 |

기술적 차별성이나 실용 이득을 뒷받침하지 못해도 음성 결과·적용성 한계는 보존한다. 그것이 자동 분해의 성능 우위를 입증한 결과로 바뀌지는 않는다. 랭킹 우위 부재는 자동 분해 가설의 기각과 같지 않으며, 자동 분해 이득이 있어도 랭킹 효과는 별도 비교가 필요하다. RQ2의 순위·전략 수·조건은 비용을 보고 N5에서 사전 선택하되 이번 N3에서 폐기를 확정하지 않는다.

**근거.** 현재 계획 §1의 자동 구성·확인 결과·맥락 신뢰성·총비용 기여 가설, N1의 독립성/지원 범위 미확보, N2 §2·6의 선행 경계와 증거 의무. 시스템의 기술적 차이를 무엇으로 뒷받침할지는 이 초안의 검토 대상이며 신규성 확인을 완료한 것이 아니다.

**남은 불확실성.** 개발과 분리된 평가층 규모·효과 크기·총비용, 기존 선행과의 세부 설계 차이, 제한된 배제의 효용은 미확정이다. CIVER 본문 접근 및 일부 문헌 세부 검토의 한계도 남아 있다.

**완료·중단 및 방향 전환 기준.** N4 상한 종료 시에는 지원 가능성과 검토 가능성만 판정하고 독립 성능을 선언하지 않는다. N5 이후 고정 평가에서 같은 수준의 성과·비용 근거가 모이면 네 축을 함께 재검토한다. 기술적 차이가 설명되지 않거나, 개발 밖 평가 근거가 없거나, 신뢰성 의무를 충족하지 못하거나, 허용 자원에서 실용 이득이 뒷받침되지 않으면 우선 해당 주장을 축소·보류한다. 일반적 시스템 우위가 성립하지 않으면 적용성/사례연구의 독자적 가치도 별도로 판단한다. 평가 결과에 맞춰 같은 자료로 방법을 튜닝해 재실행하는 것은 새 개발/탐색 작업이다.

**주장 축소와 연구 중심 전환은 다른 결정이다.** 맥락 오탐 제거·후보 배제로 중심을 옮기려면 그 방법 자체의 기술적 차별성·건전성·개발과 분리된 평가·비용 근거를 새로 검토하고 miiz의 별도 방향 결정 기록을 남겨야 한다. 랭킹을 폐기하거나 자동 분해를 포기하는 결정도 같은 방식으로 명시적 근거를 요구한다. 이번 초안은 어느 방향 전환도 확정하지 않는다.

| M2: 이진·시간 중심, 고유 원인 수 제한 | 수정 채택. 세 지표를 함께 보고 수율 비교는 유지. 이진 지표도 조기 종료의 영향을 받음. 추가 원인 규칙은 양쪽 대칭 |
| M3·S4: 특정 후보/호출 위치 배제 | 채택. 원인·경고 삭제 금지, 전체 관련 위치 누락은 미판정 |
| M4·M5: 전제·일반 속성·귀속 | 채택하되 일반/계약 조건부 층을 분리. 새 사후 명세는 양쪽 모두 탐색적 결과 |
| M6: oracle 범위 사전 분류 | 채택. unknown 유지, 전체 모수 보존, 결과를 본 뒤 범위 밖으로 이동 금지 |
| M7·M8: 용어·자원·반복 | 채택. '최초'·포괄적 '무명세'·'자동 프로젝트 확인'을 주장하지 않음 |
| S1: 취약판 미배제/수정판 배제 기대 | 제한. 특정 후보의 실제 양립/불가능 근거로 통제해야 하며 취약판 라벨만으로 유지 정답을 정하지 않음 |
| S3: SMT 후단, D6: 고정 전 후보 준비 | 보류. 현재 최소 범위에 새 solver나 평가 후보 개봉을 포함하지 않음 |
| D7: 적용성 비중이 큰 준비 병목 선택 | 제한. 신규 평가 후보 조사 대신 기존 P2 개발 근거로 병목 1종만 우선 |
| 문헌 접근·SoK 설정 | CIVER 본문 미접근과 일부만 읽은 문헌의 한계를 유지. 신규성 확정 근거로 쓰지 않음. SoK 실제 제한은 N1의 미해결 상태 유지 |

## 10. N3 최종 결정과 현재 다음 행동

이번 문서의 완료는 **권고 초안을 작성하고 현재 안내를 동기화한 것**이다. N1·N2는 각각 보고서 상태가 완료임을 확인했다. N3 진행 표는 `초안 완료·최종 결정 대기`로 남기고 담당은 miiz다.

miiz의 N3 최종 결정 기록에는 (1) 공개 벤치마크 주장과 개발층 처리, (2) entrypoint/계열·단위·root 정책, (3) 같은 검토 수준·지표·종료정책 선택 조건, (4) 전제·abort·후보 배제의 지원 경계, (5) N4 대상과 40시간 상한의 채택/변경, (6) 자동 분해의 기여 성립·주장 축소·방향 재검토 기준 및 N5 미결정 목록을 명시해야 한다. 이번 초안에 제시한 수치를 자동 승인된 예산으로 취급하지 않는다. 최종 결정 뒤에만 그 범위의 N4 작업을 별도로 시작한다.

## 11. 문서 변경 요약

- 이 초안에 요청된 7개 결정 항목과 자동 분해 기여 조건별 권고·근거·불확실성·완료/중단 기준 및 N2 권고의 조정을 기록했다.
- 현재 계획과 START_HERE의 N1 검산 예정 문구·N1/N2 시작 안내를 완료된 근거와 N3 최종 검토 안내로 바꿨다. N2는 보고서의 완료 상태와 접근 범위를 반영하고 N3는 최종 완료로 표시하지 않는다.
- 평가 설계·문제 정의·인계 안내는 초안의 위치와 후보 배제·지표 해석 경계를 연결한다. README의 오래된 다음 작업 문구도 N3 초안 최종 검토로 갱신했다. N1/N2 보고서, 과거 계획, 고정 프로토콜·manifest·계약·실행·판정은 보존한다.
- 로컬 링크·문서 내 앵커·상태/용어·변경 범위를 확인했고, N1/N2 보고서와 N1 근거 JSON의 SHA-256이 작업 전과 같음을 확인했다. 기존 인계 프롬프트 본문도 동일하다. 문서별 공백 검사와 `git diff --check`를 통과했다. 코드 변경이 없으므로 cargo 검사나 회로 도구는 실행하지 않았다. commit/push/PR은 하지 않았다.
