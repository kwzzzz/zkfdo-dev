# J 보강 3차 — A 측정 준비와 시작 관문 (2026-10-27)

**상태: 시범·전체 측정 미실행.** aq 실행기 v3_2는 신호로 정상 정지했지만, 프로세스 목록에 목적을 식별할 수 없는 `/bin/zsh ./watch.sh`(PID 90225)가 남아 있다. 사용자 지시는 자동 compact 감시기나 v3_2 재실행 스크립트가 없어야 한다고 정했으며, 시작 확인 수단을 **프로세스 목록과 state 직접 읽기**로 제한했다. 그 수단으로 `watch.sh`의 역할을 확정할 수 없어 이미지 쓰기를 시작하지 않았다. 이 프로세스를 종료하거나 스크립트 내용을 읽어 우회하지 않았다.

## 지시를 검토하고 고친 부분

- **127사례를 127번 실행하면 중복이다.** `cases/index.json`을 고유 요청으로 묶어 **15요청, 127사례, 전체 1,030클래스**를 확인했다. 각 요청은 세 군이 각각 한 번만 실행하고 127사례는 결과에서 선택한다.
- **①과 ①′의 총 탐색량은 같지 않다.** 클래스당 20초는 요청 공유 20초보다 총량을 늘린다. ①→①′는 예산 배분과 총량의 합친 효과로만 읽고, 직접 완성의 추가 효과는 ①′→③a에서 따로 본다. 군별 요청 상한과 seed는 같다.
- **시범 하나로 큰 요청의 시간을 확정할 수 없다.** 요청별 과거 시간을 유지하고, 시범에서 관측한 옵션의 추가 시간을 클래스 수에 맞춰 적용한다. 먼저 계산한 `과거 시간 + 20초×전체 클래스` 합계 **34.63시간**은 배정 예산을 모두 소모한다고 본 계획용 수치이며 실측 예상이 아니다. 시범 뒤의 재계산 없이는 24시간 관문을 판정하지 않는다.
- **준비를 전부 공유할 수 없다.** 원본 O0/O1·수정본 컴파일은 `lifting/mod.rs:3799–3915`의 내용·경로 캐시 키가 동일하므로 세 군이 공유한다. 부품 컴파일과 witness 생성은 매 군 다시 한다. instance-store는 군별로 격리했다. warm-cache 시간을 알고리즘 속도 향상으로 단정하지 않는다.
- **직접 완성의 도달은 기존 verdict를 덮지 않는다.** `result.json`과 `j-boost.json`을 분리해 저장한다. 직접 witness의 해시·Rust·snarkjs 검증이 갖춰진 경우만 보충 도달로 기록하고, 기존 배제와 충돌하면 충돌로 표시한다.
- **국소 반박 재확인의 UNSAT 범위는 정확한 후보·입력 계약뿐이다.** 합성 O0에서 무관한 main 입력을 풀자 SAT가 된 경우와 여전히 UNSAT인 경우를 확인했다. A 10사례는 아직 실행하지 않았다.
