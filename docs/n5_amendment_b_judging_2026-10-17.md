순서 (a)~(e)와 통과 조건(정직 witness 생성과 원본 R1CS의 Rust·snarkjs 만족)은 2026-10-10 보충 그대로다. (d)만 다음처럼 바꾼다.

2. 허용하는 설치 명령은 다음 표뿐이다. 표에 없는 경우, lock 파일이 없는 경우, lock 파일이 package.json과 맞지 않아 설치가 거부되는 경우는 설치하지 않고 (d) 실패로 둔다. `yarn.lock`에 `__metadata`가 있으면 Yarn 2 이상, 없으면 Yarn 1로 본다.

   | lock 파일 | 명령 |
   |---|---|
   | `package-lock.json` 또는 `npm-shrinkwrap.json` | `npm ci --ignore-scripts` |
   | `yarn.lock` (Yarn 1) | `yarn install --frozen-lockfile --ignore-scripts` |
   | `yarn.lock` (Yarn 2 이상) | `YARN_ENABLE_SCRIPTS=0 yarn install --immutable` |
   | `pnpm-lock.yaml` | `pnpm install --frozen-lockfile --ignore-scripts` |

   패키지 관리자 버전은 package.json의 `packageManager` 필드가 있으면 그 버전을 쓴다. 없으면 B의 첫 설치 전에 Node·npm·Yarn·pnpm 버전을 한 번 정해 설치 도구 기록에 적고 B 전체에 같은 버전을 쓴다. 패키지 관리자는 4항의 컨테이너 안에서 corepack으로 받는다. 받지 못하면 (d) 실패다.
3. 빌드는 (d)의 테스트·도구가 직접 실행하거나 이름으로 가리키는 package.json 스크립트 하나에서 시작해 고치지 않고 실행한다. 그 스크립트가 자동으로 부르는 pre·post 스크립트와, 그 스크립트가 패키지 관리자 명령(npm run, yarn, pnpm run, workspace 실행 등)으로 부르는 같은 저장소 사본 안의 package.json 스크립트(그 스크립트가 다시 부르는 것 포함)도 함께 돈다. 실제로 돈 스크립트의 package.json 경로·이름·순서를 모두 기록한다. 그 밖의 스크립트는 돌리지 않는다. 빌드 전체는 4항의 컨테이너 안에서 6항의 60분 안에 끝나야 한다.

## 4. 제보 전 분류와 사람 검토

1. B의 모든 L1은 사람 검토 전에 스크립트로 다음과 같이 분류한다. 분류 스크립트는 분류 결과만 출력하고 값은 출력하지 않는다.
   - 공개 입력(main의 public 입력 신호만, 출력은 넣지 않음): 기준 입력과 같은 채 도달(`public_inputs_equal` true)이면 **사설 도달**, 바꿔야 도달하면 **공개 입력 변경 도달**, 값이 없으면 **미상**(공개 입력 변경 도달처럼 취급).
   - 공개 출력: 대체 witness의 공개 출력이 정직 witness와 다르면 **출력 변경**, 같으면 **내부만 변경**, 값이 없으면 **미상**.
   - entrypoint: **배포**는 프로젝트의 빌드·배포 스크립트, verifier 생성 스크립트, README 중 하나가 직접 가리키는 main이다. 그 밖(test·mock·example 폴더, 라이브러리 시험용 main)은 **하네스**이고, 어느 쪽인지 모르면 하네스로 둔다. entrypoint 분류표(리비전, main 파일 경로, 분류, 근거 파일·줄)는 6절 4항 때, 1묶음 결과를 열기 전에 만들고 SHA-256을 기록한다.
2. "실제 취약점 후보"는 사설 도달 × 출력 변경 × 배포인 L1이다. 나머지 L1은 "제약 결함 확인"으로 따로 보고한다. 사람 검토는 기계 분류를 바꾸지 않고, 공격 가능성 판단(검증자나 앱이 공개 값을 어떻게 묶는지 등)은 별도 칸에 적는다.

## 5. S 퍼저 수정(중첩 배열 템플릿 파라미터)과 B S 재퍼징

1. 수정: zkFuzz의 위 미구현 분기만 구현한다. 수정 전 zkFuzz 커밋 SHA, 수정 diff 파일(새 테스트 파일 포함)의 SHA-256, 고친 바이너리 SHA-256, 빌드 명령과 cargo·rustc 버전을 기록한다. 중첩이 아닌 템플릿에서는 기존 바이너리와 출력이 같다는 차등 테스트를, 중첩 배열 파라미터를 가진 합성 템플릿에서는 panic 없이 도는 테스트를 기록한다.
2. W 확인: B 본 퍼징, mem20, A 퍼징의 모든 W·S ledger에서 이 panic 수를 센다. B의 W 단위 중 이 panic이 1회 이상인 단위가 있으면 그 W 단위도 고친 바이너리로 같은 설정으로 다시 퍼징하고, 그 단위의 본 W 결과는 다시 퍼징한 run으로 한다. A의 수는 개발 세트의 한계로 적고 A는 다시 퍼징하지 않는다.
3. 재퍼징: B의 S 30단위(10개 대상 × 3 seed) 전부를 대상, seed, 순서, 3,600초, 10 GiB를 그대로 두고 고친 바이너리로만 다시 돌린다. 기존 결과는 지우지 않는다. 재퍼징 단위가 environment_pressure나 실행기 중단으로 끝나면 같은 설정으로 한 번만 다시 돌린다. 대표 run은 압박 없는 마지막 run, 없으면 마지막 run에 압박 표시를 붙여 쓴다.
4. B의 본 S 결과는 다시 퍼징한 run(단위당 1회 × 3,600초)이다. 기존 S run은 부록에 전부 보고한다(panic 수, 후보, 요청, 2절의 두 엔진 판정). 두 S run의 후보는 본 표에서 합치지 않는다. 합치는 것은 4절의 실제 취약점 후보 목록에서만, 어느 run에서 나왔는지 표시해 허용한다.
5. 고친 바이너리 SHA-256은 6절 1묶음 판정을 시작하기 전에 기록하고, 그 뒤에는 바꾸지 않는다. 1묶음 결과를 본 뒤에도 재퍼징과 2묶음 판정은 이 문서대로 그대로 한다.

4. B 기준 입력 수집(3절)과 4절 1항의 entrypoint 분류표. 10개 리비전의 기준 입력은 재퍼징 요청에도 그대로 쓴다.
5. 1묶음 = 첫 B 퍼징의 S 후보(지금의 107건)와 W 후보(지금 0건). 요청 index 생성 코드의 SHA-256을 기록하고 최종 요청 index를 만든 뒤 `validate-only`를 한다. 이어 2건 시범을 두 엔진으로 한다. 시범 요청은 최종 index에서 기준 입력이 있는 S 요청 중 제약 수가 가장 많은 것과 가장 적은 것이며, 요청 ID를 시범 전에 기록한다. 시범 통과 조건은 두 엔진이 두 요청을 도구 오류나 실행기 중단 없이 끝내고 출력이 형식 검사를 통과하는 것이다. 시범은 형식 검사 통과 여부와 exit code만 출력하고 판정 값(L1·배제·unknown)은 보지 않는다. 실패하면 멈추고, 판정 논리가 아닌 실행기 결함만 고쳐 기록한 뒤 시범을 다시 한다. 시범 2건은 6항의 전체 판정에서 새 인스턴스 저장소로 다시 판정한다.
6. 1묶음 전체 판정: v2.2, 이어서 v1.
7. B S 재퍼징 30단위(5절 2항에 따라 W 단위가 더해질 수 있음).
8. 2묶음 = 재퍼징 후보. 1묶음과 같은 index 생성 코드로 만들고 1묶음과 겹치는 요청도 빼지 않는다. `validate-only`, v2.2, 이어서 v1. validate-only가 실패하면 5항처럼 실행기 결함만 고치고, 그 수정이 1묶음 판정에 영향이 없는지 기록한다.

무거운 단계는 겹치지 않게 차례로 돌리고, 단계마다 상태 파일을 따로 둔다. 2026-10-29까지 끝나지 않은 묶음·엔진은 끝난 요청 수와 함께 "미완료"로 보고한다. 그 시점에 끝난 엔진의 묶음 결과는 열 수 있고, (가)(나)(다) 비교는 두 엔진이 모두 끝낸 요청만으로 센다.

## 7. 고정과 바꾸지 않는 것

## 8. 탐색층: 구성 기준 입력

1. 이유: 3절 규칙으로 B 1묶음 107건 모두 기준 입력을 얻지 못했다(리비전별 사유는 준비 보고서). 이 엄격층 결과는 그대로 본 결과로 보고한다.
2. 이 층에서는 리비전의 기록된 커밋 소스와 문서, 같은 저장소의 라이브러리·시험 자료, 공개 라이브러리로 정직한 입력을 만드는 생성 스크립트를 쓴다. 키나 서명이 필요하면 고정 seed로 새로 만든 시험용 키만 쓴다. 비밀 값은 쓰지 않는다. 회로가 특정 공개키를 고정해 두어 시험용 키로 만들 수 없으면, 같은 저장소에 커밋된 시험 자료만 쓰고, 그것도 없으면 그 리비전은 이 층에서도 판정 불가다.
3. 생성 스크립트와 그 실행은 B 후보 값, B 요청 index의 행, 퍼징 ledger의 후보 필드, J 출력을 읽지 않는다. 입력은 리드 검토를 거쳐 확정하고 SHA-256을 기록한다. 확정한 입력은 판정 결과를 연 뒤에 새로 만들거나 바꾸지 않는다.
4. 통과 조건은 3절과 같다: 맥에서 정직 witness 생성, Rust·snarkjs의 원본 R1CS 만족, 검사에 쓴 R1CS의 SHA-256이 그 리비전 B 퍼징 단위의 R1CS와 같음. 통과하지 못한 리비전은 이 층에서도 판정 불가다.
5. 판정 엔진, 실행기, 판정 규칙은 엄격층과 같다(v2.2, 이어서 v1). 이 층의 결과는 "구성 기준 입력" 표로만 따로 보고하고 엄격층 숫자와 합치지 않는다. 실제 취약점 후보 목록에는 넣되 항목마다 이 층에서 나왔음을 적는다.
6. 엄격층 기준 입력이 없는 리비전(아직 B 요청이 없는 것 포함)은 모두 이 층 1묶음 판정 결과를 열기 전에 같은 방법으로 입력을 만들어 확정하고 SHA-256을 기록한다. 2묶음에는 이 입력만 쓴다. 이 층 1묶음 판정 결과를 연 뒤에는 이 층의 입력을 새로 만들거나 바꾸지 않는다.
7. 리비전마다 작업 시간 3시간 상한을 둔다. 넘기면 그 리비전은 이 층에서도 판정 불가로 둔다.
8. 3절 4항의 "테스트·도구·입력을 고치지 않고 … 사람이 입력을 만들지 않는다"는 이 층에서 2·3항으로 대신하고, 나머지 3절 규칙은 그대로다. 4절 분류는 구성 입력을 기준 입력으로 보고 하며, 이 층의 사설 도달은 "구성 입력 공개 값 기준"으로 적는다. 이 층의 L1, (다) 항목, v2.2에서만 나온 배제도 4절 3항 검토에 넣고, 실제 배포 공개 값에서도 성립하는지 따로 적는다. 이 층의 배제는 "구성 입력 기준 배제"로 표시한다. 2절 5항(두 엔진이 끝나기 전에는 결과를 열지 않음)은 이 층 1묶음에 따로 적용한다.
