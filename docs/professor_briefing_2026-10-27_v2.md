# 교수 논의용 기여 설명과 다음 실험

2026-10-27 KST, v2. 기존 보고와 판정을 보존하고 사용자 초안의 수치 단위와 기여 표현을 교정했다. 새 실험 결과나 연구 범위 변경 승인을 기록하는 문서는 아니다.

## 쉬운 설명

> 조각에서 오류가 나왔다고 전체 프로그램에서도 그 오류가 생기는 것은 아닙니다. 우리는 조각에서 찾은 오류가 원래 회로에서도 가능한지 확인하는 J를 만들었습니다. 특히 처음 찾은 입력은 원래 회로에서 쓸 수 없더라도, 다른 입력으로 같은 오류가 생길 수 있는지를 따로 확인합니다. 판단할 수 있는 경우에는 실제로 오류가 생기는 예나 불가능한 이유를 제시하고, 풀지 못한 경우는 미판정으로 남깁니다.

## 교수님께 설명할 본문

교수님, 현재 연구의 주 기여로 제시하려는 것은 **분할 검사에서 나온 결과를 원래 회로의 입력과 제약에 맞춰 다시 판단하는 방법**입니다. 조각에서 찾은 특정 입력이 가능한지와, 다른 입력으로도 같은 의미 오류가 생길 수 있는지를 구분합니다. 이를 위해 입력을 역산하고 내부 값을 수리한 뒤 원본 전체 제약으로 확인하는 시스템을 구현했습니다.

그 구분이 필요한 실제 사례도 확보했습니다. Clamp에서는 처음 찾은 후보가 원본의 `min=0` 조건과 충돌했지만, 다른 값으로 첫 번째 비교기(`LessThan[0]`)의 오류가 가능했습니다. 상위 IntDiv를 수정하면 해당 비교기 오류도 불가능해졌습니다. 반면 zk-email의 `rsa-test`에서는 호출자의 입력 범위 검사가 비교 오류를 막았고, 고유 비교기 인스턴스 13개에서 해당 위반을 배제했습니다. Subtract에서는 원본 제약 196,096개를 만족하면서 같은 공개 입력의 최상위 출력이 달라지는 예를 확인했습니다. 알려진 개발 사례이며 새 취약점 발견으로 세지는 않습니다.

대형 회로의 후보 생성에서도 효과를 관측했습니다. 현재 캠페인의 전체 제약 10만 이상인 공식 main 21개 리비전에서, 세 seed를 합치면 전체 회로 zkFuzz는 0개, 분할 실행은 20개 리비전에서 후보가 나왔습니다. 이것은 분석 후보를 얻었다는 성과이며 실제 버그 20개를 확인했다는 뜻은 아닙니다.

아직 탐지 우위를 입증하지는 못했습니다. 고정 매핑 18항목의 엄격한 확인 결과는 전체 zkFuzz와 분할+J가 같은 항목 1개씩입니다. 일부 회로에서는 해시 내부에 탐색이 집중되고 필요한 템플릿의 준비나 순서가 막히는 문제를 확인했습니다. 검사와 태그 래퍼를 개선하고 순서 정책을 준비했지만, 이것이 유효 발견 증가로 이어지는지는 재실험이 필요합니다. J의 미판정과 추가 비용도 남아 있습니다.

선행에는 분해·반례 전파·전체 회로 검증이 이미 있습니다. 따라서 “기존에는 J 같은 것이 없다”거나 “퍼징을 쓰므로 별개 기여다”라고 주장하지 않겠습니다. **원본에서 계산되는 내부 입력을 다루고, 후보 하나의 가능성과 의미 오류 자체의 가능성을 나누는 구체적인 방법이 무엇을 더 해결하는지**를 비교하려고 합니다.

다음에는 현재 실행 연결과 재현 검증을 마친 뒤 고친 분할 방식을 평가하겠습니다. 추가로 확인된 항목이 있으면 준비·분할·J에 쓴 총시간을 전체 zkFuzz에도 주어 차이가 남는지 확인하는 기준을 미리 정해 두었습니다. 별도로 같은 후보·회로·오류 조건에서 J의 기능을 비교해 어떤 처리가 도움이 되는지 확인하려고 합니다.

후속 개발 후보는 **판정이 막혔을 때 꼭 필요한 주변 값과 제약만 더 살펴보는 방법**입니다. 현재 작은 범위의 풀이와 수리는 구현돼 있으므로, 새로 개발할 부분은 어떤 고정값을 풀고 어떤 원본 관계를 추가할지 선택하는 규칙입니다. 이 방법이 미판정이나 비용을 실제로 줄이는지 작은 개발 비교부터 확인하겠습니다.

이 기여 방향을 중심으로 연구를 계속하는 것이 타당한지, 목표 학회·학술지 수준에 맞추려면 어떤 비교나 보장이 가장 필요한지 의견을 여쭙고 싶습니다.

## 선행연구를 설명할 범위

- [Towards Fuzzing](https://arxiv.org/html/2504.14881v2)은 부분 변이 뒤 witness 수리와 전체 검증을 제안한다. 이 경로의 효율적인 구현은 열린 문제로 제시하지만, 논문 전체를 “한 문단 제안뿐”으로 설명하지 않는다. 별도의 zk-regex 퍼징 구현과 사례 평가도 있다.
- [ScaleCirc 공식 초록](https://conf.researchr.org/details/ase-2025/ase-2025-papers/173/ScaleCirc-Scaling-the-Analysis-over-Circom-Circuits)은 691회로 평가와 Circomlib의 미보고 underconstraint 결함 3건을 보고한다. 본문 전문은 미확보이며, 이 수치를 우리의 다른 데이터셋·평가와 바로 비교해 우열을 정하지 않는다.
- [공개 구현](https://github.com/jinan789/ScaleCirc/blob/3d05d0f3e82816135419dba37dde91d48cb65068/ScaleCirc/utils_One_Template_Analysis.py#L1820-L2182)의 반례 전파는 직접 입력 연결 등의 제한이 있지만 원래 분석기로 돌아가는 경로도 있다. “호출자의 범위 제약을 못 가린다”는 주장은 근거가 없다.
- 차이 후보는 계산된 입력의 합성·수리와 후보 값/의미 위반의 분리다. 같은 속성에서 기존 방식의 최종 결과와 총비용까지 비교해야 효과를 주장할 수 있다. [상세 대조](scalecirc_overlap_review_2026-10-27_v1.md)
