## 적용하지 않은 제안

- O0는 이미 요청당 한 번 파싱한다. 초기의 추가 파싱 캐시는 이 자료에 재사용 이득 없이 해시 비용을 늘리므로 최종 구현에서 제거했다. 반복 비용의 실제 대상은 SYM 비교와 전체 제약 검사다.
- `hint injection/not_reached`를 값싸게 예측할 일반 조건을 찾지 못했다. 초기 override가 비어도 후속 진단이 다른 hint·최상위 입력을 고쳐 도달할 수 있다. 잔여 반복 0 조건은 기존 루프가 이미 거르며, 초기 오류 순서까지 바꿀 이득이 작아 별도 생략 경로를 넣지 않았다.
- 전략 병렬화는 선행 모델→주입의 데이터 의존, small proposal/sweep의 공유 벽시계 예산, injection/repair의 공유 반복 한도 때문에 보류했다. 다른 전략이 먼저 끝나 판정 근거를 바꾸는 경로는 추가하지 않았다.
- WASM-only 재컴파일은 보류했다. 처음 보는 수정에서 새 R1CS·SYM을 생성하지 않으면 현재의 원본 동등성 검사를 잃는다. 진단용 제약 삭제는 실제 R1CS도 바꾼다. 검증된 동일 수정은 기존 전체 컴파일 캐시를 계속 사용한다. 선행 캐시·디스크 작업의 완료 보고서나 구현은 발견하지 못했다.

## 비교 조건

기준은 `runs/s-round4-2026-10-27/round4b/bin/zkfDO-v2.3-development`, SHA-256 `05649971dc0fb9ece435324d3c779e2c6f148f4dc6efd74ff9fecf5a9690e700`이다. 보존된 최종 빌드 로그와 `cargo-target/debug/zkfdo-j-v23`의 같은 해시로 **dev / unoptimized + debuginfo**를 확인했다. 새 버전도 같은 dev 프로필로 비교한다. 준비 중 만든 release 빌드는 본 표에 사용하지 않는다. 근거는 `runs/j-speed-2026-11-03/baseline-build-profile.json`이다.

새 v2.4는 rustc 1.94.1로 빌드했다. 기존 target의 `.rustc_info.json`도 같은 버전을 나타내지만, frozen v2.3의 당시 rustc 버전은 보존 빌드 로그에서 확인되지 않는다. 이 캐시는 개별 바이너리의 당시 빌드와 결속된 기록이 아니므로 보조 근거로만 사용한다. 컴파일러·빌드 환경의 영향을 완전히 분리했다고 주장하지 않는다.

각 요청에서 v2.3 → v2.4 jobs 1 → v2.4 jobs 4 순서로 하나씩 실행한다. 원래 요청을 그대로 읽고 새 출력·compile cache·instance-store를 각 요청·arm에 분리한다. seed/arm 간 응용 캐시 공유는 없다. OS 파일 캐시는 비우지 않으며 고정 순서·반복 1회라는 한계를 유지한다. 모든 생성 후보·컴파일 산출물·원시 결과는 ignored `runs/j-speed-2026-11-03/` 아래에 둔다.

동시에 다른 무거운 계산 작업이 없는지는 확인했으나 OS 서비스·일반 GUI 앱을 모두 종료한 전용 측정 환경은 아니다. 따라서 작은 arm 간 시간 차이의 원인을 병렬화 하나로 단정하지 않는다. 아래의 잠자기 대응 재측정은 사전에 원인을 기록한 예외이며 빠른 측정값을 고르는 반복이 아니다.

비용은 외부 실행기의 J 프로세스 경과시간과 `wait4`의 user+system CPU로 기록한다. 실행기는 `time.monotonic()` wall과 시작·종료 UTC 시각을 모두 저장한다. **저장된 UTC 시작·종료 시각의 차이와 monotonic 경과가 잠자기 때 달랐으므로 두 값을 구분한다.** UTC는 시계 보정의 영향을 받을 수 있고 두 timer의 기록 경계도 미세하게 다르다. J가 회수한 자식 compiler/solver/node/snarkjs CPU도 포함하며 timing wrapper 자체 CPU는 별도다. 내부 `j-speed.json`의 두 timer에는 `result.json` 저장과 lift 내부 정리가 포함된다. CPU는 이후의 profile 집계 전, wall은 집계 후에 읽으며 최종 sidecar 저장과 프로세스 종료는 제외하므로, 총비용은 외부 실행기 값으로 비교한다. 각 실행 전 내장 여유 25 GiB를 검사한다. 다른 J·퍼저·빌드 작업과 겹쳐 실행하지 않는다.

외부 실행기는 0.1초 간격으로 `wait4(WNOHANG)`을 확인하므로 경과시간에 폴링 주기와 OS 스케줄링에 따른 종료 확인 지연이 더해진다. 0.1초는 엄밀한 지연 상한이 아니다. 약 0.5초인 준비 실패 요청의 작은 시간 차이는 최적화 효과로 해석하지 않는다. CPU는 OS가 반환한 값을 쓰며 이 대기 시간과 별도다.

## 차등 판정 기준

준비 상태·사유, component 분류·속성, 원본 R1CS/SYM 해시와 hinted 동등성, 사이트 수, 클래스 pattern/대표/개수/판정/사유, Rust 실패 수·snarkjs 결과, 공개 입력 동일성·출력 차이, 술어별 판정·O0/O1 일치·도달 입력 분류를 비교한다. 차이가 있으면 `STOP.json`을 남기고 다음 arm/요청을 시작하지 않는다. 입력과 의존 파일 해시는 실행 전후에도 확인한다.
