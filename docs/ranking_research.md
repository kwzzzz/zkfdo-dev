**LEOPARD에서 정확히 가져올 것**

원논문의 §§II-B/C는 네 가지 구조 복잡도 지표의 합이 같은 함수를 같은 그룹에 넣는다. 각 그룹 안에서는 의존성·포인터·제어구조 관련 11개 지표를 합산해 정렬한다. 각 그룹의 상위 후보를 단계적으로 선택해 복잡도가 낮은 함수도 기회를 얻도록 한다. 원래 방법에는 위험 점수를 비용으로 나누는 공식이 없다. [LEOPARD 원문](https://xiaoningdu.github.io/assets/pdf/leopard.pdf)

우리 제안에서는 함수 대신 **템플릿 정의 + 구체적 인자 + 의존 소스 + 필드/컴파일 설정**으로 식별되는 실행 가능한 타깃을 평가한다. C/C++ 지표를 기계적으로 번역하지 않고 Circom의 의미를 반영한 지표로 교체한다. 이 교체, 그룹 정의, 비용의 사용 방식은 우리 연구 가설이며 원논문에서 검증된 사항이 아니다. 같은 가중치를 쓰더라도 가정이므로 문서화와 비교 실험이 필요하다.

독립적인 ASIA CCS 2024 연구 *SoK: Where to Fuzz?*는 1,600건 이상의 OSS-Fuzz crash를 이용한 위치 검색 평가에서 Leopard-C와 Leopard-V 지표가 비교 대상보다 좋은 성능을 보였다고 보고한다. 그러나 두 지표를 별도로 평가했고, 전체 그룹화 알고리즘의 우월성이나 Circom에서의 버그 발견 속도를 증명하지 않았다. stack trace에 포함된 함수와 실제 결함 원인 위치 사이의 차이도 한계다. 따라서 근거는 ‘단순 지표 기반 접근을 우선 평가할 가치’까지다. [SoK §§5–6](https://mlsec.org/docs/2024c-asiaccs.pdf)

**먼저 만들 랭킹 실험의 구체적 형태**

1. 컴파일 가능한 구체적 타깃을 확정한다. 미지원 문법·분석 실패·컴파일 실패는 별도 상태로 기록한다. 실패를 위험 점수 0으로 바꾸지 않는다.
2. 타깃별 의미 기반 지표 벡터를 추출한다. 규칙 ID, 소스 위치, 신호·제약 관계, 분석 성공 여부를 보존한다. 각 타깃의 도달 가능한 의존 코드 안에서 동일 경고를 중복 집계하지 않는다. 여러 타깃이 같은 라이브러리를 사용한다면 각각의 위험도에는 반영될 수 있으며, 최종 발견 결함의 중복 제거는 별도로 수행한다.
3. 첫 번째 후보는 지표 기반 위험 점수만으로 전체 타깃을 정렬한다. 동일 가중치 등 결합 규칙은 개발 세트에서 명시하고 평가 전에 고정한다. 일부 분석 규칙의 실패·미지원 결과도 0으로 취급하지 않고 unknown으로 남기며 분석 범위와 완료도를 함께 기록한다.
4. 두 번째 후보는 동일한 위험 지표를 사용하되 LEOPARD처럼 구조 복잡도별 그룹 안에서 순위를 매기고 각 그룹에서 단계적으로 선택한다. 이 둘을 비교해야 그룹화의 기여를 알 수 있다.
5. 먼저 모든 전략의 타깃별 실행 제한을 같게 두고 ‘순서의 효과’를 평가한다. 그다음 별도 실험에서 비용 반영·동적 배분을 추가한다. 전처리부터 시작하는 전체 실험과 준비된 캐시를 입력으로 받는 랭킹 분리 실험을 구분한다. 전체 실험에서는 전처리·컴파일·재시작을 포함하며, 캐시 재사용 비용을 중복 집계하지 않는다.

그룹을 컴파일 후 R1CS 제약 수가 정확히 같은 타깃끼리 정의하면 대부분 한 개짜리 그룹이 될 수 있다. 원논문의 구조 복잡도와 R1CS 규모는 같은 개념이 아니다. 그룹 경계나 비용 분모를 바꾼다면 변경된 알고리즘으로 이름 붙이고 비교해야 한다. 그룹 간 동점 선택도 고정 규칙 또는 기록된 난수 시드로 재현 가능하게 만든다.

**Circom 지표에서 바꿔야 할 점**

| 현재 문자열 지표 | 조사에 근거한 개선 후보 | 해석 |
|---|---|---|
| `<--` 등장 횟수 | 대입 신호와 연결된 제약, 불필요한 단일 화살표 대입 등 | 다른 위치에서 올바르게 제약했을 수 있으므로 존재 자체가 결함은 아님 |
| `assert` 전체 횟수 | 컴파일 시점의 인자 검사와 witness 시점의 신호 검사를 구분 | 서로 역할이 다르므로 같은 위험 점수를 줄 근거가 없음 |
| `LessThan` 등장 횟수 | 해당 인자의 범위 제한을 확인할 수 있는지 | 패턴의 존재보다 사용 조건을 분석 |
| `Num2Bits`, `IsZero` 등장 횟수 | 구체적 인자·범위·0 검사와 다른 제약의 관계 | 보호 검사를 추가한 코드도 단순 횟수 점수에서는 더 위험해질 수 있음 |
| signal/constraint 선언 횟수 | 구체적 인자로 컴파일한 규모와 실제 준비·실행 시간 | 위험도와 실행 비용의 측정값을 구분 |

공식 문서는 알려진 값에 대한 assert는 컴파일 때 평가되고, 그 외에는 witness 생성 코드에 검사를 넣는다고 설명한다. [Circom Code Assertion](https://docs.circom.io/circom-language/code-quality/code-assertion/)

Circomspect는 제약이 약한 중간 신호, 미사용 컴포넌트 출력, 범위를 확인할 수 없는 비교, 0이 아닌 제수를 보장하지 않는 나눗셈 등을 경고한다. 이를 분석 근거로 수집할 수 있지만 경고는 결함 확정이 아니다. 각 규칙의 제약과 예외를 유지해야 한다. [Circomspect 분석 규칙](https://github.com/trailofbits/circomspect/blob/main/doc/analysis_passes.md)

SASTFuzz는 경고가 표시된 코드의 비율과 여러 분석기의 합의를 각각 평가했고, 해당 실험에서 경고 밀도가 유용하지 않아 합의 방식을 선택했다. 이 결과를 Circom의 모든 경고 점수에 일반화할 수는 없지만, ‘경고가 많을수록 좋다’는 가정을 비교 없이 채택하지 말아야 할 이유가 된다. [SASTFuzz §4.2.1](https://mediatum.ub.tum.de/doc/1736881/1736881.pdf)

**시간 배분 알고리즘은 두 번째 단계**

Fuzzing at Scale의 Simple MAB는 프로그램별 coverage/time을 보고 높은 값의 프로그램을 주로 고르면서 일부는 무작위로 탐색한다. Discounted MAB는 오래된 성과의 비중을 낮춘다. Boian은 할인과 탐색 비율을 시간에 따라 바꾼다. 논문은 퍼저 프로세스를 정지·재개하여 상태를 유지한다. 이는 UCB를 그대로 구현한 알고리즘이 아니다. [원문 §3.2](https://arxiv.org/html/2406.18058v2)

이 연구의 주 비교 실험은 대규모 프로그램 집합을 근거로 반복 실행 없이 수행했다는 한계가 있다. 공개 구현과 실험 설정은 참고할 수 있지만, 보고된 coverage 개선율이나 작은 시간 조각을 Circom 성능·기본값으로 가져오지 않는다. [원문 §6](https://arxiv.org/html/2406.18058v2), [저자 구현](https://github.com/ivicanikolicsg/fuzzing_at_scale)

우리 적용의 후보는 ‘각 Circom 타깃 = 하나의 선택지’로 두고, 짧은 실행 구간에서 얻은 새 정보를 바탕으로 다음 배분을 갱신하는 방식이다. 그러나 어떤 새 정보가 실제 TCCT 결함 발견을 예측하는지부터 검증해야 한다. 원논문의 coverage reward를 버그 성공률이나 fitness 감소로 바꾸면 별도 알고리즘이며 성능 보장도 승계되지 않는다.

현재 [runner.rs](../src/runner.rs)는 상태·시간·마지막 세대 번호 등을 저장하며 coverage·fitness 이력과 상태 복원은 구현하지 않았다. timeout 때 프로세스를 종료하므로 여러 짧은 호출을 이어 붙이는 것은 같은 탐색 상태의 계속 실행이 아니다. 비용이 큰 준비 단계를 반복하면 오히려 예산을 낭비할 수 있다. 지금은 Boian·UCB·Thompson sampling 중 이름부터 정하기보다 실행 상태와 관측값을 확보하는 편이 타당하다.

추가로 로컬 zkFuzz 소스 `072bf1fbbd1c9ecad58d4f6d2204c3b96e7fec17`를 확인했다. `--show_stats_of_ast`는 파싱·타입 분석 후 템플릿별 구조 통계를 출력한다. `--print_stats_csv`는 symbolic trace와 side constraint의 연산자·변수 등 통계이며 coverage/fitness 시계열이 아니다. GA 진행 로그에는 세대별 best fitness가 있으므로 이를 파싱하는 어댑터를 검토할 수 있다. 내부 coverage 계산도 존재하므로 ‘zkFuzz에 coverage가 없다’고 할 수는 없다. 부족한 것은 외부 스케줄러가 사용할 안정적인 관측·제어 계약이다. [로컬 main](../.external/zkFuzz/src/main.rs), [GA 진행 출력](../.external/zkFuzz/src/mutator/mutation_test.rs), [내부 coverage](../.external/zkFuzz/src/mutator/mutation_test_update_input_fn.rs)

통계만 얻는 사전 실행은 퍼징 결과와 별도로 표시한다. 탐색을 끈 실행의 무발견 메시지는 결함 탐색 결과가 아니다. AST 출력에는 포함된 다른 템플릿도 있으므로 타깃 소속을 확인하고, 필드 이름·값의 의미·구체적 인자 반영 여부를 검증한 후 특징으로 사용한다.

세대 번호나 로그 크기는 탐색 진척의 참고값일 뿐 발견한 새 행동 수나 버그 확률이 아니다. 결함 발견은 희소하므로 초기 무발견을 안전 판정으로 쓰지 않는다. coverage가 있더라도 타깃별 규모와 공유 코드가 달라 합산 방식이 목적과 맞는지 확인해야 한다.

UCB1은 보상이 유계이고 조건부 평균이 일정한 모델에서 분석되므로, 시간이 지나며 새 발견이 줄어드는 퍼징에 원래 보장을 그대로 주장할 수 없다. Successive Halving은 예산 안에서 최선의 선택지를 식별하려는 방법이라 여러 타깃의 누적 결함 발견량을 높이는 목적과 구분해야 한다. 느리게 성과가 나는 회로를 조기 탈락시키는 정책은 별도 비교가 필요하다. [UCB1 §2](https://link.springer.com/content/pdf/10.1023/A:1013689704352.pdf), [Successive Halving](https://proceedings.mlr.press/v51/jamieson16.pdf)

**현재 저장소에서 확인한 준비 상태**

- `ranker.rs`: 고정 토큰 가중치 / 로그 기반 비용으로 파일 순위를 출력한다.
- `cli.rs`: rank 결과와 schedule은 분리되어 있다. schedule은 경로순 파일 목록을 사용한다.
- `targets.rs`: 구체적 인자와 래퍼를 만들지만 지원 문법이 제한된다. 래퍼의 include/main 몇 줄만 분석하면 타깃의 의미를 측정할 수 없다.
- `runner.rs`: 구조화된 결과 저장은 있지만 동적 선택에 필요한 진척 이력·resume 제어는 없다.
- 조사 당시 두 manifest는 비어 있었다. 이후 `manifest.dev10.json`에 서로 다른 direct-mode 타깃 3개를 추가했고, `manifest.dev30.json`은 여전히 비어 있다. dev10이라는 이름이 10개나 독립 평가 세트를 뜻하지 않는다.

격리한 템플릿은 원래 호출자가 제공하던 입력 전제조건을 잃을 수 있다. 따라서 래퍼에서 발견한 반례와 실제 프로젝트의 허용 입력에서 도달 가능한 결함을 구분하는 검증 절차를 제안한다. 타깃 신원은 중복 실행을 줄이는 용도이고, 결함의 근본 원인 신원은 평가에서 중복 집계하지 않는 용도다.

데이터의 출발점으로는 zkbugs의 Circom 항목을 검토할 수 있다. 공식 저장소에는 코드 commit, 원래/격리 entrypoint, 취약 위치, 감사 출처와 재현 상태가 기록되며 direct/original 모드를 구분한다. 목록에 있다는 사실만으로 재현 성공이나 zkFuzz 검출 가능성을 가정하지 않는다. 각 결함이 TCCT oracle의 검출 대상인지도 구분한다. [zkbugs](https://github.com/zksecurity/zkbugs)

**선택을 결정할 평가**

| 비교 | 확인할 질문 |
|---|---|
| random, small-first, 기존 가중치, warning-first | 새 설계가 단순한 기준보다 나은가? |
| 의미 기반 위험도만 vs 동일 지표 + 복잡도 그룹 | LEOPARD식 그룹화가 실제로 도움이 되는가? |
| 같은 순위에서 비용 미반영 vs 비용 반영 | 준비·실행 비용 때문에 생기는 차이는 얼마인가? |
| 같은 초기 순위에서 균등 배분 vs 적응 배분 | 실행 피드백을 쓰는 효과가 있는가? |

랭킹 자체는 알려진 원인 위치/타깃의 Recall@K·순위 지표로 본다. 최종 성과는 전체 시간에 따른 확인된 고유 결함 수, 첫 결함까지 시간, 준비·실패에 쓴 시간으로 본다. 무발견 실행은 시간 제한에 걸린 관측으로 남기고 임의의 발견 시간을 넣지 않는다. 라벨이 없는 회로를 모두 안전한 음성 표본으로 처리하지 않는다.

프로젝트·템플릿 계열·동일 결함의 변형을 개발/평가 세트 사이에 섞지 않는다. 전략마다 같은 타깃, 버전, 하드웨어, 전체 예산과 반복 실험 조건을 적용하고 난수 영향을 보고한다. 먼저 순서 효과를 분리해 본 뒤 실제 가변 배분에서는 ‘동일 타깃별 timeout’을 강제하지 않고 동일 전체 예산으로 비교한다. 이는 기존 [평가 계획](evaluation_plan.md)을 구체화한 제안이다.

**연구 공백의 확인 범위**

zkFuzz §IV-B는 제약 오차 fitness를 이용한 변이 후보 선택을 이미 사용한다. zkCraft §3.3도 R1CS 행을 점수화하여 변이 후보를 고른다. 둘은 회로 내부의 탐색이므로 ‘Circom에는 랭킹이 없다’는 주장은 부정확하다. [zkFuzz v3](https://arxiv.org/html/2504.11961v3), [zkCraft v6](https://arxiv.org/html/2602.00667v6)

이번에 확인한 두 ZK 논문과 관련 검색에서는 여러 구체적 Circom 타깃 사이의 정적 위험 순위와 전체 시간 배분을 결합한 직접 대응 방법을 찾지 못했다. 이는 모든 선행연구에 없다는 증명이 아니다. 검색어에는 Circom/zero-knowledge fuzzing + target selection/ranking/scheduling/budget allocation, conventional fuzzing + vulnerability metrics/multi-program scheduling을 포함했다. 논문의 방법과 공식 구현을 우선 확인했고 최신 크롤링 날짜를 발표 연도로 사용하지 않았다.

인접 구현인 zkHydra는 이미 여러 ZK 보안 도구를 실행하고 timeout·worker·direct/original 모드를 관리한다. 따라서 도구를 실행하고 결과를 모으는 기능만으로 새 기여를 주장하기 어렵다. 우리는 랭킹·배분 정책과 그 측정된 효과로 차이를 입증해야 한다. [zkHydra](https://github.com/zksecurity/zkhydra)

추가 경계 사례로 Arguzz(USENIX Security 2026)는 zkVM 내부 명령에 fault를 고르게 주입하기 위한 선택 방식을 다루며, Circuzz(CCS 2025)는 회로 처리 도구의 pipeline을 시험한다. 연구 대상의 층위가 다른 사례이므로 광범위한 ‘ZK scheduling 최초’ 주장에 포함해 검토해야 한다. [Arguzz](https://mariachris.github.io/Pubs/SECURITY-2026.pdf), [Circuzz](https://mariachris.github.io/Pubs/CCS-2025.pdf)

**웹 ChatGPT와 Codex의 역할**

OpenAI는 ChatGPT의 연구 활용으로 논문·노트의 출처, 상충하는 주장, 방법의 한계를 종합하는 작업을 설명한다. [공식 연구 종합 안내](https://learn.chatgpt.com/use-cases/synthesize-research-evidence)

이 작업에서는 웹 ChatGPT를 독립 문헌 검토에 활용하고, 저장소와 실제 실행 계약의 확인은 현재 작업 환경에서 이어가는 조합을 추천한다. 특정 제품이 더 정확하다는 성능 비교를 확인한 것은 아니다. 검토를 넘긴다면 아래 요청을 사용할 수 있다.

> 외부 zkFuzz를 유지하면서 여러 실행 가능한 Circom 템플릿 인스턴스를 고정된 전체 시간 예산 안에서 우선순위화하려 한다. LEOPARD의 정적 타깃 선정과 Fuzzing at Scale의 동적 배분이 적합한지 1차 자료로 반박·검증해 달라. seed/변이 위치 선택과 회로 간 선택을 구분하고, 더 직접적인 선행연구와 zkHydra 같은 인접 구현도 찾아 달라. 현재 runner 관측값은 실행 상태·시간·마지막 generation이며 coverage/fitness 이력과 resume는 없다. zkFuzz 자체에는 AST/제약 통계 옵션·세대별 best fitness 로그·내부 coverage 계산이 있으나 외부 스케줄러용 어댑터는 아직 없다. Circom에서 이미 효과가 증명됐거나 관련 논문이 전혀 없다고 가정하지 말고, 원논문의 방법·필요 데이터·우리의 변경점·검증 실험을 분리해 제시해 달라.
