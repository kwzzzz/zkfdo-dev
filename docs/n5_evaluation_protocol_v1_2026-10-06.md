# N5 평가 프로토콜 v1 (2026-10-06 고정)

상태: **고정(2026-10-06, miiz 최종 확인).** 최종 확인 때 B의 총예산을 600초에서 3,600초로 바꿨다(§5, §13). 이 변경은 이 문서에 따른 어떤 실행보다 앞선다. [초안 v0](n5_evaluation_protocol_draft_2026-10-06.md)을 바탕으로 miiz 결정(§13)을 반영했다. 초안은 수정하지 않고 보존한다. 고정은 [N3 결정 §5](scope_decision_final_2026-10-01.md#5-n5-고정-방식과-평가층)대로 이 문서, 대상 목록 JSON과 해시, 도구 해시, miiz 결정 기록으로 남긴다. 고정 후 결과를 보고 규칙·전제·방법을 바꾸지 않는다. 바꾸면 새 버전으로 기록하고, 바뀐 뒤의 실행은 탐색층으로 따로 보고한다.

## 1. 연구 질문과 주장 범위

- **RQ1(주):** 같은 entrypoint와 같은 총예산에서 S+J와 W를 같은 확인 수준으로 비교한다. 지표는 K5a(분할만 확인 r, 통째만 확인 l), K5b(최초 확인 시각, 미관측은 검열), K5c(고유 원인 수), K5d(준비·실행·판정·검토 총비용)다.
- **RQ-C(맥락 판정 신뢰성):** 수정 커밋 쌍에서 결함 인스턴스가 수정 전에 도달하고 수정 후에는 도달하지 않는가(배제 또는 미판정). 수정 후 도달은 엔진 오류 후보로 검토한다. 미판정률을 함께 보고한다.
- **RQ2(보조):** 분할 순서 전략의 최초 발견 시간. 우위를 논문 성립 조건으로 삼지 않는다.
- **주장하지 않는 것:** 일반적 우위, 새 결함 발견의 필수성, 분해 발상 자체의 최초성, 범위 전파 같은 선행 기술, 공개 입력 도달의 공격 가능성(위협 모델 조건부).
- 결과가 불리하면 주장 범위를 줄여 보고한다. 결과에 맞춰 규칙을 바꾸지 않는다.

## 2. 평가층과 노출 (결정 6)

알려진 결함 결과와 새 발견을 섞지 않고 층별로 따로 보고한다.

| 층 | 대상 | 노출 |
|---|---|---|
| **D 개발** | inference(subnet-2-circom) 전체, Banyan `hot-proofs-blake3-circom`, zk-email `zk-email-verify`, A-02·S-0x·L-01~L-07에 쓴 자료, `tests/fixtures/*` | 방법·규칙 조정에 사용. 결과는 개발 관측으로만 보고 |
| **Q 공개 지식 노출** | zkbugs의 나머지 Circom 항목 전부 | 결함과 위치가 공개돼 있다. 우리가 개발에 쓰지 않았어도 "미노출"이라고 주장하지 않는다 |
| **B 구조 준비 노출** | 갈래 B의 배포 main(C-03·E-01·E-02·F-01·M-01 대상) | 설치·컴파일·대상 탐색만 했고 퍼징·후보 검토·결함 지식은 없다. 이 층의 확인 결과를 "새 발견" 후보로 따로 보고하며, 준비 노출은 열로 기록한다 |

순수한 분리층(S, 어떤 노출도 없는 대상)은 이번 고정에서 비어 있다. B층은 준비 노출이 있으므로 S로 부르지 않는다.

## 3. 대상 목록과 포함·제외 규칙

### A 정답 대조 (결정 2)
- **분모:** zkbugs `dataset/circom`의 `zkbugs_config.json` 70건 전체를 추적한다. 그중 `Fix Commit`이 있는 50건이 대조 후보다. 수정 커밋이 없는 20건은 수정 전 실행만 하고 RQ-C에서 제외하며, 사유를 남긴다.
- **1단계 범위:** D층 개발 사례(inference PR #2의 결함들, Banyan, zk-email 맥락 오탐 대조)와, 수정 커밋 50건 중 **이미 설치·준비 기록이 있는 프로젝트의 항목 전부**다. 목록은 고정 시점의 E-01·C-03 기록으로 기계적으로 만든다.
- **2단계 범위:** 나머지 수정 커밋 항목 전부. 1단계 결과와 무관하게 50건 전체가 분모다.
- **리비전:** 결함 리비전은 `Commit`, 수정 리비전은 `Fix Commit`이다. 한 PR이 여러 결함을 고친 경우 L-06처럼 PR 안의 개별 커밋 또는 그 파일 변경만 적용한 패치 리비전(leave-one-out)을 추가하고, diff와 해시를 기록한다.
- **entrypoint와 준비:** zkbugs `Direct Entrypoint`·`Original` 입력을 쓴다. 준비는 E-01 설치 정책과 F-01 탐색기로 하고, 프로젝트별 수동 수정은 금지한다.
- **실패 처리:** 설치·컴파일·준비 실패, 미지원, 시간 초과는 분모에 남긴다. 준비에 성공한 사례만 사후에 고르지 않는다.

### B 표적 (결정 3)
- **분모:** E-02 역할 규칙(경로 기반, 고정)으로 `deployment_main`이고 원본 제약 10만 이상인 entrypoint 전체다(C-03 production + E-01/E-02, F-01·M-01 준비 기록).
- **포함 규칙:** 원본 컴파일 성공(120초, 또는 600초 측정에서 성공한 것은 `compile_600` 층으로 표시하고 컴파일 시간을 비용에 넣음) 그리고 준비 success 또는 partial(적격 조각 1개 이상).
- **1단계(10/15 전):** 포함 규칙에 맞는 것 중 **저장소마다 원본 제약 수가 작은 것부터 2개, 총 최대 10개**. 같은 수면 경로 사전순. 저장소가 5개보다 적으면 10개를 채우지 않고 그대로 둔다.
- **2단계:** 포함 규칙에 맞는 나머지 전부.
- **목록 생성 시점:** E-02 완료 직후, **zkFuzz 실행 전에** 위 규칙으로 기계적으로 만든다. 목록 JSON의 SHA-256을 이 문서의 부록으로 기록한 뒤 실행한다. 규칙은 지금 고정되고 목록만 나중에 생성되므로, 목록 생성 전에 B 대상의 퍼징 결과를 보는 일은 없다.

## 4. 실행 단위와 중복 제거

- 단위는 (프로젝트, 소스 리비전, entrypoint, 실행을 바꾸는 설정)이다. 라벨, 검토 술어, 반복만으로 새 단위 예산을 주지 않는다.
- 분할 조각은 F-01 탐색기의 컴파일 단위(인스턴스 키 기준 중복 제거)와 루트 단위다. 루트를 일괄 제외하지 않는다.
- 같은 entrypoint의 수정 전·후 리비전은 별도 단위이고 쌍으로 묶는다.

## 6. 확인 수준

| 수준 | 뜻 |
|---|---|
| L0 | zkFuzz 후보 신호(조각 또는 전체) |
| L1 | entrypoint 수준 확인: TCCT `entrypoint_violation`(원본 R1CS를 Rust·snarkjs 두 방법으로 만족하고 최상위 출력이 정직 계산과 다름), 또는 가정 술어 `assumption_violation_reachable`(인스턴스 단위, 두 검사기) |
| L2 | 원인 귀속: A는 zkbugs 결함 위치(템플릿·줄)에 대응하고 수정 리비전에서 도달하지 않음. B는 사람 검토로 원인을 정함 |

W와 S+J를 **같은 수준**에서 비교한다. 도달은 반드시 공개/사설 분류(`reach_inputs`)와 함께 보고한다. 배제는 증명(상수, 닫힌 원뿔 z3 unsat, 비트 분해·범위 전파)일 때만 쓴다.

## 7. 정답 대조 규칙 (A)

결함 b에 대해 다음을 정의한다.
- **수정 전 확인:** 결함 리비전에서 b의 위치 템플릿 인스턴스가 L1에 도달한다.
- **수정 후 대조:** 수정 리비전에서 같은 인스턴스가 도달하지 않는다. 도달하면 `fix_reach`로 표시하고 엔진 오류로 검토한다.
- **연쇄 판정:** 같은 수정에 다른 결함이 함께 있으면 그 결함만 되돌린 leave-one-out에서 다시 판정한다(L-06 Clamp 사례). 도달 근거가 다른 알려진 결함의 hint에 의존하면 `chained`로 분류한다.
- **보고:** 결함별 W/S+J 확인 여부, 최초 시각, 맥락 판정의 도달·배제·미판정, 공개/사설 분류.

## 8. 표적 처리와 사람 검토 (B, 결정 4)

- 정답이 없으므로 수준별 수와 비용을 비교한다.
- **사람 검토 범위: 전부.** W와 S+J에서 나온 L1 결과 중 사설만 도달과 TCCT 위반을, 중복 제거한 (entrypoint, 인스턴스) 단위로 **전부** 검토한다. 공개 입력 변경 도달도 목록으로 남기고, 위협 모델 판단과 함께 검토한다.
- 검토는 판정을 열기 전에 정한 양식(인스턴스, 깨진 조건, 입력 분류, 원인 후보, 프로젝트 의미, 결론)으로 기록하고, 건마다 검토 시간을 기록한다.
- 원인이 확인되면 책임 있는 공개 절차(별도 문서)를 따른다. 공개 전에는 결함 세부를 공유 문서에 쓰지 않는다.

## 9. 비용 기록

준비(탐색·준비, F-01·E-02 기록을 재사용하면 그 시간), 실행(W, S), 판정(J), 사람 검토 시간, 컴파일과 캐시 적중을 따로 기록한다. 벽시계, CPU 시간, 측정 중 기계 부하(load average)도 남긴다.

## 10. 집계와 불확실성

- **K5a:** 대상×seed 쌍에서 r(분할만 확인)과 l(통째만 확인)을 센다. 층별로 나눈다.
- **K5b:** 최초 L1 시각의 생존 분석(미관측은 T에서 검열).
- **K5c:** 같은 귀속·중복 제거 규칙 아래 고유 원인 수.
- **K5d:** 총비용의 중앙값과 합.
- **조각 커버리지:** S에서 시도한 조각 수 / 적격 조각 수를 대상마다 보고한다(600초 시점과 T 시점).
- **신뢰구간:** 대상(B) 또는 결함(A) 단위 부트스트랩. 표본이 작다는 것을 명시하고 일반화하지 않는다.
- 1단계 결과는 "1단계(최소본)"로 표시해 보고하고, 2단계를 포함한 전체 결과로 대체하지 않는다.

## 11. 고정 대상과 금지

- **고정 대상:** 이 문서, A·B 대상 목록 JSON(해시, B는 §3 시점 규칙에 따라 생성 후 부록에 기록), seed 목록, 도구 해시. 도구는 zkFuzz `ac2d9d16…`, circom 2.2.3 `8991887…`, 탐색 zkfDO `f8c9f64d…`, 판정 zkfDO `e5cb0184…`이다.
- 고정 후 결과를 보고 규칙·전제·방법을 바꾸지 않는다.
- B 대상의 zkFuzz 실행은 목록 해시를 부록에 기록한 뒤에만 한다.
- 실행은 E-02 완료 후 시작한다(측정 중 다른 무거운 작업 금지).
