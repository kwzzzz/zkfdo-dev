## 2. 코드에서 확인한 실행 구조

읽은 중심 파일은 `src/candidate_review/lifting/mod.rs`, `predicate.rs`, `instances.rs`이며, 종료점과 상한을 확인하기 위해 같은 디렉터리의 `synth.rs`, `repair.rs`와 `scripts/run_n6_j1.py`도 읽었다. 이하 `mod.rs` 등의 줄 번호는 문서 끝 SHA-256으로 고정한 현재 소스 기준이다.

### 2.1 술어 탐색은 이미 자기 판정 실패 뒤에도 실행된다

`mod.rs:939–959`는 `evaluate_class`의 결과를 받은 뒤 표적이 있으면 `predicate::judge`를 호출한다. `evaluate_class`가 `Synthesis::Unknown`으로 반환하는 `mod.rs:1939`도 이 호출을 막지 않는다. `predicate.rs:423–437`의 별도 탐색은 `base_input`, `candidate_hints=false`, `protected_site=None`, `inputs_free=true`, 빈 pinned/후보 targets에서 출발한다. `predicate_search_not_reached`는 `repair::search`가 **실행된 뒤** 도달 witness를 반환하지 못할 때 붙는다(`predicate.rs:438–450`).

따라서 55개를 “술어 탐색 미호출”로 해석해 호출 위치만 옮기는 안으로 해결을 예상할 수 없다. 독립 일정 배치는 중복 탐색·준비 의존성을 줄이는 후보이고, 55개의 직접 개선 대상은 술어 탐색 자체의 cycle/no_progress/error다. 단, 클래스 루프에 도달하기 전 후보 신호/컴포넌트 검사·hint 준비 실패는 요청 전체를 끝낼 수 있다(`mod.rs:545–569`, `597–603`, `800–867`). 이를 우회하려면 원본 entrypoint 준비와 후보별 준비를 분리해야 하며, 기존 55개와 다른 경로다.

## 4. 제안 구조와 확인 조건

### 4.1 원뿔·수리의 변경 경계

우선 채택 후보는 구조 기반 작은 원뿔 제안, 효과 없는 SAT의 다음 경로 선택, 실패 제약 보존이다. 입력·hint·후보 site 역할을 기준으로 선택하며 프로젝트명·템플릿명·특정 후보 SHA·W/S를 분기 조건으로 쓰지 않는다. `LessThan`은 기존 zkFuzz 가정 술어 정의에 필요한 식별만 유지한다. `DistanceFromScore.positive`는 A의 사후 회귀 확인 표적이며 탐색 우선순위나 특수 규칙이 아니다.

도달 검색용 지역 모델과 배제 증명용 모델을 별도로 표시한다. 지역 SAT 모델은 원본 전체에서 재현하기 전에는 unknown이다. 지역 UNSAT는 원본의 제약 부분집합과 모든 witness에 성립하는 사실만 사용했는지 확인해야 한다. 기준 입력값, 탐색용 blocking clause, 실패 모델의 임의 경계값을 고정한 UNSAT는 해당 탐색 경로의 실패일 뿐 전역 배제가 아니다. 후보 값 도달의 배제와 후보 독립 술어 전체의 배제도 합치지 않는다.

### 4.2 술어 작업의 분리와 저장소

현행 표적 생성(`mod.rs:926–938`)과 인스턴스 매핑을 먼저 보존한다. 후보에 깨진 조건이 있으면 그 인스턴스, 없으면 미리 수집한 컴포넌트 LessThan 목록을 쓴다. 이 목록은 **입력 가정 경로 또는 정직 컴포넌트 생성이 abort된 경우에만** 수집한다(`mod.rs:640–654`). 정직 생성에 성공한 일반 TCCT 후보는 이 기본 목록이 비어 있다. 원본 entrypoint 구조를 준비한 뒤 표적별로 같은 순서의 술어 검색을 예약할 수 있다. 이것은 이미 존재하는 후보 독립 검색을 공통 작업으로 분리하는 설계이며, 모든 TCCT 후보나 모든 entrypoint 인스턴스로 표적을 확대하는 안은 별도 프로토콜/탐색층 결정이 필요하다.

저장소는 두 종류로 분리한다.

- **검증된 증명:** 원본 O1/O0 R1CS·두 SYM·술어 정의·인스턴스·검증 설정과 증거 파일 해시에 묶는다. v2 schema와 새 디렉터리를 사용한다. v1/L-07 결과를 v2의 새 관측으로 가져오지 않는다. 도달은 두 검사기와 신호 대응 검증 정보를 모두 갖춘 경우만 공유한다.
- **탐색 시도:** 증명 키 외에 엔진/설정 SHA, 기준 입력 SHA, 시작 상태, 탐색 종류·순서·할당을 포함한다. 동일한 실패 탐색의 중복을 줄일 수 있으나 cached unknown은 계속 unknown이며 새로운 후보의 자체 witness 확인을 생략할 이유가 아니다. 다른 시작 상태나 예산에는 재사용하지 않는다.

현행 증명 키(`predicate.rs:576–584`)는 entry key·instance·술어 이름을 쓰며, entry key(`mod.rs:750–764`, `904–907`)는 O1 R1CS·O1 SYM·O0 R1CS hash다. 현재 `store_read`는 entry key와 instance만 확인한다(`predicate.rs:586–590`). v2 설계에서 schema·허용 verdict·증거 결합 검증을 명시한다.

`reach_inputs`의 공개/사설 변경 분류는 기준 입력에 상대적이다(`predicate.rs:501–528`). 현재 cache hit는 과거 분류를 복사한다(`379–382`). v2에서는 base-input hash를 결합하거나 원래 검증 증거를 현재 base와 비교하여 분류를 다시 계산해야 한다. 값은 계속 ignored `runs/`에 둔다. 상반된 증명은 기존 `instance_store_conflict`(`594–605`)와 집계 `conflict`(`instances.rs:138–170`)로 보존하고, 성공에 흡수하지 않는다.

### 4.3 L1 기준은 그대로 유지

| 경로 | 반드시 유지할 조건 |
|---|---|
| TCCT | 원본 R1CS Rust 불만족 0과 snarkjs `correct`(`mod.rs:2029–2070`), 공개 입력 동등성, 후보 주입 보유, 기존 출력 차이/정직 생성 abort 규칙(`2072–2137`). 다른 site 변경은 기록하고 원인 귀속으로 자동 승격하지 않음 |
| 입력 가정 후보의 입력 도달 | 원본 전체 witness 검사와 후보 site 입력 일치(`mod.rs:2194–2240`). 입력 도달만으로 가정 술어 위반을 주장하지 않음 |
| 가정 술어 도달 | Rust 0·snarkjs correct·O0/O1 모든 해당 wire 일치·술어 성립(`predicate.rs:467–470`, `706–758`). 자체 witness 재사용도 이미 검증된 O1과 O0 대응 확인(`648–695`) |
| hint 수리 | O0/O1 원본 R1CS 불변 및 O1 SYM 동등성(`repair.rs:864–905`), TCCT comparator에도 같은 조건(`908–943`). 진단본의 check 삭제는 위치 추적에만 쓰며 최종 witness는 원본으로 재검사 |

`instances.rs`는 결과 문자열을 모아 own/effective를 만드는 집계기이며 증명 검증기가 아니다(`83–123`, `138–170`). 집계 단계에 새 L1 인증 책임을 넘기지 않는다.

## 5. W/S 공정성과 결과 분리

W와 S 후보는 같은 v2 바이너리·도구·설정·표적 생성 규칙·solver/크기/반복 상한·시작 입력 정책·검색 순서·중단 규칙을 사용한다. S의 특정 함수만 개선하거나 W에 다른 예산을 적용하는 설계는 채택하지 않는다. A의 c9221e8d·loo-dfs만 특별 취급하는 설계도 제외한다.

현행 실행기는 리비전 단위로 cache/store를 공유한다(`run_n6_j1.py:514–531`, `601–606`). v2는 비어 있는 별도 cache/store에서 시작하고, 리비전별 정리·요청 순서·캐시 적중 비용을 함께 기록한다. 공유로 얻은 술어 판정은 `own/effective`, `shared_from`, 독립 검색 작업 ID와 최초 검증 완료 시각을 남긴다. 먼저 수행한 방식의 증거를 다른 방식의 자체 발견이나 더 이른 발견 시각으로 소급하지 않는다. 공통 비용은 별도 보고하고 사전에 고정한 규칙 없이 한 방식에만 부과하지 않는다.

동일 실패의 memoization이 먼저 실행한 방식에 따라 다른 검색 기회를 주지 않도록, 완전히 같은 시작/설정/허용량의 재사용만 인정한다. 후보 witness 확인은 W/S 모두 계속 수행한다. 요청 순서 독립적인 최종 instance 결합과 요청별 실행 시간의 순서 효과는 별도로 보고한다. 요청 없는 인스턴스, 기준 입력 실패, 표적 미대응은 배제로 바꾸지 않는다.

A v1은 사전 등록 본 결과로 유지한다. 향후 A v2는 개발 세트 결과이며, B는 v2와 필요한 N5 개정이 고정된 뒤 별도 지시로 처음 판정한다. 이 문서 작성은 B 평가 허가나 N5 변경이 아니다.

## 6. A 비용 추정과 별도 예산 확대안

### 6.1 고정 실측 기준과 기본안

기존 A의 765요청 wall 합은 **5,686.192초(1.580시간)**, 전체 state 경과는 **5,738.224초(1.594시간)**다. 두 값의 차이는 52.032초다. 최대 요청 163.907초, 컴파일 합 705.018초, 컴파일 cache hit 2,095회, instance-store hit 257회다. 이 값은 기존 보고서에서 인용했으며 재측정하지 않았다. 650 L1이 유지될지, unknown이 얼마나 줄지는 아직 미상이다.

기본안은 수치 상한을 일괄 확대하지 않고 기존 검색 안에서 무효 제안·중복 준비를 대체한다. 그러나 각 경로의 기존 시간과 새로운 cache 효과는 현재 자료만으로 식별되지 않는다. 따라서 예상 시간을 하나의 측정값처럼 쓰지 않고 다음 **용량 계획 민감도**로 제시한다. 0.8·1.0·1.2배는 관측된 성능 개선률이나 신뢰구간이 아니라 요청 작업이 20% 감소/불변/증가한다고 놓은 가정이다.

| 가정 | A 전체 시간 비교값: 5,686.192 × 배율 + 52.032 |
|---|---:|
| 요청 작업 0.8배 | 4,600.986초 = 1.278시간 |
| 요청 작업 불변 | 5,738.224초 = 1.594시간 |
| 요청 작업 1.2배 | 6,875.462초 = 1.910시간 |

실제 기본안이 이 구간 안에 든다는 보장은 없다. 새 abort 수리에서 컴파일이 늘거나 캐시를 덜 쓰면 밖으로 벗어날 수 있다. 향후 회귀에서는 요청 합·전체 wall·요청 최대·단계별 solver/재현/compile·cache hit·정리 비용을 기록하여 이 가정을 대체한다. 49·55를 고유 요청 수로 취급하거나 `765×20초`를 요청 전체 시간으로 쓰지 않는다.

### 6.2 예산 증액은 별도 결정

기본 구조 개선과 분리해 검토할 후보는 (i) sweep 20초 확대, (ii) repair 6회 확대, (iii) 새 abort 수리 허용량, (iv) 요청별 추가 탐색 allowance다. 어느 것도 이번 문서에서 채택하거나 설정에 반영하지 않는다. 20초 sweep만 늘려도 300/600 원뿔 크기 실패나 cycle 자체는 해결되지 않는다.

전체 비용 비교를 위해 **별도로 강제되는 요청당 추가 탐색 허용량 Δ를 최대 765요청에 동일 적용하고, 기존 요청 작업과 외부 비용이 그대로라는 가정**을 둔다.

| 추가 탐색 가정 | 추가 탐색 노출 | A 전체 비교값 |
|---|---:|---:|
| 요청당 +10초 | 최대 7,650초 | 13,388.224초 = 3.719시간 |
| 요청당 +20초 | 최대 15,300초 | 21,038.224초 = 5.844시간 |

이 값은 실제 요청 timeout 또는 총 wall 상한이 아니다. 일반식은 `T_v2 = 5,738.224 + 추가 탐색 + Δ컴파일/검증/정리 − 재사용 절감 + 기타 처리 변화`다. 표에는 추가 컴파일/검증/정리와 캐시 변화가 들어 있지 않다. 기존 600초 도구 호출과 solver 종료 여유도 유지된다. 전체 wall 상한이 필요하면 전 단계를 감싼 deadline과 중단 시 unknown 처리 규칙을 별도로 설계·승인해야 한다. 임의로 전체 20초를 적용하면 기존 최대 163.907초 요청과 L1 650 보존 조건을 깨뜨릴 수 있다.

예산 비교는 향후 W/S에 같은 설정으로 수행하고, 구조 개선판과 증액판의 결과를 분리한다. B의 성공률을 보고 예산을 조정하는 절차는 포함하지 않는다.

## 7. 승인 후 검증 계획 — 이번에는 수행하지 않음

리드 승인과 mem20 완료 조건이 충족된 뒤 별도 지시 범위에서만 구현·A 회귀를 수행한다. 현재 원래 state는 중단 상태이므로, 향후 v4.4 재실행이 완료되더라도 원래 v4.3 state를 completed로 고쳐서는 안 된다. 어떤 새 완료 기록과 원본 참조를 mem20 완료 근거로 쓸지는 후속 지시에서 명시해야 한다.

구현 시 기존 `tests/lifting_engine_regression_test.rs` 등 필수 회귀와 코드 필수 검사를 수행한다. 설계에 대응하는 확인 항목은 작은 cone SAT의 재현 실패가 L1이 되지 않는지, search-only UNSAT가 배제로 승격되지 않는지, 효과 없는 SAT가 제한된 대안으로 넘어가는지, cycle/한도/도구 오류가 unknown으로 남는지, 진단본·R1CS 변화·checker 불일치가 차단되는지, 저장소 키/기준 입력·W/S 순서 변경에 따라 증거가 섞이지 않는지다. 새 테스트는 구현 승인 후 작성한다.
