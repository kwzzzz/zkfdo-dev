# 계획 개정 제안: 규모 한계를 먼저 보이고, 순위는 실제 결함으로 시험한다 (2026-09-27)

**상태: 제안.** 지도교수와 논의한 뒤 확정한다. 확정 전까지는 [2026-09-24 계획](plan_revision_2026-09-24.md)과 그 규칙이 그대로 유효하다. 이미 고정한 프로토콜, 조사 결과, 실행 기록, 판정은 수정하지 않는다.

## 요약

- zkFuzz는 결함 부분만 떼어 낸 작은 회로에서는 찾는 결함을, 프로젝트 전체에서는 시간 안에 찾지 못한다. zkFuzz 논문과 2026년 SoK 논문이 이를 보고했고, 우리 측정도 같다(1절).
- zkfDO가 이미 만든 파이프라인(실제 `main`에서 타깃 탐색, direct wrapper 생성, 예산 스케줄러)이 바로 이 문제를 푸는 방법이다.
- 따라서 질문을 두 단계로 둔다.
  - **RQ1(기반):** 같은 시간 예산에서 zkfDO가 zkFuzz 전체 실행이 놓친 결함을 얼마나 되찾는가. 2026-09-24에 기준선이 없다는 이유로 축소했던 RQ5(대형 프로젝트)를 SoK가 제공하는 기준선과 함께 되살린 것이다.
  - **RQ2(핵심 기여):** 분해한 타깃이 예산 안에 다 돌 수 없을 때, 어떤 순위가 실제 결함을 더 빨리·많이 찾는가. 원래 연구 질문 그대로이며, 시험 방법만 바꾼다. 분해 자체는 zkFuzz 저자들이 제안한 방향이므로 우리 고유의 기여는 RQ2에 있다.
- 정답 결함은 우리가 심은 결함 대신 **공개 실제 결함**(zkbugs Circom 70건, SoK와 같은 계열의 자료)을 쓴다. 판정은 SoK와 같은 결함 위치 일치 기준을 쓴다.
- 주입 결함 평가(B1~B3)는 보류한다. 연구 주제("대형 프로젝트, 제한된 시간 예산")는 바뀌지 않는다.

## 1. 왜 바꾸는가

### 1.1 문헌이 확인한 규모 한계

- **zkFuzz 논문** (Takahashi et al., IEEE S&P 2026) 8절: 실행 시간이 대상 프로그램 크기에 비례하며, 대상을 잘라(slicing) 일부만 실행하면 개선될 수 있다고 적었다. 논문 평가는 2시간·5만 세대 설정에서 했다.
- **SoK 논문** (Kolozyan et al., arXiv 2607.23752, 2026-07): 실제 결함 70건을 **격리 모드**(결함 코드만 떼어 낸 최소 wrapper)와 **프로젝트 모드**(원래 코드베이스)에서 비교했다. 제한 시간은 600초다.
  - 도구 전체: 격리 모드 32/70(45.7%) → 프로젝트 모드 11/56(19.6%)
  - zkFuzz: 격리 모드 탐지 25건(시간 초과 25, 미탐 16, 오류 4) → 프로젝트 모드 탐지 4건(시간 초과 36, 미탐 12, 오류 4)
  - 두 모드 모두 컴파일되는 56건 중 14건은 격리 모드에서만 탐지됐다(도구 전체 기준).
  - 결론: 지금 도구들은 작은 코드 조각 분석에 더 맞는다.
- SoK는 Chaliasos et al.(USENIX Security 2024)의 데이터셋을 Circom 70건으로 확장했다고 밝혔다. 우리가 써 온 zkbugs(`a0eed74`)도 같은 데이터셋 계열이고 Circom 70건이다. 두 목록이 같은지는 R1에서 SoK 공개 산출물과 대조해 확인한다.
- **프로젝트 모드의 실제 구성 (2026-09-29 확인):** zkbugs 설정의 `Original Entrypoint`가 비어 있는 사례가 14건으로, SoK에서 프로젝트 모드로 컴파일되지 않은 건수(70 − 56)와 같다. 따라서 SoK의 프로젝트 모드는 zkbugs의 `Original Entrypoint`를 실행한 것으로 보인다(R1에서 확인). 그 56건 중 43건은 프로젝트 안의 실제 회로 파일이고, 13건은 결함 템플릿 하나만 감싼 생성 파일(예: `src/generated/subtract_main.circom`)이다. 생성 파일 13건은 이미 격리 모드에 가까우므로, 분해의 효과는 주로 43건에서 나타날 것이다.

### 1.2 우리 측정 (개발 프로젝트 inference)

같은 O1 결함(`Where`의 `<==` → `<--`)을 두 방식으로 실행했다([보고서](../reports/dev-ranking-pilot-2026-09-27/README.md#전체-회로-실행과의-비교)).

| 방식 | 결과 |
|---|---|
| 분해 실행 (`Where()` 타깃) | 세대 0에서 0.03초 만에 반례. 주입 타깃이 실행된 12회 모두 |
| 전체 실행 (`src/circuit.circom`, 비선형 제약 179,712개) | 30분 동안 세대 3개(0~2)만 끝내고 반례 없음. 세대 0 완료까지 908초 |

- 세대 하나에 약 440초가 걸렸다. 기본 500세대에는 약 61시간이 필요하고, 600초 제한이면 세대 0도 끝나지 않는다.
- 실행 중 스택 샘플에서 파싱은 이미 끝났고, 탐색 루프가 프로그램 전체 trace를 해석하는 함수에 머물러 있었다. zkFuzz는 세대마다 변형 프로그램 30개를 입력 30개에 모두 실행하므로 세대 하나의 비용이 전체 회로 크기에 비례한다. **이것이 대형 프로젝트에서의 병목이다.**

### 1.3 기존 평가 설계(B)의 문제 — P1 파일럿에서 확인

[P1 파일럿](../reports/dev-ranking-pilot-2026-09-27/README.md)(45회)에서 다음을 확인했다.

- **주입이 순위 특징을 바꾼다.** `<--` 주입으로 `Where`의 위험 점수가 0에서 2로 올라 cost-aware 순위가 14위에서 2위가 됐다. 위험 기반 전략에 유리한 순환이다.
- **zkFuzz가 찾을 수 있는지가 연산자마다 다르다.** 세 결함 중 O1만 탐지됐다. 탐지 범위 밖의 주입은 전략 비교에 정보를 주지 않는다.
- **부족 조건이 만들어지지 않았다.** 45회 중 27회가 모든 타깃을 시작했다.
- **정답 결함 하나를 만드는 비용이 크다.** 13개 기준 검증, 교란 쌍둥이, relation-exclusion 증명이 사례마다 필요하다.

### 1.4 zkFuzz 한계의 두 종류

| | 규모 한계 | 탐지 범위 한계 |
|---|---|---|
| 뜻 | 떼어 내면 찾지만, 전체에서는 시간 안에 못 찾음 | 떼어 내도 못 찾음 |
| 근거 | SoK 프로젝트 모드 시간 초과 36/56, 1.2절 측정 | SoK 격리 모드 미탐 16건, Tangle 의미 결함, P1의 O2 |
| zkfDO | **다루는 문제** | 범위 밖 |

결과를 해석할 때 두 종류를 섞지 않는다. 탐지 범위 한계로 못 찾은 결함은 zkfDO의 실패로도, zkfDO의 근거로도 세지 않고 따로 보고한다.

### 2.3 알게 된 것

1. **대형 프로젝트에서 먼저 막히는 것은 규모다.** 세대 하나의 비용이 전체 회로 크기에 비례해서, 전체 실행은 몇 세대도 못 돈다. 순위는 그다음 문제다. 분해한 타깃이 예산 안에 다 돌 수 없을 때 의미가 생긴다.
2. **zkFuzz의 한계는 두 종류이고, zkfDO가 고칠 수 있는 것은 규모 한계다**(1.4절).
3. **주입 결함은 순위 전략의 공정한 정답이 되기 어렵다.** 주입이 전략이 보는 특징을 직접 바꾼다.
4. **실제 결함의 공개 자료와 문헌의 판정 기준을 쓰는 편이 싸고 비교 가능하다.** SoK는 결함 위치 일치와 애매한 경우의 수동 확인으로 판정했다.
5. **도구 제약:** Circomspect(0.9.0)는 익명 컴포넌트가 있는 템플릿을 분석하지 못한다. 우리 탐색은 circomlib Poseidon 등에서 불완전해진다. zkbugs에는 취약·패치 쌍과 production 연결을 모두 갖춘 독립 후보가 없었다(T2b).
6. **아직 없는 것:** 순위 전략이 일반적으로 낫다는 근거, 프로젝트 호출 경로까지 검증된 새 결함.

## 4. 바꾸지 않는 것

- 고정 문서, 조사 결과, 실행 기록, 판정은 수정하지 않는다. 바꿀 때는 새 버전 파일을 만든다.
- 평가 사례에는 프로토콜을 고정하기 전에 zkFuzz를 실행하지 않는다. (c) 단계 사례는 T2b에서 zkFuzz 없이 조사만 했으므로 지금도 미실행이다.
- 원시 후보, witness, 컴파일 산출물은 ignored `runs/`에 두고 Git에는 값 없는 경로·해시·판정·시간만 둔다.
- 결과가 불리해도 그대로 보고한다. 결과를 본 뒤 규칙을 바꾸면 그 자료는 개발용으로 강등한다.
- zkFuzz는 기본 설정으로 실행한다(5절).

## 5. zkFuzz 설정 원칙과 화이트리스트

- zkFuzz++는 circomlib의 `IsZero`와 `Num2Bits`를 일부러 변이 대상에서 뺀다(zkFuzz 논문 5.2절 White List). 두 템플릿은 `<--`가 있지만 안전성이 증명돼 있어서, 변이하면 항상 제약 위반으로 끝나 탐색 시간만 쓴다. 거의 모든 회로에 여러 번 나오므로 빼면 탐색이 불확실한 코드에 집중된다. 논문의 ablation에서 화이트리스트를 빼면 일부 결함을 찾는 데 100배 넘게 느려졌다.
- 이 설계는 타당하며 바꾸지 않는다. 주 실험은 zkFuzz 논문·SoK와 같은 기본 설정으로 돌려야 비교가 공정하다.
- 화이트리스트는 템플릿 이름으로 판단하므로 "그 이름의 템플릿은 검증된 circomlib 원본"이라는 가정 위에 있다. P1의 O5 미탐은 우리가 프로젝트 자체 `IsZero` 안에 결함을 넣어 이 가정을 깬 결과다. zkFuzz의 결함이 아니라 우리 주입 위치 선택의 문제로 기록한다.
- 실제 결함 평가에서는 결함 위치가 화이트리스트 이름의 템플릿 안에 있는 사례를 표시한다. RQ1·RQ2의 주 비교는 기준선과 zkfDO 모두 기본 설정으로 돌린다. 그런 사례가 있으면, 이름이 같아도 내용이 circomlib 원본과 다른 템플릿은 건너뛰지 않는 설정을 zkfDO 옵션으로 추가하고 기본 설정 결과와 따로 보고한다. zkFuzz 내부는 고치지 않는다. 실행 기록에는 zkFuzz 설정을 남긴다.

## 6. 새 작업

### P2. 개발용 RQ1 파일럿 (실제 결함) — 담당: miiz

- **목적:** 정식 평가를 준비하는 동안, 이미 개발에 써서 오염 걱정이 없는 실제 결함으로 "통째 실행 대 분할 실행"을 먼저 비교해 본다. 기준선 실행 절차와 판정 방법도 여기서 시험한다. 독립 평가 결과가 아니다.
- **사례:** 개발 노출 결함 22건 중 `Original Entrypoint`가 프로젝트 회로 파일이고, 해당 커밋의 로컬 사본이 있으며, 고정 도구로 컴파일과 조각 탐색이 되는 것. inference `Subtract`는 production entrypoint(`src/circuit.circom`)로도 비교한다.
- **순서:** 후보 컴파일·조각 탐색(zkFuzz 없음) → 설정 파일 고정 → 실행 → 결함 위치 판정 → 보고서
- **보고서:** `reports/dev-rq1-pilot-2026-09-29/`

### R0. 계획 개정 — 담당: miiz

### R1. 평가 자료 확정 (zkFuzz 실행 금지) — 담당:

- SoK 공개 산출물(<https://github.com/t-sorger/zkp-security-tools>)에서 결함 목록, 프로젝트 모드의 entrypoint와 컴파일 설정, 도구 설정, 결과를 가져와 zkbugs `a0eed74`와 대조한다.
- 결함마다 노출 단계, `Original Entrypoint`의 종류(프로젝트 회로 파일·생성 파일·없음), 고정 circom 2.2.3으로 프로젝트 모드 컴파일 가능 여부, 결함 템플릿 위치, 결함 템플릿이 entrypoint의 루트 템플릿인지 여부, 화이트리스트 이름 여부, SoK의 zkFuzz 결과(격리·프로젝트 모드)를 기록한다.
- 산출물: 값 없는 평가 자료 목록(`datasets/`)과 보고서
- 금지: 평가 사례에 zkFuzz 실행, 평가 사례를 보고 도구를 사례별로 조정하는 것

### R2. 도구 보완 — 담당:

1. **전체 실행 기준선:** 프로젝트 entrypoint에 zkFuzz를 같은 예산·seed로 한 번 실행하고, 상태·완료 세대·최대 메모리를 기록한다([whole-main 스크립트](../reports/dev-ranking-pilot-2026-09-27/whole-main/run_whole_main.py)를 도구로 옮긴다).
2. **라이브러리 내부를 펼치지 않는 탐색:** 라이브러리 경로의 템플릿은 잎으로 두고, 프로젝트 자체 인스턴스를 완전하게 나열한다. Poseidon 등으로 탐색이 불완전해져 프로젝트가 빠지는 문제에 대응한다.
3. **위치 일치 평가:** 결함 템플릿 인스턴스에서 나온 반례를 탐지로, 그 상위 인스턴스에서 나온 반례는 따로 분류한다.
4. **실행 기록:** zkFuzz 설정(화이트리스트, 변이 설정)을 결과에 남긴다.
5. **루트 템플릿 처리:** entrypoint 파일 안에 `component main`이 있는 루트 템플릿은 더 작게 자를 수 없다. 결함이 루트 템플릿에 있는 사례를 R1에서 세고, 그런 사례를 zkfDO 실행에 어떻게 포함할지(예: 루트는 전체 실행 한 번으로 포함) 정한다.
6. **(조건부) 화이트리스트 옵션:** R1에서 결함이 화이트리스트 이름의 템플릿 안에 있는 사례가 나올 때만 5절의 옵션을 만든다.

- 시험은 이미 개발에 쓴 프로젝트(inference, circomlib 등)에서만 한다.

### R3. 평가 프로토콜 작성·고정 — 담당:

다음을 고정한다.

- 사례 집합과 노출 단계별 보고 방식. 평가 단위는 결함 하나(취약 커밋과 프로젝트 모드 entrypoint)다. RQ1의 주 집합은 `Original Entrypoint`가 프로젝트 회로 파일인 사례로 두고, 생성 파일 사례는 따로 보고한다.
- 예산: RQ1의 600초 조건과 RQ2의 부족 조건 예산
- 전략: 전체 실행 기준선, `random`(여러 ranking seed), `small-first`, `path-order`, `risk-only`, `cost-aware`
- zkFuzz seed 수, 병렬 실행 수
- 판정 규칙: 기준선 반례의 결함 귀속은 SoK처럼 수동으로 확인한다
- 분석: 결함별 짝 비교, 효과 크기와 서술 중심
- 실패·컴파일 불가·탐색 불완전의 처리

### R4. 실행 — 담당:

### 나중에 검토할 확장

- **RQ3 후보, 조각 단위 SMT 도구:** zkFuzz의 무작위 변형으로는 여러 값을 동시에 맞춰 바꿔야 드러나는 결함(P1의 O2)을 찾기 어렵다. Picus 같은 SMT 기반 도구는 출력이 하나로 정해지는지를 풀이로 확인하지만, SoK에서 프로젝트 모드에서는 시간 초과와 오류로 성과가 떨어졌다. zkfDO가 만든 작은 조각에서 이 도구를 함께 돌리면 분해가 다른 도구에도 도움이 되는지 볼 수 있다. 범위가 넓어지므로 RQ1·RQ2가 끝난 뒤 지도교수 동의를 받아 추가한다.
- **향후 과제, 명세 기반 판정:** 계산 코드와 제약이 같은 방식으로 틀린 의미 결함(Tangle)은 zkFuzz의 판정 방식으로는 원리상 찾을 수 없고, 사람이 쓴 명세가 필요하다. 이번 계획에서는 다루지 않는다.

## 8. 위험

- **되찾을 수 있는 격차의 크기는 R1 전에는 모른다.** SoK 격리 모드에서도 zkFuzz가 25건을 시간 초과했으므로 분해로도 못 찾는 결함이 있다.
- 옛 문법과 의존성 때문에 고정 컴파일러로 프로젝트 모드 컴파일이 안 되는 사례가 SoK(14건)보다 많을 수 있다.
- 분해 실행은 호출자 맥락이 빠지므로, 전체 회로에서는 나올 수 없는 입력으로 만든 후보를 낼 수 있다. 정밀도를 따로 보고한다.
- 600초 안에 모든 타깃이 끝나면 전략 차이는 탐지 시간의 차이뿐이다. 그래서 RQ2에는 부족 조건을 만드는 작은 예산을 따로 둔다. 실제 결함에서도 순위가 무작위보다 낫지 않을 수 있고, 그 경우 그대로 보고한다.
- (c) 단계 사례가 적으면 독립 결과는 서술적으로만 보고한다.
