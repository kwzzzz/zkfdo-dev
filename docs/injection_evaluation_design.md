# 주입 결함 평가 설계 (B) — 초안

작성일: 2026-09-26. **상태: 초안.** 이 문서는 아직 고정본이 아니다. T4(검토 엔진과 개발용 주입)와 T6(비용 보정)를 마친 뒤, **첫 B 평가 프로젝트를 열기 전에** 남은 값을 채워 최종 고정한다. 고정 뒤에 바꾸면 새 버전을 만들고, 그 전에 연 B 프로젝트는 개발용으로 강등한다.

## 1. 결정과 주장 범위

**결정 (2026-09-26, 결정자 miiz):** T2b의 0건 결과와 고정 문서는 그대로 보존한다. 이후 연구를 B와 C로 나눈다. B는 실제 버그에서 유도한 사전 고정 주입 결함으로 순위 전략을 비교하고, C는 변형하지 않은 실제 대형 프로젝트에서 실행 가능성과 비용을 측정한다. B 평가 프로젝트는 기존 개발 프로젝트, T2b 조사 프로젝트, T6 및 개발 주입에 사용한 프로젝트와 프로젝트 계열 단위로 분리한다. 새 취약점 발견은 완성 조건이나 B의 주 지표에 포함하지 않고 별도 탐색 성과로 둔다.

**B가 답하는 질문:** 실제 버그에서 유도한 **알려진 주입 패턴**이 처음 보는 프로젝트와 위치에 놓였을 때, 순위 전략이 제한된 시간 예산 안에서 그 결함을 더 빨리 또는 더 많이 찾게 하는가.

**B가 답하지 않는 질문:** 주입 패턴에 없는 새로운 결함 유형 전반에 대한 성능. 이렇게 확대해서 주장하지 않는다. 실제 결함에 대한 검출 타당성은 개발 사례(v1.1~v3)로 따로 보인다.

## 2. 프로젝트 풀

### 2.1 "처음 보는 프로젝트"의 정의

설계와 도구를 고정하기 전에 **개발이나 튜닝에 쓰지 않은 프로젝트**다. 고정된 절차로 처음 열어 적격성을 검사하는 것은 괜찮다. 하지만 그 뒤에 도구를 고치면, 그 프로젝트는 개발용으로 강등한다.

### 2.2 제외

[B 전용 제외 스냅샷](../datasets/exclusions.injection-eval.draft.json)에 있는 프로젝트와 그 계열은 B에 쓰지 않는다. 지금은 기존 개발·조사 프로젝트 14개와 T2b에서 열었거나 확장 단계에서 살펴본 16개를 합친 30개가 들어 있다. B를 고정할 때 T6 보정 프로젝트와 개발용 주입 프로젝트를 추가한다.

- **같은 계열:** 포크와 부모 저장소는 같은 계열이다. circomlib 같은 표준 의존성을 빼고, 제외 프로젝트의 `.circom` 파일과 바이트가 같은 파일을 가진 저장소도 같은 계열로 본다.
- 개발용 주입(T4)은 **이 스냅샷에 이미 있는 프로젝트에서만** 한다.

### 2.3 후보 목록과 T6·B 분할

사람이 "좋아 보이는" 프로젝트를 B에 고르지 않도록, 후보는 목록으로 먼저 고정하고 T6와 B에 무작위로 나눈다.

1. 공개 Circom 프로젝트 후보 목록을 **고정한 출처와 날짜**로 만든다(예: 정해진 GitHub 검색어, 정렬 기준, 조회일). 출처와 검색어는 고정할 때 정한다.
2. 제외 스냅샷과 계열 규칙으로 거른다.
3. 남은 목록을 고정 seed로 섞고, 정해진 비율로 T6 풀과 B 풀에 나눈다.
4. T6는 T6 풀에서만, B는 B 풀에서만 **목록 순서대로** 적격성을 검사한다. 부적격이면 사유를 기록하고 다음 프로젝트로 넘어간다.

## 3. 프로젝트 적격성 (T6·B 공통)

[T2b 공통 절차](../reports/heldout-survey-2026-09-26/PROCEDURE.md)를 그대로 쓴다.

0. **프로젝트 성격:** 저장소 자체의 회로가 응용이나 프로토콜을 구현해야 한다. 컴파일러·분석기·린터·코드 통계 도구처럼 테스트용 `.circom` 파일만 가진 저장소, 결함 데이터셋, 튜토리얼·강의·퍼즐·CTF 모음은 부적격이다. README와 저장소 설명으로 판정하고 사유를 기록한다. 후보 목록이 메타데이터만으로 만들어졌기 때문에 이 검사는 목록 순서대로 적격성을 볼 때 한다.
1. 원래 저장소 revision을 고정할 수 있다.
2. production entrypoint가 빌드·배포 설정이나 문서로 실제 산출물에 연결된다.
3. 의존성을 lockfile 고정 버전으로 설치할 수 있다(설치 스크립트 차단).
4. production `main`이 circom 2.2.3으로 컴파일된다.
5. 고정 도구의 탐색이 **complete**다(미지원 구문, 미해결 include 없음).
6. 프로젝트 자체 소스의 고유 인스턴스 수 `N_p`가 기준 이상이다(값은 고정할 때 정한다).

## 4. 주입 연산자 (실제 결함에서 유도)

개발 사례에서 실제로 확인한 결함을 거꾸로 적용한 패턴이다. 연산자 목록과 가중치는 고정할 때 확정한다.

| ID | 변형 | 유래한 실제 결함 | 적용 조건 |
|---|---|---|---|
| O1 | 신호 정의 `s <== e`를 `s <-- e`로 바꿔 제약을 없앤다 | Subtract(곱셈 결과 미제약), Add32Bits(carry 미제약) | `s`가 출력이거나, 출력에 영향을 준다 |
| O2 | 비트 신호의 불리언 제약 `b * (b - 1) === 0`을 없앤다 | XorWords(비트 제약 누락) | `b`가 비트 분해나 선택에 쓰인다 |
| O3 | 비교기 입력의 범위 검사(`Num2Bits(n)` 등)를 없앤다 | Banyan CheckDepth, zk-email FpMul, BigMod(입력 범위 누락) | 검사 대상이 `LessThan`·`GreaterThan` 계열의 입력이다 |
| O4 | 엄밀한 비트 분해를 필드 크기 분해로 바꿔 별칭(alias)을 허용한다 | UniRep BigLessThan(`Num2Bits` 별칭) | 254비트 분해나 `AliasCheck`가 있다 |
| O5 | 출력과 조건을 잇는 등식·`IsZero` 제약을 없앤다 | circomlib Decoder(출력 미제약) | 출력이 입력 조건으로 결정된다 |

주입 위치는 **평가 프로젝트 자체의 템플릿**으로 한정한다. 의존성 라이브러리는 바꾸지 않는다.

## 5. 표집 절차

표집 단위는 **프로젝트 → 고유 타깃 → 연산자 → 적용 위치**다. 각 단계는 고정 seed의 결정적 난수로 고른다.

1. 프로젝트마다 주입 결함 `M`개를 만든다. 결함마다 서로 다른 고유 타깃에 놓는다.
2. 고유 타깃은 프로젝트 자체 소스의 인스턴스 가운데 고정 seed로 순서를 섞어 앞에서부터 고른다.
3. 타깃마다 적용 가능한 연산자를 가중치에 따라 고르고, 그 연산자의 적용 위치 가운데 하나를 고른다.
4. **실패하면 넘어가는 규칙:** 적용 위치가 없거나, 컴파일이 실패하거나, 6절의 검증을 통과하지 못하면 같은 타깃의 다음 위치 → 다음 연산자 → 다음 타깃 순으로 넘어간다. 넘어간 사례와 사유는 모두 기록한다. 결함이 `M`개가 될 때까지 계속하고, 타깃이 모자라면 부족한 채로 기록한다.
5. 한 프로젝트의 결함들은 한 변형본에 함께 넣는다. 결함끼리 서로의 타깃 경로에 영향을 주면 앞서 고른 결함만 남기고 뒤의 것은 4번 규칙으로 다시 고른다.

## 6. 주입 결함의 독립 검증 (zkFuzz 없이)

주입한 결함마다 다음 다섯 가지를 모두 확인해야 평가에 넣는다.

1. **입력 계약 충족:** 반례의 입력이 clean 원본 wrapper의 입력 계약을 만족한다.
2. **mutant 제약 전체 충족:** 반례 witness가 mutant의 R1CS 제약을 모두 만족한다.
3. **속성 위반:** 사전에 정한 property signal에서 불변식 위반을 직접 판정한다. 출력이 있는 경우 같은 입력의 clean 출력과 다른지를 쓸 수 있다. 출력이 없는 경우에도 비트성·범위·보존식처럼 독립적인 속성이 있어야 하며, 4번으로 대신하지 않는다.
4. **clean relation에서 배제:** 같은 입력의 정상 clean witness가 clean R1CS를 만족하는지 먼저 확인한다. 고정된 signal-name projection으로 만든 disturbance assignment가 주입 관련 clean 제약을 깨뜨리는지 확인한 뒤, 같은 input/property signal을 유지하면서 다른 clean-only wire로 제약을 만족시킬 수도 없음을 기계적으로 확인한다. 방법은 모든 실패 제약 wire가 사전 property signal로 고정되는 경우, 연산자별 proof checker, 또는 검증 가능한 UNSAT certificate 중 하나로 미리 고정한다.
5. **production 도달:** 주입한 템플릿 인스턴스가 production entrypoint에서 도달 가능하다.

**반례 만드는 방법(교란 쌍둥이):** mutant와 **제약은 같고 witness 계산식만 다른** 쌍둥이 소스를 만든다. 예를 들어 O1이면 `s <-- e`를 `s <-- e + 1`로 바꾼다. 쌍둥이의 R1CS와 SYM이 mutant와 같은지 raw hash로 확인한 뒤, 계약을 만족하는 공통 입력으로 clean과 twin witness generator를 모두 다시 실행한다. generator·입력·산출물의 해시를 고정하고, clean witness의 canonical 표현·완전성·clean R1CS 전체 제약 충족을 확인한다. 연산자마다 교란 규칙, clean projection, relation-exclusion 증명 방식을 미리 정한다(O2는 비트 값을 2로, O4는 다른 분해를, O5는 틀린 출력을 쓴다). projected assignment 한 건의 실패만으로 relation 차이를 주장하지 않는다. 독립 property나 relation-exclusion certificate를 만들지 못하면 그 위치는 실패로 기록하고 5절 4번 규칙으로 넘어간다. **zkFuzz로 돌려서 잡히는 결함만 남기지 않는다.**

검증은 T4 공용 검토 엔진(입력 전제, 원본 제약 전체, 사전 속성)을 확장해서 한다.

## 7. 편향 기록

주입은 순위 특징을 직접 바꿀 수 있다. 결함마다 clean → mutant 변화를 기록한다.

| 항목 | 영향받는 전략 |
|---|---|
| Circomspect 경고 수와 규칙별 위험점수 | `risk-only`, `warning-first`, `cost-aware` |
| 제약 수(`size`) | `small-first`, `cost-aware` |
| 경로(`path`) | `path-order` |
| 동점 그룹(`ties`) | 동점 처리를 쓰는 모든 전략 |

결과는 "주입이 해당 전략의 특징을 바꿨는가"로 나눠서 보고한다. 특징을 바꾸지 않은 결함만 모은 집계를 함께 보여, 결함을 심는 방식 자체가 전략에 유리하게 작용했는지 구분한다.

## 8. 실험과 분석 (T3·T7로 연결)

- [계획 문서](plan_revision_2026-09-24.md) 2절의 설계를 따른다. 프로젝트마다 같은 절대 시간 예산으로 한 번의 paired-block 캠페인을 돌리고, 결과는 프로젝트별과 동일 가중 macro로 보인다. 효과 크기와 서술적 결과를 중심으로 보고하며, 프로젝트별 `started/N_p`를 반드시 적는다.
- **주 지표:** 주입 결함의 최초 발견시간과 예산 내 발견 수. 발견은 zkFuzz 후보가 6절과 같은 세 기준(입력 계약, mutant 제약, 속성 위반)을 통과하고, 주입한 결함 위치와 일치할 때만 센다.
- **순위 품질 보조 분석:** 계획상 배치(주입 결함 인스턴스의 계획 순위)와 실행 검증 발견을 구분한다.
- **자연 결함 후보:** 주입 위치가 아닌 곳에서 나온 후보는 B의 발견 수에 합치지 않는다. 별도로 검토하고, 진짜 결함이면 공개 전에 프로젝트에 알린다.

## 9. 고정할 때 채울 값

- 후보 목록의 출처·검색어·조회일, 분할 seed와 T6·B 비율
- 프로젝트 수 목표와 최소 `N_p`, 프로젝트당 결함 수 `M`
- 연산자 목록과 가중치, 연산자별 교란 규칙·clean relation-exclusion 증명 방식
- 표집 seed
- 시간 예산과 타깃별 timeout(T6 보정 결과로), 전략 목록, ranking seed와 paired block 수
- 분석 스크립트와 그 해시
- 크기 편향을 보정한 민감도 분석을 둘지 여부

## 10. 한계

- 주입 결함은 인공 결함이다. 결과는 주입 패턴과 비슷한 결함에 대해서만 말할 수 있다.
- 연산자는 개발 사례에서 유도했으므로, 개발 사례와 비슷한 결함 유형에 치우칠 수 있다.
- 작성자와 검토자가 같다(miiz). 고정 전 점검과 교차 확인 기록으로 보완한다.
