**용어:** 이 문서에서 **취약본**은 결함이 있는 실제 과거 소스이고, **패치 대조본**은 그 결함을 고친 실제 패치 소스다. 패치 대조본은 다시 **공식 패치**(프로젝트에 병합된 커밋, 예: UniRep `3348caa`)와 **제안 패치**(병합되지 않은 PR, 예: circomlib Decoder의 open PR #81 `9d2918e`)로 나눠 적는다. 두 경우 모두 우리가 코드를 일부러 취약하게 바꾼 것이 아니다. 원본을 변형해 만든 fixture(예: MiMCSponge)는 정확한 원본·패치 쌍이 아니므로 평가에서 제외한다.

## 1. 왜 수정하는가

지금까지 확인한 것은 **파이프라인이 알려진 결함을 끝까지 재발견하고, 검토 기준까지 통과시킬 수 있다**는 점이다(v1.1, v2, v3에서 각 1건). 연구의 핵심 주장은 **예산이 부족할 때 순위를 매겨 실행하면 무작위나 단순 기준보다 검토를 통과한 결함을 더 빨리 또는 더 많이 찾는다**는 것인데, 이 주장은 아직 시험하지 못했다. 이유는 다음과 같다.

1. **예산이 부족한 상황을 한 번도 만들지 않았다.** 지금까지 실험의 타깃은 2~4개였고, 예산 안에서 모두 끝까지 실행됐다. 이렇게 되면 전략 간 차이는 순서 효과뿐이다(v2 보고서에도 기록됨). 순위가 의미를 가지려면 모든 타깃을 다 실행할 수 없어야 한다.
2. **취약본·패치 대조본 쌍은 순위 평가에 맞지 않는다.** 패치는 보통 제약 몇 줄 차이라서 정적 특징이 거의 같다. v3에서 두 쌍 모두 위험점수가 같았다(`0=0`, `1=1`). 동점은 `target_id`(소스·설정의 SHA-256) 오름차순으로 정리되므로([src/static_rank.rs](../src/static_rank.rs) `risk_order`), 패치 대조본이 먼저 실행된 것은 편향이 아니라 해시 순서에 따른 우연이다. 설계의 문제는 패치 대조본을 순위 실행 예산에 함께 넣은 것 하나다. 쌍 설계는 **취약본에서 나온 문제가 패치 대조본에서 사라지는지 확인하는 통제용**이지 순위 평가용이 아니다.
3. **사례 하나를 검증하는 비용이 크다.** 9/15~9/23 동안 한 번에 결함 1~2개를 검증했다. 이 속도로는 원인 5개 이상·프로젝트 3개 이상으로 여러 전략을 짝지어 비교하기 어렵다.
4. **계획한 범위가 구현 범위보다 넓다.** `evaluation_plan.md`의 `analyzer-aware`, `adaptive` 전략과 RQ4(smoke→deep)는 구현돼 있지 않다. `cost-aware`는 T5에서 추가했다.

## 2. 수정 결정

| 항목 | 기존 계획 | 수정 |
|---|---|---|
| 평가 세트 구성 | 알려진 원인마다 취약본·패치 대조본 쌍, 직접 래퍼 중심 | **취약 버전 프로젝트의 실제 `main`에서 도달 가능한 구체 타깃 전부**(결함 타깃 + 결함 없는 타깃)를 한 세트로 둔다. 패치 대조본은 순위 대상에서 빼고, 후보가 나왔을 때 문제가 사라지는지 확인하는 음성 대조로만 쓴다 |
| 부족 조건 | 모든 타깃을 실행할 수 있는 수준 | **프로젝트마다 같은 절대 시간 예산 하나로 캠페인을 한 번 실행한다.** scheduler는 실제 경과시간을 차감하므로 타깃이 빨리 끝나면 모두 시작될 수 있다. 그러면 "부족 조건 조성 실패"로 기록하고 다시 돌리지 않는다. 같은 절대 예산이므로 프로젝트마다 실행되는 비율이 달라지는데, 이는 의도한 운영 설계다. 그래서 결과에는 프로젝트별 `started/N_p`를 반드시 보고한다. 모든 타깃이 시작된 프로젝트도 사후에 빼지 않고 부족 조건 조성 실패로 주 결과에 포함한다. 이런 프로젝트를 뺀 집계를 보일 때는 민감도 분석으로만 표시한다. 2026-09-24에 정한 조건 A(프로젝트별 상위 `K_p`개만 시작)의 별도 실행은 2026-09-26에 취소했다(6절) |
| 순위 품질 보조 분석 | 조건 A 별도 실행 | 같은 계획과 실행 기록에서 두 지표를 **구분해서** 본다. **(1) 계획상 배치:** 알려진 결함 인스턴스가 각 전략의 계획 순위 몇 번째에 있는지(첫 결함 인스턴스의 순위, 상위 k개 안의 결함 인스턴스 수). 실행 없이 계산되며 실제 발견 성과가 아니다. **(2) 실행 검증 발견:** 계획 순서의 앞 k개 안에서 실행으로 나오고 검토를 통과한 고유 원인 수. 실패와 타깃별 정상 timeout도 자기 순위 자리를 차지하고, 빼고 뒤를 당겨 세지 않는다. 전체 예산 때문에 잘린 실행(기록된 `execution_limit_seconds`가 타깃별 제한보다 작은 실행)은 따로 분류한다. 비교할 k는 모든 전략·block에서 끝까지 실행된 연속 구간 안으로 T3에서 미리 정한다. (2)는 비용과 실행 결과의 영향을 받으므로 "비용과 무관한 순위 품질"이라고 부르지 않는다 |
| 입력 계약 | – | 타깃은 고유 실행 구성(`instance_key`: 소스·템플릿·구체 인자)이다. 입력 계약은 direct wrapper 자체의 계약 하나로 정하고, 주 평가는 이것으로 판정한다. 호출자마다 보장하는 입력 범위가 다를 수 있으므로 호출자별 영향은 프로젝트 수준 지표로 따로 판정한다. manifest는 타깃당 계약을 하나만 가진다 |
| 예산 결정 | – | T3에서 **고유 인스턴스 기준 `N_p`**(호출 위치 수가 아니다)와 **개발용 비용 측정**으로 시간 예산과 타깃별 timeout을 정한다. 비용 측정은 T1 제외 프로젝트나 zkbugs 밖 프로젝트(T6)에서만 한다. 예산을 정하는 데 쓴 프로젝트는 보정 자료로 표시하고, 같은 결과를 독립 검증 결과로 다시 제시하지 않는다. 준비·컴파일 비용은 퍼징 예산과 따로 기록한다 |
| 실행 단위와 집계 | 여러 타깃을 한 순위로 | **프로젝트별로 순위를 매기고 예산을 적용해 실행한다.** 결과는 프로젝트별로 먼저 제시하고, 프로젝트마다 같은 가중치를 둔 macro 평균으로 모은다. 타깃이 많은 프로젝트가 결과를 지배하지 않게 하기 위해서다 |
| 분석 | 유의성 비교 | 프로젝트와 결함 수가 적어 검정력이 낮다. **효과 크기와 서술적 결과를 중심**으로 보고하고, 유의성은 주장하지 않는다 |
| 비교 전략 | 계획서의 8개 | 필수: `random`(여러 ranking seed), `small-first`, `path-order`, `risk-only`, `cost-aware`. 선택: `warning-first`(Circomspect 설치 시). `adaptive`, `analyzer-aware`는 제외 |
| RQ3 (분석기 경고) | 별도 결합 전략 | `warning-first`와 `risk-only`를 한 번 비교하는 것으로 축소 |
| RQ4 (smoke→deep) | 핵심 기여 | **향후 과제로 이동.** 시간이 남으면 T8의 최소 형태만 구현 |
| RQ5 (대형 프로젝트 관리) | naive 실행과 비교 | 현재 절차에는 naive 기준선이 없다. **실제 규모에서의 발견률·준비 성공률·비용 feasibility로 한정**한다(T6). 결함을 찾지 못해도 결과로 성립한다 |
| 후보 검토 | 사례마다 수동 스크립트 작성 | **공용 검토 엔진과 사례별 속성 predicate를 분리해 자동화**(T4). 사람은 사전 속성 정의와 최종 판정 확인만 한다 |
| 동점 처리 | 문서화 안 됨 | 각 전략의 주 기준이 같으면 `target_id` 해시 순서로 정한다. 계획 JSON에 `ties`를 기록하고 실행 전에 다시 계산해 검증한다(T5) |
| 음성 결과 | – | 순위 전략이 이기지 못하면 그대로 보고하고 원인(특징 해상도, 동점, oracle 한계 등)을 분석한다. 가중치를 사후에 바꾸면 그 세트는 개발용으로 강등한다 |

바뀌지 않는 것:

- 주 지표: 실행에서 나온 후보가 (1) 입력 전제 충족, (2) 고정 원본 제약 전체 충족, (3) 사전 정의 속성 위반을 모두 통과한 **고유 원인**의 최초 발견시간과 예산 내 개수
- 프로젝트 호출 경로까지 확인된 결함은 별도로 집계한다
- 원시 후보와 대형 산출물은 ignored `runs/`에 두고, Git에는 해시·판정·시간만 둔다
- 독립 평가 세트는 원인 5개 이상, 프로젝트 3개 이상

## 2-1. T2b 이후 결정: B+C (2026-09-26)

> T2b의 0건 결과와 고정 문서는 그대로 보존한다. 이후 연구를 B와 C로 나눈다. B는 실제 버그에서 유도한 사전 고정 주입 결함으로 순위 전략을 비교하고, C는 변형하지 않은 실제 대형 프로젝트에서 실행 가능성과 비용을 측정한다. B 평가 프로젝트는 기존 개발 프로젝트, T2b 조사 프로젝트, T6 및 개발 주입에 사용한 프로젝트와 프로젝트 계열 단위로 분리한다. 새 취약점 발견은 완성 조건이나 B의 주 지표에 포함하지 않고 별도 탐색 성과로 둔다.

- **결정자:** miiz. 기준 문서 4절("부족하면 T3를 어떻게 진행할지 결정하고 이유를 기록한다")에 따른 결정이다.
- **이유:** zkbugs에서 독립 평가 후보를 하나도 확보하지 못했다(패치 출처, production 연결, 옛 Circom 문법 때문). 순위 효과는 정답이 있는 결함으로만 공정하게 셀 수 있으므로 B로 검정하고, 실제 규모에서의 쓸모는 C로 보인다. 실제 결함 사례(v1.1~v3)는 실제 결함 검출 타당성의 근거로 남긴다.
- **B의 주장 범위:** 알려진 주입 패턴이 처음 보는 프로젝트와 위치로 일반화되는가. 새로운 결함 유형 전반의 성능으로 확대해서 주장하지 않는다.
- **완성 조건:** B(순위 효과), C(실행 가능성과 비용), 개발 사례 검증. 새 취약점은 완성 조건이 아니다.
- **설계:** [주입 결함 평가 설계 초안](injection_evaluation_design.md), [B 전용 제외 스냅샷 초안](../datasets/exclusions.injection-eval.draft.json). 기존 제외 목록과 heldout 기준 문서는 수정하지 않는다.
- **표현:** T6의 프로젝트는 "결함 없는 프로젝트"가 아니라 "결함을 주입하지 않은 원본 프로젝트"다.

### T3a. 개수 상한(`K_p`) 구현 — 취소 (2026-09-26)

- **취소 이유:** 조건 A를 별도로 실행하지 않기로 했다(2절, 6절). 순위 품질은 같은 계획과 실행 기록에서 보조 분석한다. 이 작업으로 구현한 코드는 없다.

- **금지:** 기존 보고서의 판정 파일을 덮어쓰지 않는다. 신호 값을 Git에 커밋하지 않는다.
- **완료 (2026-09-27):** strict schema 1 spec/request/report/index, raw R1CS·SYM·assignment 검증, 고정 timeout의 predicate·generator·compiler·외부 verifier, backend·주입 검토, selected-entrypoint reachability와 clean relation-exclusion 검증, schema 2 confirmation·실제 evaluator 연결을 구현했다. backend spec은 frozen prepared corpus의 R1CS·compiler·semantic arguments와 결속하고, 주입 qualification은 별도 full reproduction argv로 닫힌 `-l` include 순서와 exact wrapper instance를 재검증한다. qualification bundle은 현재 엔진으로 다시 실행해 원본 review와 일치해야 하며, 같은 spec의 backend request가 이를 실제 소비하는 통합 시험을 통과한다. final output은 staging 완성 뒤 atomic rename한다. 보존된 v1.1 36쌍·v2 36쌍·v3 1쌍의 후보 73개가 모두 기존 판정과 일치했고, 220개 실행 행(비후보 147개), 원인 중복 제거, 값 비보존과 frozen oracle·내부 evidence hash를 자동 교차 검증했다. 합성 시험으로 후보 0개, 복수 후보·복수 spec, 후보 파일·adapter·공유 입력 오류 경계와 주입 qualification의 정상·generator·compiler library·assignment·hash·parse·binding 경로를 검증했다. `clean_revision`의 upstream checkout, `single_diff` patch 적용, production entrypoint 지정은 B2 프로젝트 provenance의 별도 필수 gate로 남긴다.
- **보완 (2026-09-27):** 처음 올린 시험 일부가 Git에 없는 로컬 증거(컴파일한 R1CS·SYM, 보존 후보, 빌드 경로의 실행 파일, 당시 소스 스냅샷)를 요구해 깨끗한 checkout과 CI에서는 컴파일되지 않거나 실패했다. 이 시험들은 로컬 전용(`#[ignore]`)으로 표시하고, 회귀 검증을 추적 증거 모드(CI 기본)와 `--require-local-evidence` 모드로 나눴다. macOS에서 막 생성된 프로세스 그룹에 대한 일시적 EPERM도 짧게 재시도한다. 회귀 결과는 `runs/`에 보존한 실행 파일로 다시 만들었고, 판정 내용은 이전 결과와 같다. backend 경계 시험을 합성 fixture로 옮겨 CI에서도 돌게 하는 일은 후속으로 남긴다.

### T5. `cost-aware` 전략과 동점 기록 — 담당: miiz

- **목표:** `evaluation_plan.md`에는 있지만 구현되지 않은 `cost-aware` 전략을 추가하고, 동점 정보를 계획에 남긴다.
- **완료 조건:** `cargo fmt`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test`를 통과한다. 기존 전략의 계획 순서는 바뀌지 않는다.
- **금지:** 기존 전략의 점수나 가중치를 바꾸지 않는다. v1~v3 결과를 보고 가중치를 조정하지 않는다.
- **결과 (2026-09-24, 검토 대기):**
  - `cost-aware` = `risk_score / cost_bits(size)` 내림차순. `size`는 prepare 단계에서 이미 측정하는 컴파일 제약 수이고, `cost_bits`는 `size + 1`의 비트 길이(대략 log₂)다. 이는 실행 시간을 측정해 만든 비용 모델이 아니라, 타깃 크기의 영향을 완만하게 반영하는 휴리스틱이다. timeout이 있다는 사실만으로 로그 공식이 정당화되지는 않는다. 제약 수를 그대로 쓰면 0~5점짜리 위험점수가 묻히므로 로그 척도를 썼다. 정수 곱으로 비교해서 플랫폼과 관계없이 같은 순서가 나온다.
  - **동점 규칙:** 모든 전략은 자신의 주 기준이 같을 때 `target_id` 순으로 정한다. `cost-aware`의 주 기준은 "비율, 그다음 작은 `size`"이므로, 비율이 같으면 제약 수가 작은 쪽, 그것도 같으면 `target_id` 순이다. `ties`는 이 주 기준이 같아서 `target_id`로만 순서가 갈린 그룹을 센다.
  - **계획 schema 2:** 새 계획은 `schema_version: 2`이고 `ties`(그룹 수, 해당 타깃 수, 최대 그룹 크기)를 반드시 가진다. 실행 전에 다시 계산해서 다르면 거부한다. `random`은 `null`이어야 한다. 기존 고정 계획(schema 1)은 `ties` 없이 그대로 허용하고, schema 1에 `ties`가 붙어 있으면 거부한다. 고정된 v3 계획이 새 검증을 통과하는 것도 확인했다.
  - **회귀 확인:** 고정된 v3 prepared 파일로 `risk-only` 계획을 다시 만들었을 때 순서가 저장된 계획과 같았다. `ties`는 v3의 두 동점 쌍을 `tie_group_count: 2`로 보고했다. 테스트 146개 통과, 로컬 도구가 필요한 5개는 ignored.
  - **확인 (2026-09-26):** 현재 공식을 유지하기로 확정했다. 평가 후보를 본 뒤에는 공식을 바꾸지 않는다. `src/static_rank.rs`의 `cost_bits` 주석에 남아 있는 timeout 근거 문구는 조사 기간 동안 도구 소스를 고정 커밋과 같게 두기 위해 T2b 뒤에 고친다.
  - **주의:** v3에서 `cost-aware`는 두 쌍 모두 취약본을 먼저 둔다. 제약이 빠진 취약본의 `size`가 더 작기 때문이다. 이는 취약본·패치 대조본 쌍 설계에서 생기는 현상이고 순위 성능의 근거가 아니다. v3는 개발용이며, 이 확인은 공식을 정한 뒤 회귀 점검으로만 했다.

### T6a. 제외된 프로젝트로 도구 진단·보완 (T2b 선행) — 담당: miiz

- **목표:** T2b를 시작하기 전에 실제 프로젝트 탐색의 한계를 찾아 고친다. zkFuzz는 실행하지 않는다.
- **반드시 T1 제외 목록에 있는 프로젝트만 쓴다.** 평가 후보 프로젝트를 열어 보고 도구를 고치면 그 후보는 개발 자료가 된다.
- **알려진 한계:** 현재 탐색은 저장소 전체에서 `component main`이 정확히 하나여야 한다([src/targets.rs](../src/targets.rs)). 실제 프로젝트는 `main`이 여러 개인 경우가 많다. 라이브러리 경로 지정과 wrapper 컴파일 timeout 처리도 부족하다.
- **최소 구현 범위:**
  - 한 번에 하나의 `--entrypoint PATH` 지정, 선택한 entrypoint의 도달 가능 closure만 처리
  - 반복 가능한 `--library-path`
  - wrapper별 컴파일 timeout(기준 문서의 600초)과 자식 프로세스 트리 종료
  - entrypoint, library path, 실행 명령, 경과시간, 상태(성공·실패·timeout)를 결과에 기록
  - synthetic fixture와 이미 제외된 실제 프로젝트로 회귀 검증
- **산출물:** 진단 보고서(막힌 지점과 원인), 위 기능 구현과 테스트, 확정한 zkfDO 커밋·바이너리 해시, circom 바이너리 해시, CLI 인자, 하드웨어 기록
- **진행 (2026-09-24):** 최소 구현 범위를 모두 구현했다(커밋 `87c799f`, 테스트 153개 통과). 진단 중 lexer의 제곱 시간 문제를 찾아 고쳤다. 제외된 프로젝트 6개의 `main` 191개가 모두 인식되고 컴파일 경로도 동작한다. 남은 한계는 Circom 구문 지원(특히 익명 컴포넌트 호출), 의존성 설치 절차, production entrypoint 판정이다. [진단 보고서](../reports/t6a-discovery-diagnostic-2026-09-24/REPORT.md)
- **진행 (2026-09-26):** 익명 컴포넌트 호출(`Template(params)(signals)`)의 도달성 탐색을 구현했다(커밋 `d4f0ea5`). 반복문과 중첩 호출, 구체 템플릿 인자를 처리하고, 구체화할 수 없는 인자는 추정하지 않고 미지원으로 기록하며, 같은 줄의 서로 다른 호출 위치도 구분한다.
- **진행 (2026-09-26):** wrapper 컴파일을 컴파일 단위로 재사용한다(커밋 `17eea4c`). 재사용 키는 wrapper 원문, 의존성 closure 해시, circom 바이너리, 컴파일 설정, 제한시간이다. 호출 위치별 항목과 직접 부모는 그대로 남고, `instance_key`·`parent_instance_key`로 상위 호출 경로 전체를 복원할 수 있다. 제외된 프로젝트 3개(entrypoint 18개)에서 컴파일 5,240회가 63회로, 컴파일 시간이 159.8초에서 4.0초로 줄었고, 호출 위치 5,240개의 컴파일 결과는 전후에 모두 같았다([측정 보고서](../reports/t6a-compile-reuse-2026-09-26/REPORT.md)). 의존성 설치 절차와 production entrypoint 판정은 기준 문서 3·4단계에 규칙을 넣었다. 남은 미지원 구문(예: Moonsong의 1,089건)은 추가 구현하지 않고, 기준 문서대로 탐색이 불완전한 프로젝트를 주 평가에서 제외한다.
- **완료 (2026-09-26):** 컴파일 시도와 실제 프로세스 시작을 구분했다(커밋 `2f4ad7d`). 조사용 바이너리를 `runs/heldout-tooling-2026-09-26/zkfDO`(SHA-256 `750ecb03…`)로 보존하고, 도구 해시와 조사 명령을 기준 문서 1절에 고정했다.

### T6. zkbugs 외 대형 프로젝트 실행 가능성 연구 (RQ5) — 담당:

- **전제:** T6a에서 나온 필수 기능 구현
- **목표:** 실제 규모 Circom 프로젝트에서 zkfDO의 타깃 발견률, 준비 성공률, 비용을 측정한다. 비교가 아니라 feasibility 연구다.
- **T3 입력 역할:** 타깃별 실제 실행 시간 분포를 재서 T3의 시간 예산과 타깃별 timeout을 정하는 데 쓴다. 이렇게 쓴 프로젝트는 보정 자료로 표시하고, 같은 결과를 독립 검증 결과로 다시 제시하지 않는다.
- **절차:**
  1. zkbugs 데이터셋에 **사례로 들어 있지 않은** 공개 Circom 프로젝트 2~3개를 고르고 커밋을 고정한다. 선정 이유와 제외 이유를 기록한다.
  2. 각 프로젝트의 실제 `main` 파일들에서 타깃을 탐색한다.
  3. 기록할 항목: 파일·템플릿 수, 발견한 구체 인스턴스 수, 지원하지 않는 구문 때문에 빠진 수, wrapper 컴파일 성공률, 준비 시간, 균일 예산 실행에서 `timeout`, `failure`, `no_counterexample`, `bug_found` 비율, 타깃별 비용 분포.
  4. 실행 전에 예산·seed·도구 해시를 고정한다.
  5. `bug_found` 후보가 나오면 T4 도구로 세 기준을 검토하고, 프로젝트 호출 경로 확인은 별도로 기록한다.
- **산출물:** `reports/real-project-feasibility-YYYY-MM-DD/REPORT.md` 및 값 없는 evidence JSON
- **금지:** 발견한 후보를 검토 없이 "취약점"이라고 쓰지 않는다. 이 결과를 독립 평가 세트(T3)와 합산하지 않는다.

### T7. 독립 평가 실행과 분석 — 담당:

- **목표:** v4 프로토콜에 고정된 **시간 예산 paired-block campaign 전체를 한 번** 수행하고, 모든 후보를 검토한 뒤 고정된 분석 코드로 전략을 비교한다.

- T7이 끝나고 시간이 남을 때만 진행한다. 예: 짧은 smoke 실행에서 timeout이 난 타깃은 뒤로 미루는 규칙 하나. 새로운 평가 세트나 T7과 같은 세트의 별도 부록으로만 보고한다.

## 4. 공통 작업 규칙

- **Git:** commit, push, PR 병합은 변경 내용을 확인한 뒤 한다. PR 병합은 merge commit만 쓴다. 커밋 메시지와 PR 본문에 `Co-Authored-By` 같은 공동 작성자 표기를 넣지 않는다.
- **고정된 자료:** 기존 프로토콜, manifest, contracts, 실행 결과, 판정 파일을 사후 수정하지 않는다. 바꿔야 하면 새 버전 파일을 만든다.
- **개발용과 평가용 분리:** T1 목록에 있는 사례와 프로젝트는 평가 세트에 넣지 않는다. 평가 세트 사례에 zkFuzz를 실행한 순간 그 실행은 기록 대상이 되며, 버리거나 다시 돌리지 않는다.
- **증거 보관:** 원시 후보·R1CS·SYM은 `runs/`(ignored)에 두고, Git에는 경로·해시·판정·시간만 둔다.
- **코드 변경:** `cargo fmt`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test` 통과. 주변 코드 스타일을 따른다.
- **검토:** 별도 검토자가 없으므로 작성과 최종 확인을 miiz가 맡는다. 무언가를 고정하기 전에는 (1) 자동 점검(경로·해시·테스트)을 돌리고, (2) 사전 노출·사후 수정 여부를 점검 목록으로 확인하고, (3) 교차 확인에서 나온 지적과 처리 결과를 문서에 남긴다. 작성자가 곧 검토자라는 한계는 보고서에 그대로 적는다.
- **작업 기록:** 작업을 시작하거나 끝내면 3절의 `담당` 칸과 아래 진행 표를 갱신한다.
