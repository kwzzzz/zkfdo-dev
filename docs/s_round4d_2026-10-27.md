## 2. J·Banyan·실행 순서

J fixture 20개 회로의 제약 최댓값은 **31개**([탐침](../runs/s-round4-2026-10-27/round4d/fixture-probe-v1/summary.json)). 옛 24개와 같은 입력·기대 판정으로 v2.3 CLI와 새 Round4 캐시를 사용하는 [새 하네스](../scripts/s_round4d_j_tests_20261027.py)를 실행해 **24/24 통과**했다([결과](../runs/s-round4-2026-10-27/round4d/j24-run-v2/summary.json)); 엔진 SHA-256 `05649971dc0fb9ece435324d3c779e2c6f148f4dc6efd74ff9fecf5a9690e700`, 감시 기록 214.97초. 기존 테스트 파일은 수정하지 않았다. 일반 `cargo test`에서는 보호된 옛 CLI 경로를 쓰는 이 24개만 제외하고 별도 하네스로 실행했다.

지정 Banyan 사본 SHA-256 `82b91a1c525167667a7ec80dc6555839a5e7af7ca1acad14db81e0607066c683`에는 v2.2 S **고친 24건+버그 108건**의 집계만 있다. 개별 요청·판정·후보·구성 입력·소스가 없어 기본 경로와 view 경로를 실행하지 않았다. [필요 경로 목록](../runs/s-round4-2026-10-27/round4d/banyan-input-audit-v1.json)에 판정 폴더의 정확한 v2.2 join 경로 2개와 132건마다 필요한 `request`, `completed_result`, `candidate`, `base_input`, `component_wrapper`, `entrypoint`, 원본 fragment spec, 전체 `source_closure`를 적었다. 집계 사본만으로는 132개 개별 파일 경로를 알아낼 수 없다. 판정 폴더는 열지 않았다. v2.3 판정의 종류·사유 일치는 **미확인**이며 채택 판단에 쓰지 않는다.

새 실행기는 replay → view → S → 새 후보 J → 엄격층 채점 → 새 L1 리비전만 같은 총시간 W → W 확인을 연결한다. [합성 시험 5건](../scripts/s_round4d_postdeadline_test_20261027.py)은 첫 spec 뒤 디스크 중단, 새 L1 없음→W 없음, 새 L1 있음→해당 리비전 세 seed에 `T/3`, 채점 실패→후단 중단, 호출 뒤 준비비용 영수증을 확인했다. 실제 회로는 돌리지 않았다. S 첫 spec 완료 뒤 그 출력 폴더를 재서 `18 GiB + 남은 spec 수 × 완료 spec 최대 크기`를 다음 spec 전에 확인한다. 내장 감시 30/20/18 GiB, cargo-target 8 GiB, `-j 1`, nice 19를 유지한다.
