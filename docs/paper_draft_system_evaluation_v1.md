## 1. 문제와 시스템 설계

### 1.1 해결하려는 문제

영지식 증명 회로의 under-constrained 결함은 정상 계산과 다른 할당을 제약이 받아들이는 결함이다. zkFuzz는 제약은 만족하지만 정상 계산과 다른 출력을 내거나 정상 계산을 중단시키는 할당을 찾는 TCCT 오라클 기반 퍼저다. 이 연구는 zkFuzz를 바꾸지 않고 외부 분석 엔진으로 사용한다 [문제 정의; Project Identity].

문제는 실제 프로젝트의 entrypoint가 크다는 데 있다. 개발 사례 inference의 production entrypoint는 제약이 196,096개다. 여기에 zkFuzz를 600초 동안 통째로 실행한 세 번은 모두 첫 세대도 끝내지 못했다 [DEV-P2; 결과]. 대상이 커질수록 실행이 어려워지고 프로젝트 단위 분석에서 시간 초과와 오류가 늘어난다는 점은 zkFuzz 논문과 SoK가 이미 보고했다 [LIT-N2; §2.1, DEV-P2; 해석 1]. 이 관측은 그 현상이 우리 개발 사례에서도 나타났다는 확인이며 새 발견이 아니다.

결함이 있는 컴포넌트만 떼어 분석하면 이 한계를 피할 수 있다. 그러나 SoK의 격리 모드는 결함 위치를 아는 사람이 만든 최소 wrapper를 사용했다 [LIT-N2; §2.1]. 실제 감사에서는 결함 위치를 모른다. 따라서 이 연구의 시스템 문제는 다음과 같다. **결함 위치를 쓰지 않고 entrypoint에서 분석 대상을 자동으로 구성하면, 어디까지 적용되고, 같은 자원에서 어떤 검토된 결과를 얻으며, 비용은 얼마인가** [계획; §1, 평가 설계; §1].

자동 구성에는 네 가지 구체적 어려움이 있다.

첫째, Circom 템플릿은 매개변수화되어 있다. 같은 템플릿도 구체 인자에 따라 제약과 의미가 달라진다. 분석 단위는 템플릿 이름이 아니라 구체 인자까지 정해진 인스턴스여야 한다.

둘째, 같은 구성이 매우 많은 호출 위치에서 반복된다. 개발에 노출된 세 프로젝트의 entrypoint 18개에서 wrapper가 만들어지는 호출 위치는 5,240곳이었다. 컴파일 입력이 같은 것끼리 묶으면 63개였다 [ENG-T6A; 결과]. 호출 위치마다 컴파일하면 비용이 커진다. 반대로 단순히 합치면 호출자마다 다른 입력 보장, 곧 호출 맥락을 잃는다.

셋째, 지원하지 않는 구문, 설치되지 않은 외부 의존성, entrypoint의 역할이 적용 범위를 끊는다 [T6A-DIAG; 남은 한계].

넷째, 떼어 낸 컴포넌트의 결과는 해석하기 어렵다. 컴포넌트의 출력은 entrypoint에서 중간값일 수 있다. 따라서 컴포넌트의 TCCT 위반이 곧 entrypoint의 위반은 아니다 [LIT-N2; §3.1]. 호출자가 걸어 둔 입력 검사가 빠진 조각에서는 실제로 일어날 수 없는 반례도 나온다 [DEV-P2; 정답 외 반례 검토]. 또 zkFuzz는 한 프로세스에서 첫 반례를 찾으면 탐색을 끝낸다 [LIT-N2; §4.1]. 그래서 통째 실행과 분할 실행이 내는 후보는 처음부터 수와 수준이 다르다.

### 1.2 entrypoint에서 분석 대상까지

시스템은 Rust CLI zkfDO로 구현되어 있다 [README; Implemented now]. 분석 대상은 다음 순서로 만든다.

1. **entrypoint와 포함 closure.** 프로젝트의 유일한 `component main`이나 사용자가 지정한 entrypoint 파일에서 시작한다. 그 파일에서 도달하는 include만 읽는다. include는 파일의 디렉터리, 프로젝트 루트, 지정한 라이브러리 경로 순서로 해석한다 [T6A-DIAG; 보완한 것].
2. **구체 인스턴스 전개.** 지원하는 구문 부분집합 안에서 compile-time 인자를 평가하며, `main`에서 도달하는 컴포넌트 인스턴스화를 따라간다. 익명 컴포넌트 호출의 전개는 T6a 진단 뒤에 추가됐다(커밋 `d4f0ea5`, 메시지 “Discover anonymous component instances”). T6a 측정은 이 커밋을 재사용 전 기준 버전으로 썼다 [ENG-T6A; 측정 방법]. 함수로 계산하는 템플릿 파라미터, 컴파일 타임 변수 배열, 직접 컴포넌트 배열 초기화 같은 구성은 아직 지원하지 않는다 [T6A-DIAG; 남은 한계, DEV-P2; 발견 사항 3]. 지원하지 않는 경우는 근사한 대상으로 바꾸지 않고 사유와 함께 기록한다 [탐색 설계; Explicitly Unsupported].
3. **호출 위치 기록.** 탐색 결과는 호출 위치마다 항목 하나를 둔다. 각 항목에는 정의 소스, 구체 파라미터 벡터, 부모 템플릿과 그 파라미터, 컴포넌트 이름, 소스 줄을 남긴다 [탐색 설계; Supported Subset]. 여기에 고유 실행 구성을 가리키는 `instance_key`와 직접 부모의 `parent_instance_key`도 남긴다. 보고서의 `root_instance_key`와 함께 이 기록이 호출 그래프를 이룬다. 그래서 모든 상위 호출 경로를 복원할 수 있다 [ENG-T6A; 바꾼 것, 보완].
4. **wrapper 생성.** 구성마다 원본 소스를 include하고 `component main = T(구체 인자)`만 선언한 독립 wrapper를 프로젝트 밖에 만든다. 원본 파일은 수정하지 않는다 [탐색 설계; Wrapper Form].
5. **컴파일 단위.** 재사용 키는 다음을 모두 넣은 SHA-256이다: wrapper 원문, include closure의 파일별 해시와 해석되지 않은 include, 컴파일러 경로와 해시, 컴파일 설정, 제한 시간. 키가 같은 호출 위치는 wrapper 하나와 컴파일 한 번을 공유한다. 각 호출 위치에는 소속 단위와 재사용 여부가 남는다 [ENG-T6A; 바꾼 것]. 컴파일러는 별도 프로세스 그룹에서 실행되며, 제한 시간이 지나면 그룹 전체가 종료된다 [T6A-DIAG; 보완한 것].
6. **실행과 검토.** 준비, 계획, 실행 단계는 타깃별 제한 시간과 전체 예산 아래 zkFuzz를 부르고, 저장된 후보를 실행 기록에 연결한다. 정적 특징과 사전 고정 순서 전략은 보조 분석에 쓴다 [README; Implemented now]. 후보는 공용 검토 엔진이 입력 계약, 고정 R1CS, 사전 속성으로 다시 검사한다 [검토 설계; §1]. 그 결과는 값 없는 증거 기록과 오프라인 집계로 남는다 [AG-01].

### 1.3 구체 인스턴스, 호출 위치, 파라미터 구성, 컴파일 재사용

이 설계에서 네 개념의 역할은 서로 다르다.

**구체 인스턴스**는 소스, 템플릿, 구체 인자가 같은 고유 실행 구성이다 [ENG-T6A; 보완]. 컴파일, 퍼징, 컴포넌트 수준 판정이 모두 이 단위로 이루어진다.

**파라미터 구성**은 인스턴스를 가르는 기준이다. 정상 개발 fixture의 `Bits(8)`, `Bits(32)`, `Bits(256)`처럼 파라미터가 다르면 별도 대상이다. 산술 통제는 `Step(2)`와 `Step(3)`의 파라미터가 계산 결과를 실제로 바꾸도록 만들었다 [NE-01; 실행 대상과 자동 구성]. 파라미터는 비용에도 영향을 준다. P2에서 제약 3,183개의 `RSAPad(121, 17)` 조각은 30초 안에 첫 세대를 끝내지 못했다. 반면 제약 145,656개의 `FpPow65537Mod(121, 17)` 조각은 같은 시간에 40~70세대를 돌았다 [DEV-P2; 결과]. 조각의 크기만으로 실행 비용을 예측할 수 없다는 뜻이다.

**호출 위치**는 같은 인스턴스가 호출 그래프의 어디에서 쓰였는지를 가리킨다. 호출자가 보장하는 입력 범위와 출력의 쓰임이 여기에 달려 있다. 같은 인스턴스라도 호출자마다 전제가 다를 수 있다. 그래서 입력 계약, 맥락 판정, 프로젝트 수준 판정은 호출 위치별로 한다 [ENG-T6A; 바꾼 것, 평가 설계; §4].

**컴파일 재사용**은 호출 위치를 줄이지 않고 컴파일 작업만 줄이는 공학 장치다. 재사용 키가 같다는 것은 컴파일 입력이 같다는 뜻이다. 서로 다른 호출 맥락이 의미상 같다는 뜻이 아니다. 그러므로 재사용한 artifact를 쓰더라도 정상 경계값과 후보 판정은 원래 호출 위치에 연결해야 한다. NE-02는 작은 통제에서 이를 확인했다. artifact 하나를 공유한 세 호출 위치 `main.a`, `main.b`, `main.m.inner`는 서로 다른 정상 경계 입력을 받았고, 각자 원본과 일치했다 [NE-01; ‘실행 대상과 자동 구성’, ‘조건, 계산과 대응 확인’]. 한 번 컴파일해 여러 진입점에 재사용하는 생각은 일반 소프트웨어의 compositional fuzzing에 선례가 있다 [LIT-N2; §2.1]. 따라서 이를 기법의 새로움으로 내세우지 않는다.

### 1.4 결과 해석의 네 층

자동 분해의 결과를 성공 하나로 합치면 서로 다른 주장이 섞인다. 이 연구는 네 층을 구분한다 [계획; §3, 문제 정의; Meaning of Review Outcomes, LIT-N2; §3].

**정상 대응**은 결함 후보와 무관한 층이다. 자동 생성한 wrapper가 정상 입력에서, 원본 인스턴스의 해당 호출 위치 경계와 같은 계산을 하는지 본다. wrapper의 결과를 원본 호출 위치로 되돌려 해석하려면 먼저 이 조건이 필요하다. 그러나 정해진 정상 입력에서 일치한다고 해서, 악의적 할당까지 포함한 의미 동등성이 보이지는 않는다. 최적화로 신호가 사라지거나 배열 인터페이스가 쓰이면 대응 규칙 자체가 필요하다 [LIT-N2; §3.2, 체크포인트; §2].

**후보 검토**는 zkFuzz가 낸 특정 후보를 다시 계산하는 단계다. 후보가 실행 기록에 연결되는지, 사전에 선언한 입력 전제를 만족하는지, 고정한 원본 컴포넌트 R1CS 전체를 만족하는지 본다. 그리고 사전에 정한 속성, 곧 정상 계산과 다른 출력이나 계산 중단을 위반하는지 확인한다. 모두 통과하면 컴포넌트 확인이다. 이 재검사는 검토 엔진이 자동으로 수행한다. 그러나 입력 계약과 속성 predicate는 사람이 실행 전에 써야 한다 [검토 설계; §1, LIT-N2; §2.2·§3.5]. zkFuzz의 `NOT SAFE` 출력이나 정답 위치와의 일치는 이 층의 증거가 아니다 [LIT-N2; §3.9].

**원인 귀속**은 확인된 후보를 고유 원인에 연결하는 층이다. 같은 원인이 여러 호출 위치에서, 또는 그 원인을 포함한 상위 조각에서 반복 관측되면 한 번만 센다. 위치가 같다는 사실은 보조 정보다 [계획; §3, LIT-N2; §3.6]. 두 방식을 같은 수준에서 비교하려면 통째 실행의 후보도 같은 절차로 컴포넌트 원인에 연결해야 한다. 그 절차는 **계획·미고정**이다.

**프로젝트 의미 확인**은 별도 근거가 필요한 층이다. 사전에 정한 프로젝트 속성이 원본 프로젝트의 입력 전제, 제약, 호출 맥락에서 실제로 위반됨을 보여야 한다. 고정 entrypoint 제약 전체를 다시 확인한 entrypoint TCCT 확인은 그 사이에 있는 별도 층이다. 이를 컴포넌트 원인 수에 더하거나 프로젝트 속성 위반으로 자동 승격하지 않는다 [문제 정의; Meaning of Review Outcomes, N3 결정; §3].

**맥락 후보배제**는 이 네 층과 별개의 축이다. 분해로 잃은 호출자 제약 때문에 특정 후보가 그 호출 위치에서 실현될 수 없음을 보이는 신뢰성 과제다. 컴파일된 entrypoint 제약의 부분집합에서 어떤 경계값이 불가능하면, 전체 제약에서도 불가능하다. 따라서 배제는 국소적으로 건전하게 할 수 있다. 반면 양립은 국소적으로 확정할 수 없다 [LIT-N2; §3.2]. 특정 후보의 배제는 원인 전체의 배제나 경고 삭제가 아니다. 결론을 얻지 못하면 미판정으로 남긴다 [평가 설계; §5].

## 2. 평가 방법

### 2.1 평가 질문과 세 축

평가는 세 질문에 답하도록 설계했다 [평가 설계; §1].

- **RQ1(주 질문):** 실제 entrypoint에서 자동 구성한 분석은 어느 범위에 적용되는가? 같은 entrypoint를 통째로 분석할 때와 비교해, 같은 자원과 시간에서 검토된 고유 원인과 총비용은 어떻게 다른가?
- **맥락 판정:** 분해 후보 가운데 호출 맥락상 배제, 미판정, 별도 확인으로 나뉘는 결과는 얼마나 되는가? 그 판정의 비용과 보장 범위는 무엇인가?
- **RQ2(보조):** 사전에 고정한 단순 순서들은 최초 확인 대상 시간과 예산 내 결과에 어떤 차이를 만드는가?

순위의 우위나 새 취약점 발견은 완료 조건이 아니다. 이익이 없거나 적용 사례가 적으면 그대로 보고한다.

평가는 세 축으로 나누며, 축끼리 섞지 않는다.

**적용성.** 사전에 고정한 전체 대상 모수에서 탐색, 준비, 실행, 검토의 각 단계를 통과한 비율을 본다. 단계별 미지원, 실패, 미확인 사유도 함께 보고한다. 사람이 보완해 성공한 경우는 자동 성공과 따로 센다 [평가 설계; §4]. P2의 zk-email이 그 예다. 자동 준비가 조각 네 개를 모두 제외해 조각마다 zkFuzz를 직접 호출했으므로, 자동 파이프라인의 적용 성공으로 세지 않는다 [DEV-P2; 설정, 계획; §2].

**같은 자원의 검토된 성과.** 양쪽 방식에 같은 검토 수준을 적용한다. 주 비교 수준은 사전 정의한 일반 TCCT 기준의 컴포넌트 확인과 원인 귀속으로 권고됐다. 계약 속성과 프로젝트 의미 속성은 보조층이다 [N3 결정; §3]. 실행 단위마다 세 가지를 함께 보고한다.

- 하나 이상의 확인이 있는지 여부.
- 최초 확인 대상의 생성 시각, 또는 그것이 검증되지 않으면 연결된 실행의 완료시각 상한.
- 검토된 고유 원인 수.

확인 여부는 같은 쌍대 분모에서 비교한다. 분할만 확인한 구제 단위 r과 통째만 확인한 손실 단위 l을 보고하고, l ≥ r이면 이 이진 지표의 관측 순증가가 없다고 본다. 이 판단이 시간, 원인 수, 비용의 이득까지 부정하지는 않는다 [N3 결정; §6]. entrypoint TCCT 확인과 검토·투영·귀속 미판정은 수, 분모, 사유와 함께 따로 보고하며 원인 수로 환산하지 않는다.

**비용.** 준비, 컴파일과 캐시, 분석 실행, 맥락 판정, 수동 검토를 나누고 총비용도 함께 보인다. 준비된 상태에서의 비교와 처음부터 드는 비용을 혼동하지 않는다. 준비·검토 비용을 빼야만 생기는 이득은 ‘준비된 상태의 이득’으로 제한한다 [평가 설계; §3, N3 결정; §6]. 지금까지의 통제 실행은 자동 검토 시간은 기록했지만 사람의 검토 시간은 계측하지 않았다 [LEG-V1; 비용, LEG-V2; Execution integrity and costs, LEG-V3].

### 2.2 개발 관측과 개발에서 분리된 평가

자료는 세 층으로 나눈다 [N3 결정; §5].

- **D(개발):** 방법, 규칙, 선정을 조정하는 데 쓴 자료.
- **S(개발과 분리):** 그런 사용이 없다는 이력 근거를 갖춘 자료.
- **Q(불명):** 사용 관계를 확인하지 못한 자료.

노출은 개발 사용, 실행, 준비와 컴파일, 소스와 패치 열람, 프로젝트 열람, 메타데이터, 공개 결과 지식으로 나눠 기록한다. 공개 벤치마크의 Circom 70건은 모두 메타데이터와 공개 결과에 노출됐다. 그래서 S층이라도 ‘한 번도 노출되지 않은 자료’를 뜻하지 않는다. 기존 제외목록에 없는 5건과 저장소 3개도 미노출 세트로 복원할 수 없다 [DATA-N1; §6].

이 초안의 예비 결과는 모두 D층의 개발 관측이며, 개발과 분리된 평가 결과는 아직 없다. S층에서 양쪽 방식이 모두 준비된 단위가 없으면 주장을 적용성 분석으로 줄인다. 그런 단위가 하나뿐이거나 계열 독립성이 불명하면 사례연구나 기술 비교로 줄인다 [N3 결정; §6]. 부족분을 메우려고 개발 사례를 독립 평가 증거로 다시 쓰지 않는다 [문제 정의; Contribution Hypotheses and Evidence Needed].

### 2.3 독립 단위와 반복

실행 단위는 프로젝트, 재현 가능한 소스 버전, entrypoint, 실행을 바꾸는 설정의 조합으로 만든다. 라벨, 검토 predicate, 반복, 방식의 차이만으로는 새 단위의 예산을 주지 않는다 [평가 설계; §2]. seed 반복은 변동성을 재는 것이지 독립 사례가 아니다. 같은 프로젝트나 계열의 여러 entrypoint와 결함은 군집으로 다룬다.

사례 수, 실행 단위 수, 고유 원인 수는 서로 다른 값이다. 공개 자료의 original 56행을 (프로젝트, 커밋, original entrypoint)로 묶으면 잠재 묶음 36개가 나온다. 그러나 설정과 의존성을 확인하지 않았으므로 확정 실행 단위 수가 아니다 [DATA-N1; §4]. 같은 원인을 반복 관측한 후보는 한 원인으로 센다. 예를 들어 v1.1의 후보 36개는 모두 같은 Subtract 원인의 반복 관측이다 [LEG-V1; 결론].

자료가 적을 것으로 보여, 검정보다는 단위별 쌍대 결과표, 개별 결과, 효과 크기와 불확실성 중심으로 보고하라는 권고를 받았다 [LIT-N2; §4.7]. 통계 절차와 seed 집계 규칙(어느 seed에서든, 과반, 모두)은 **계획·미고정**이다 [LIT-N2; §4.6].

### 2.4 실패·미지원·미판정의 처리

준비 실패, 미지원, 시간 초과, 미판정은 모수에서 지우지 않고 사유와 함께 남긴다 [계획; §4, 평가 설계; §2]. 각각의 의미는 다음과 같다.

- 시간 초과는 회로가 안전하다는 뜻이 아니다.
- 준비 실패는 탐지 실패가 아니다.
- 지원 범위 밖은 탐지 음성이 아니다.
- 검토가 끝났지만 판정이 미해결인 후보도 음성이 아니다.

앞선 후보의 검토가 완결되지 않으면 ‘최초’ 확인 시각을 확정하지 않는다. 대신 현재 확인된 후보의 시각과 검토되지 않은 선행 후보를 함께 보고한다 [N3 결정; §3]. 같은 설정에서 찾지 못한 결함은 경험적 미탐으로 기록한다. 오라클의 원리적 한계는 별도 논증이 있을 때만 주장한다 [계획; §2]. 오라클 적합성에 따른 조건부 분석의 부분집합은 실행 결과를 보고 정하지 않는다. 실행 전에 결함 메타데이터로 정해야 한다 [LIT-N2; §4.5].

평가 자료를 처리하는 기록·집계 경로도 이 규칙을 따르도록 수정했다. 실행 실패나 후보 참조 누락은 완결된 ‘후보 없음’이 되지 않는다. 기록 사이에 판정이 상충하면 양성 보고의 존재와 미해결 상태를 함께 남긴다 [AG-01; 수정 기록 §6]. 이는 자료 처리의 신뢰성을 위한 장치이며 평가 결과가 아니다.

### 2.5 첫 반례 종료와 자원의 공정성

zkFuzz는 위반을 찾으면 그 프로세스의 탐색을 끝낸다 [LIT-N2; §4.1]. 통째 실행은 실행당 반례가 최대 하나이고, 분할 실행은 조각마다 하나다. 그래서 두 방식의 탐지 능력이 같아도, 같은 예산에서의 고유 원인 수는 분할에 유리할 수 있다. 따라서 원인 수는 종료와 배분 정책을 포함한 파이프라인 수율로만 비교하고, 순수한 오라클 능력의 우위로 해석하지 않는다 [평가 설계; §4].

종료 정책은 설계 A를 연구 설계로 채택했다. 실행 단위의 공통 총할당 안에서 반복 시도하고 잔여 예산을 쓰되, 결과 종류나 사후 판정에 따라 정책을 바꾸지 않는 방식이다. 통째 한 번 호출과 조각별 한 번 호출을 비교하는 native-stop 비교(B)는 명시적 대안으로 남겼다 [N3 채택; §2, N3 결정; §3]. A의 실행기는 아직 구현되지 않았다.

할당을 소진했다고 해서 실제로 쓴 CPU, 벽시계 시간, 메모리, 대기 시간이 같아지지는 않는다. 그래서 할당과 실제 사용량을 따로 기록한다. 동시 실행 수와 경쟁 작업도 결과를 바꿀 수 있다. P2는 사례와 방식의 조합 8개를 한 기계에서 동시에 실행했다 [DEV-P2; 설정]. 정식 평가의 동시성과 자원 상한은 **계획·미고정**이다.

### 2.6 아직 고정하지 않은 사항

아래는 모두 **계획·미고정**이며 N5에서 실행 전에 고정한다 [계획; §5, 평가 설계; §6, N3 결정; §5]. 이 초안은 이 값들을 정하지 않는다.

- 초기 대상 목록, 출처와 버전, 노출층 배정, 포함·제외 규칙, 부재와 불명 처리.
- 실행 단위 생성, 중복 제거, 사례 대응 규칙. 준비 실패, 미지원, 재시도, 허용 패치의 처리. root와 child, production과 test entrypoint의 처리. 조각 선택 규칙. P2의 ‘프로젝트 내부 인스턴스만 조각’은 파일럿 설정이었다.
- RQ1 대표 순서와 보조 전략 수, 총예산과 타깃별 제한, seed 수와 집계, 실행 순서와 동시성, 자원 상한, 캐시와 비용의 포함 범위. 이전 파일럿의 600초, 30초, seed 3개는 자동으로 상속하지 않는다.
- 종료, 잔여 예산, 재시작, 환경 장애 재시도 규칙.
- 비교 수준, 일반 속성과 계약 속성, 입력 전제와 abort형의 처리, 원인 귀속, 알려진 원인과 추가 원인의 대칭 규칙, 검토 순서·상한·표본, 재주석의 우선순위와 층별 원인 귀속, 맥락 후보배제의 판정 범위.

## 3. 현재 예비 결과

이 절의 결과는 모두 개발 관측이다. 개발과 분리된 평가가 아니며, 새 결함 발견을 비교한 본표는 아직 없다 [근거 색인; 논문 절별 사용 위치].

### 3.1 자동 구성 이후의 정상 계산과 경계 대응 (NE-01)

정상 실행 실험은 제한된 기능 검증이다. 자동 구성한 wrapper가 실제 컴파일러와 정상 계산 경로에서 원본 인스턴스와 같은 경계를 재현하는지 확인했다 [NE-01; 체크포인트 §2].

대상은 결함 없는 정상 산술 fixture 두 개다.

- 기존 discovery fixture `ProjectMain(64)`: child 호출 위치 7곳, wrapper 구성 7개. 파라미터가 다른 `Bits(8/32/256)` 등을 포함하며, 공유할 수 있는 동일 구성은 없다.
- 작은 산술 통제 `Root → Step(2), Step(3), Branch(5)`: 호출 위치 5곳, 구성 3개. `Step(2)`가 `main.a`, `main.b`, `main.m.inner` 세 곳에서 서로 다른 정상 입력을 받는다.

두 대상 모두 기존 `targets --no-validate` 경로가 대상과 wrapper를 자동 생성했다. 미지원, 누락, 수동 wrapper 대체는 없었다 [NE-01; 실행 대상과 자동 구성].

원본과 wrapper는 Circom 2.2.3에서 `--O0 --r1cs --wasm --sym --inspect --prime bn128`로 실제 컴파일했다. 대상마다 정상 입력 3개를 고정했다. Circom이 생성한 WASM으로 계산한 모든 witness는 `snarkjs wtns check`로 검사했다. 경계 비교는 두 단계로 했다. 먼저 discovery의 `parent_instance_key`, `instance_key`, 컴포넌트 이름으로 호출 경로를 펼쳤다. 그다음 원본 `.sym`의 해당 `in/out`을 wrapper의 `main.in/out`과 대조했다. wrapper 입력은 확인된 원본 경계 입력에서 가져왔다. 소실된 witness index, 없는 신호, 고아·순환 호출 경로는 추정하거나 0으로 채우지 않고 실패로 처리했다 [NE-01; ‘조건, 계산과 대응 확인’].

| 대상 | 호출 위치 / 구성 | 원본 포함 컴파일, 미재사용 → 재사용 (방식별 2회 합계) | 정상 경계 일치 |
|---|---:|---:|---:|
| 기존 `ProjectMain(64)` fixture | 7 / 7 | 16 → 16 | 84/84 |
| 반복·상이 파라미터 산술 통제 | 5 / 3 | 12 → 8 | 60/60 |

8개 조건 실행에서 원본과 wrapper의 실제 컴파일 52회가 모두 성공했다. 실패, 시간 초과, 프로세스 시작 실패는 없었다. 원본 정상 계산 24회, wrapper 정상 계산과 경계 비교 144회, 생성 witness의 R1CS 검사 168회가 모두 통과했다 [NE-01; 첫 표와 본문, 체크포인트 §2].

이 수치는 원본 프로세스 기록 568개와 조건별 결과를 직접 대조해 얻었다. 568개의 내역은 버전 조회 4, discovery 8, 컴파일 52, 정상 계산 168, 제약 검사 168, witness export 168이다. 당시 오류가 알려진 오프라인 집계기는 쓰지 않았다 [NE-01; 실제 비용과 원본 도구 기록].

**52, 168, 144는 독립 사례 수가 아니다.** 독립 fixture 2개에서 같은 정상 입력 세 개를 방식별로 두 번씩 반복한 검사의 횟수다. 이 결과가 보이는 범위는 O0, bn128, scalar `in/out`, 대상당 정상 입력 3개다. 그 범위에서 자동 구성, 실제 컴파일, 정상 계산, 전체 R1CS 검사, 경계 비교가 연결됐다. 배열 인터페이스, 최적화된 컴파일, 임의 입력, 다른 프로젝트에서의 대응은 보이지 않는다. wrapper가 원본 의미를 일반적으로 보존한다는 것도 보이지 않는다 [체크포인트; §2].

### 3.2 반복 구성의 컴파일 재사용 (NE-02)

같은 실험에서 컴파일 정책 두 가지를 비교했다. 현행 discovery와 wrapper 생성은 그대로 두고, artifact를 호출 위치마다 컴파일하는 조건과 완전한 캐시 키마다 한 번 컴파일하는 조건을 맞세웠다. 캐시 키는 wrapper 본문 해시, include 의존성 전체의 경로와 해시, 컴파일러 경로와 해시, 컴파일 플래그, 라이브러리 경로, 제한 시간이다. 각 조건은 새 application cache와 새 출력 디렉터리를 썼다. 대상마다 1회차는 미재사용→재사용, 2회차는 재사용→미재사용 순으로 실행했다 [NE-02; ‘조건, 계산과 대응 확인’].

산술 통제의 원본 포함 컴파일은 방식별 2회 합계 12회에서 8회로 33.3% 줄었다. 원본을 빼고 wrapper 컴파일만 보면 10회에서 6회로 40% 줄었으므로, 분모를 함께 적어야 한다. 기존 fixture는 공유할 동일 구성이 없어 16→16이며, 대조 결과 역할을 한다. 재사용 조건에서도 산술 통제의 경계 비교는 실행마다 15회(입력 3개 × 호출 위치 5곳) 모두 일치했다 [NE-01; 실제 비용과 원본 도구 기록]. 즉 artifact 하나를 공유하면서도 호출 위치와 서로 다른 정상 경계 입력이 유지됐다 [체크포인트; §2].

이 비교는 artifact 컴파일 정책의 통제 관측이다. 제품의 과거·현재 버전 전체, 기존 `targets --inspect` 경로의 전후, 통째·분할 퍼징의 성능을 비교한 것이 아니다.

### 3.3 준비 비용과 측정 구간 전체 비용 (NE-03)

준비 시간은 벽시계 시간으로, 자동 탐색과 wrapper 생성부터 원본과 필요한 wrapper artifact의 컴파일, 출처 해시 기록까지를 포함한다. 정상 계산, 제약 검사, witness export, 경계 비교는 별도 구간으로 쟀다 [NE-01; 실제 비용과 원본 도구 기록]. 아래 표의 값은 원문의 조건별 값에서 다시 계산한 방식별 평균이다. 원문 보고서의 대표 평균(산술 통제 준비 0.130137→0.078667초)과는 반올림 자리만 다르다 [NE-03; 체크포인트 §3].

| 대상·구간 | 미재사용 평균(초) | 재사용 평균(초) | 차이(초) |
|---|---:|---:|---:|
| 산술 통제 준비 | 0.1301375 | 0.0786675 | −0.0514700 |
| 산술 통제 정상 계산·검증 | 7.5618635 | 7.6994215 | +0.1375580 |
| 산술 통제 두 구간 합계 | 7.6920010 | 7.7780890 | +0.0860880 |
| 기존 fixture 준비 | 0.1574185 | 0.1508315 | −0.0065870 |
| 기존 fixture 두 구간 합계 | 10.5873600 | 10.3733900 | −0.2139700 |

산술 통제의 준비 시간은 평균 약 51.47밀리초, **약 39.55% 감소**했다. 그러나 준비와 정상 검증을 합한 측정 구간의 합계는 **7.692001초에서 7.778089초로** 약 1.12% 늘었다. 기존 fixture의 합계는 약 2.02% 줄었다. 두 fixture 모두 정상 검증 비용이 준비 비용보다 훨씬 크다. 그래서 준비 단계의 감소가 측정 구간 전체의 감소로 이어지지 않았다.

방식별 반복은 두 번뿐이다. OS 파일 캐시를 비우지 않았고, 공유 개발 머신의 백그라운드 활동도 모두 통제하지 않았다. 따라서 어느 차이도 전체 처리시간의 우위나 열위를 입증하지 않는다 [체크포인트; §3]. 이 합계에는 소스 snapshot 생성, 개발 도구 빌드, 버전 조회, 보고 비용이 들어 있지 않다. CPU와 메모리도 측정하지 않았다. 그러므로 이 값은 연구 전체의 비용이나 퍼징 총비용이 아니라 ‘측정한 준비+정상 검증 구간의 합계’다.

### 3.4 기존 개발 관측

#### 컴파일 재사용의 규모 (ENG-T6A)

T6a는 개발에 이미 노출된 세 프로젝트(zk-email, Inference, Moonsong)의 `component main` 파일 18개를 측정했다. circom 2.2.3, 컴파일 제한 600초를 썼다. 결과는 다음과 같다 [ENG-T6A; 결과].

- 호출 위치 5,240곳의 컴파일이 63회로 줄었다.
- 컴파일 시간 합계는 159.8초에서 4.0초로 줄었다.
- 전체 소요는 164.2초에서 14.1초로 줄었다.
- 호출 위치별 컴파일 결과는 전후가 같았다. 성공 5,234곳, 불일치 0, 시간 초과 0이다.

해석에는 한계가 있다. 측정한 entrypoint 대부분은 테스트용 회로였다. 재사용 버전을 먼저 실행했으므로 비교 버전은 데워진 파일 캐시의 이점을 받았다. 절감은 컴파일 작업에 한정되며, 퍼징할 독립 대상의 수나 퍼징 비용과는 별개다 [ENG-T6A; 해석과 한계]. NE-02와는 실험과 대상이 다르므로 두 수치를 합산하지 않는다. 탐지 성능이나 기법이 새롭다는 근거로도 쓰지 않는다 [근거 색인; ENG-T6A 행].

#### 탐색 적용성의 한계 (T6A-DIAG, 근거 색인 외 기존 보고서)

09-24 진단은 같은 노출 프로젝트 6개의 `main` 191개를 하나씩 탐색했다. 결과는 다음과 같았다 [T6A-DIAG; 보완 후 진단].

- 문제 없이 대상을 찾은 entrypoint: 6개
- 일부 미지원 구문이 있는 entrypoint: 78개
- 대상이 0개인 entrypoint: 107개

주된 원인은 익명 컴포넌트 호출, 컴파일 타임 변수 배열, 직접 컴포넌트 배열 초기화, 함수로 계산하는 파라미터와 반복 경계였다. 해석되지 않은 include는 모두 설치되지 않은 npm 의존성이었다. 문제 없이 대상을 찾은 6개는 모두 테스트용 회로였다 [T6A-DIAG; 남은 한계].

이후 익명 컴포넌트 탐색이 추가됐으므로 위 수치는 현재 적용률이 아니다. 같은 보고서의 정정에 따르면 표의 ‘발견 타깃’은 호출 위치 수다. 프로젝트 전체의 고유 대상은 15~95개였다 [T6A-DIAG; 정정 (2026-09-26)]. 현재 지원 범위의 적용률은 개발 밖 자료에서 아직 측정하지 않았다.

#### 통째 실행과 분할 실행의 개발 파일럿 (DEV-P2)

P2는 개발에 쓴 알려진 결함 두 사례에서 두 방식을 비교했다 [DEV-P2; 설정].

- **통째:** entrypoint 전체에 zkFuzz를 600초 동안 한 번 실행한다.
- **분할:** 프로젝트 내부 소스의 고유 인스턴스를 조각으로 만들어, 조각당 30초, 전체 600초로 차례로 실행한다. 순서는 random, small-first, path-order 세 가지였다.

zkFuzz seed는 3개를 썼다.

**inference.** production entrypoint이며 제약 196,096개, 조각 21개다. 통째 실행은 세 번 모두 600초 안에 첫 세대를 끝내지 못했다. 분할 실행은 아홉 번 모두 정답 결함 위치인 `Subtract()`와 `Clamp(40)` 조각에서 반례를 냈고, 21개 조각을 203~206초에 끝냈다. 첫 정답 위치 반례는 small-first와 path-order에서 1.4~1.6초, random에서 60초, 198초, 203초였다 [DEV-P2; 결과].

이 관측은 RQ1의 동기이며 검토된 성과가 아니다. 분할의 성공 기준은 정답 템플릿 조각에서 반례가 나왔는지, 곧 위치 일치였다. 그 반례들은 따로 검토하지 않았다. 현재 계획은 위치 일치만으로 성과를 세지 않는다 [계획; §2·§3].

정답 외 조각 8개의 반례도 소스와 호출 관계로만 분류했다. 검토 엔진의 판정이 아니다 [DEV-P2; 정답 외 반례 검토].

- `IntDiv` 세 조각: `out`을 묶는 제약이 없는 쪽으로 분류했다.
- `LessThan` 넘침 검사를 위반한 다섯 조각: 경로별 정밀 검토 전에 실제 회로에서도 일어날 수 있는 쪽으로 분류했다.

통째 실행에는 후보가 없었다. 따라서 두 방식의 후보를 같은 수준에서 검토하는 비교 경로도 이 파일럿에서는 확인되지 않았다 [N3 결정; §2].

**zk-email.** entrypoint는 `rsa-test.circom`이며 제약 153,137개, 조각 4개다. 두 방식 모두 정답 `FpMul(121, 17)`을 찾지 못했다. 정답 조각은 아홉 번 모두 30초 안에 기본 탐색량 500세대를 끝내고도 반례를 내지 않았다. 따라서 이 설정의 경험적 미탐이다.

모든 분할 실행에서 `BigLessThan(121, 17)` 조각은 첫 세대에 반례를 냈다. 이 템플릿은 각 limb가 n비트 안에 든다고 가정한다. 실제 호출자 `RSAVerifier65537`은 `signature`를 `Num2Bits(n)`로, `modulus`는 `RSAPad` 안의 `Num2Bits(n)`로 먼저 검사한다. 떼어 낸 조각에는 이 검사가 없으므로, 이 반례는 맥락에서 실현될 수 없는 것으로 수동 분류됐다 [DEV-P2; 결과, 정답 외 반례 검토]. 이 수동 논증은 원인 수준의 판단이다. 자동 맥락 판정의 검증을 대신하지 않는다 [LIT-N2; §3.3].

이 entrypoint에는 두 가지 제약이 더 있다. 경로상 테스트 회로일 수 있지만 production 여부를 확인하지 않았다 [LIT-N2; §2.2]. 또 자동 준비가 외부 의존성 식별과 미지원 파라미터·배열 때문에 조각 네 개를 모두 제외해, 조각마다 zkFuzz를 직접 호출했다 [DEV-P2; 발견 사항 3]. 개발에 노출된 결함 22건 가운데 이번에 비교할 수 있었던 것은 2건이었다 [DEV-P2; 발견 사항 2].

#### 알려진 원인의 통제 검토 기록 (LEG-V1·V2·V3)

세 통제 실행은 사람이 고른 취약본·수정본 컴포넌트 쌍으로 순서 전략을 비교한 과거 캠페인이다. 자동 분해의 결과가 아니다. 프로토콜, 대상, 반복 수가 서로 달라 하나의 성능 분자로 합치지 않는다 [현황; 검토된 실행 결과]. 이 기록이 보여 주는 것은 후보 검토 층의 작동이다.

- **v1.1:** 12 paired block, 36개 전략 실행의 후보 36개가 모두 네 단계를 통과했다: 실행 기록 연결, 입력 전제, 고정 R1CS 전체 만족, 사전 속성 `c = a - b mod p` 위반. 그러나 모두 같은 Subtract 원인의 반복 관측이므로 고유 원인은 1건이다 [LEG-V1; 결론, 후보 검토].
- **v2:** Banyan 원인이 같은 방식으로 확인됐다. Tangle 원인은 재발견되지 않았다 [LEG-V2; Result].
- **v3:** 단일 파일럿에서 Decoder 원인이 확인됐다. BigLessThan은 취약본·수정본 모두 30초 제한에서 시간 초과로 끝났다. 74.156초는 앞선 두 시간 초과를 포함한 scheduler 완료시각의 상한이며, 정확한 생성 시각이 아니다 [LEG-V3].

세 실행 모두 프로젝트 수준 확인은 0건이다. 사람의 검토 시간은 계측하지 않았다. 순서 전략에 따른 시간 차이는 사전 고정된 대상 순서의 효과로 해석됐다 [LEG-V1; 전략 결과, LEG-V2; Result]. 순위가 일반적으로 우위라는 근거가 아니다.

#### 공개 벤치마크의 분모와 노출 (DATA-N1)

SoK 공개 산출물의 Circom 사례는 70건이고, 그중 original entrypoint 결과가 있는 것은 56건이다. 공통 56건에서 zkFuzz의 공개 정답 일치 라벨은 다음과 같다 [DATA-N1; §3].

- 격리만 TP: 10건
- 프로젝트만 TP: 1건
- 양쪽 TP: 3건
- 양쪽 비TP: 42건

42건에는 오류, 시간 초과, 판정 결측이 섞여 있다. 그래서 이를 확정 미탐이나 안전한 회로로 부를 수 없다.

이 격차는 자동 분해의 동기가 되지만, 우리 방법의 성공을 보장하지 않는다 [근거 색인; 논문 절별 사용 위치]. SoK의 과거 수치는 같은 환경에서 잰 기준선도 아니다. 실제 실행 제한도 미해결이다. 논문과 README는 600초, 공개 JSON은 300초, 집계 코드는 600초로 서로 맞지 않는다 [DATA-N1; §8].

### 3.5 평가 자료 처리의 구현 검증 (AG-01)

독립 검증은 값 없는 합성 JSON으로, 오프라인 기록·집계 경로의 과대 집계와 완결성 오류 일곱 가지(N1–N7)를 재현했다 [AG-01; 독립 검증 §3]. 주요 사례는 다음과 같다.

- 실행 실패나 후보 참조 누락이 완결된 ‘후보 없음’이 된다.
- 기록 사이의 상충 판정이 숨겨진다.
- 겹치는 등록 범위 때문에 같은 원인을 두 번 센다.
- 도구별 검사를 일반 TCCT 원인으로 승격한다.
- 층을 넘는 귀속 충돌을 놓친다.

수정은 이 경우들을 보수적으로 처리하도록 바꾸었고, 회귀 테스트 12개(집계 7, 기록 5)를 추가했다. 수정 기록에 따르면 새 12개는 수정 전 snapshot에서 모두 실패하고 수정 후 통과했다. 기존 기록·집계 테스트 61개는 전후 모두 통과했다. 수정 작업이 보고한 최신 검사는 fmt와 지정 clippy 통과, Rust 테스트 297개 통과·0 실패·22 ignored다 [AG-01; 수정 기록 §6]. 이 297은 정상 실행 당시의 Rust 285개·Python 4개와 검사 시점이 다르므로 합산하지 않는다 [체크포인트; §4].

이 결과는 평가 자료를 잘못 승격하지 않도록 하는 구현 검증이다. 결함 탐지 실험이 아니며, 이 연구의 주 기여도 아니다. 기록·집계 경로는 입력이 보고한 주장을 모을 뿐 원인의 의미를 인증하지 않는다. 수정 전의 독립 검증을 수정 후 구현 전체의 독립 인증으로 쓰지도 않는다 [체크포인트; §4]. 다음 정책은 N5에서 정하도록 남겼다: 재주석의 우선순위, 층별 원인 귀속, 실패 시도의 재시도·제외, 등록 범위 사이의 관계.

### 3.6 정상 호환성 실험 (NC-01): 결과 대기

NC-01은 정상 대응이 O1과 작은 배열 인터페이스에서도 성립하는지, 성립하지 않으면 어디서 왜 지원 범위가 끊기는지를 확인하는 실험이다 [NC 인계; 이번 한 질문]. 별도 작업으로 진행 중이며 **결과 대기**다. 이 초안은 그 결과를 사용하지 않는다.

## 4. 선행 연구와 한계

### 4.1 검토한 문헌의 범위

선행 연구는 N2 방법론 검토가 기록한 범위에서만 서술한다 [LIT-N2; §1].

**우선 대조 문헌 8편.**

- 본문을 읽은 것: zkFuzz, SoK, Towards Fuzzing ZKP Circuits, Wildfire. SoK는 zkVM 형식 검증 절을 훑어보는 데 그쳤다. Wildfire는 표와 그림의 수치 셀을 판독하지 못했다.
- 일부 절만 정독한 것: Picus/QED², CCC-Check, ZEQUAL.
- 원문에 접근하지 못한 것: CIVER. 공식 저장소 README와 다른 논문의 2차 서술만 읽었다.

**보조 문헌.** FuzzSlice는 앞부분, zkCraft는 초록과 도입만 읽었다. LIEZZ와 퍼징 일정·대상 선택에 관한 연구 두 편은 초록만 읽었다.

2026-10-01에 웹 검색을 두 번 했지만 위 목록 밖에서 직접 대응하는 연구를 찾지 못했다. 그러나 검색이 망라적이지 않으므로 이를 선행이 없다는 근거로 쓰지 않는다. 아래 서술은 N2가 원문에서 확인해 기록한 내용이다. N2의 절을 근거로 달며, 원문을 다시 대조하지 않은 새 인용이나 절 번호는 만들지 않는다.

### 4.2 선행이 이미 다룬 것

분해, 모듈식 분석, 컴파일 재사용, 맥락 실현 가능성은 모두 아이디어나 다른 맥락의 구현으로 선행이 있다 [LIT-N2; §2.1].

- **zkFuzz:** TCCT 오라클을 제시했다. 큰 대상을 잘라 부분 실행하는 아이디어를 한 문장으로 언급했다. 첫 위반에서 탐색을 끝낸다. 오탐이 없다는 결과는 그 benchmark 단위와 TCCT 정의에서의 결과다. 따라서 분해 조각의 결과로는 이어지지 않는다.
- **SoK:** 격리 모드와 프로젝트 모드의 격차, 큰 코드베이스에서 늘어나는 시간 초과와 오류를 보고했다. 컴포넌트 합성과 인터페이스 불변식을 향후 과제로 들었다. 격리 모드는 결함 위치를 아는 사람이 만든 wrapper였고, 오탐은 측정하지 않았다.
- **Towards Fuzzing ZKP Circuits:** 큰 회로를 부분 회로 단위로 퍼징하고, 그 결과를 전체 회로에서 검증해 오탐을 막자고 제안했다. 실제로 구현한 것은 zk-regex 차등 퍼저였다. 부분 회로 퍼징은 구현하지 않았다.
- **Wildfire:** 일반 소프트웨어에서 격리 함수를 퍼징한 뒤 호출 맥락에서 실현 가능성을 확인했다. 이는 양성 방향의 확인이며, 확인에 실패해도 불가능의 증명으로 보지 않았다. 고립 함수마다 다시 컴파일하지 않는 장치도 있었다.
- **Picus/QED², CIVER, ZEQUAL:** 형식 분석 쪽에서 Circom 회로를 하위 회로나 컴포넌트 단위로 다룬다.
  - Picus/QED²는 컴파일러 debug 정보로 회로를 나눠 반례를 점진적으로 조립하고, 결론이 나지 않으면 unknown으로 보고한다.
  - CIVER는 README 기준으로, 모든 컴포넌트를 모듈식으로 검사하고 tag와 전제·후제 조건을 검증한다.
  - ZEQUAL은 하위 회로가 일관적이라고 가정한 템플릿 단위 검증이다. 반례 116개 가운데 수동 확인으로 실제 결함은 26개였다. 가정을 풀고 다시 돌려 20개를 더 찾았다. 모듈 단위 결과에는 재확인과 수동 판정이 필요하다는 직접 선례다.
- **CCC-Check:** 제약에서 값 범위를 건전하게 과대근사하며, 입력 tag를 전제로 가정한다.
- **FuzzSlice:** 함수 slice 퍼징의 충돌이 호출자 제약 때문에 진양성이 아닐 수 있음을 지적했다.

zkFuzz가 찾은 원인의 55.2%가 계산 abort형이었다는 보고는 입력 전제 처리의 중요성을 보여 준다 [LIT-N2; §3.5].

### 4.3 차별성 가설과 입증 의무

N2가 검토한 문헌에서는 다음과 같은 평가를 찾지 못했다. 결함 위치 없이 Circom entrypoint를 자동으로 컴포넌트로 나눠 TCCT 퍼저를 실행하고, 같은 entrypoint의 통째 실행과 같은 자원으로 비교한 평가다 [LIT-N2; §2.1]. 이것은 검색 범위를 밝힌 부정문이다. 아이디어 수준에서든 조합 수준에서든 ‘최초’라는 주장의 근거가 아니다 [LIT-N2; §2.2]. 이 연구의 차별성은 아이디어 목록이 아니다. 다음 네 가지를 함께 입증하는 데 있다는 가설이다 [계획; §1].

1. **적용 범위.** 결함 위치 없이 실제 entrypoint에서 대상을 자동 구성한다. 입증하려면 준비 실패와 미지원을 포함한 개발 분리 자료의 적용성이 필요하다. 현재 근거는 개발 자료의 탐색·재사용·정상 실행 관측뿐이다(T6A-DIAG, ENG-T6A, NE-01·02).
2. **같은 수준의 검토된 결과.** 같은 자원에서 컴포넌트 확인과 원인 귀속을 같은 수준으로 수행해 결과를 비교한다. 입증하려면 비교 가능성 관문과 K5 지표가 필요하다. 현재 근거는 없다. P2에는 통째 후보가 없었고 분할 후보는 검토하지 않았다.
3. **해석의 신뢰성.** 컴파일된 제약과 정확한 신호 대응 위에서 특정 후보를 건전하게 배제하고, 미판정과 비용을 보고한다. 현재는 제안 단계다. NE-01의 정상 대응은 그 전제 조건 중 하나일 뿐이다. P2의 `BigLessThan` 사례는 문제가 실제로 생긴다는 수동 관측이다.
4. **총비용.** 준비, 실행, 맥락 판정, 수동 검토를 포함한 총비용을 측정한다. 현재 근거로는 작은 정상 fixture에서 준비 감소가 측정 구간 전체의 감소로 이어지지 않았다(NE-03). 사람의 검토 시간은 아직 측정한 적이 없다.

컴파일 재사용, 실행 관리, 검토 엔진은 이 가설을 떠받치는 시스템 구성요소다. 이들이 존재한다는 것만으로는 새로운 알고리즘이나 성능 우위의 근거가 되지 않는다 [계획; §1, 문제 정의; Project Identity].

### 4.4 한계와 타당성 위협

**작은 정상 fixture.** NE-01·02·03은 결함 없는 정상 산술 fixture 두 개에서 얻었다. 조건은 scalar `in/out`, O0, bn128, 대상당 고정 입력 3개다. 최적화로 신호가 제거되거나 배열 인터페이스가 쓰일 때의 대응은 확인하지 않았고, 그 첫 질문인 NC-01은 결과 대기다. 이 결과를 독립 프로젝트 2개의 결과나 일반적인 의미 동등성으로 확대하지 않는다 [체크포인트; §2].

**적은 반복과 캐시.** 비용 비교는 방식별 2회다. OS 파일 캐시를 비우지 않았고, 공유 머신의 활동을 모두 통제하지 않았으며, CPU와 메모리를 재지 않았다. T6a는 재사용 버전을 먼저 실행해 비교 버전에 유리한 캐시 조건을 만들었다 [ENG-T6A; 해석과 한계]. 통계적 속도 우위나 cold-cache 성능은 주장하지 않는다.

**개발 노출.** 모든 예비 결과는 개발에 쓰였거나 노출된 자료에서 나왔다. P2의 두 사례, T6a의 세 프로젝트, 정상 fixture가 그렇다. 공개 70건 전체도 메타데이터와 공개 결과에 노출됐다 [DATA-N1; §6]. 개발 분리 평가가 없으므로 일반화 근거가 없다.

**의미 대응과 귀속의 미입증.** 정상 입력의 경계 일치는 악의적 할당에서의 동등성이나 호출자 제약의 보존을 보이지 않는다. 원본 템플릿을 호출하는 wrapper를 만들었다는 사실과 원본 의미 보존의 검증은 다르다 [N3 결정; §2]. 첫 분기 컴포넌트로의 투영과 통째 후보의 원인 귀속은 가설이다. 원인 귀속 절차가 고정되지 않았으므로, 같은 원인이 여러 조각에서 반복되면 고유 원인 수가 부풀 수 있다. 반대로 서로 다른 원인이 합쳐질 수도 있다 [LIT-N2; §3.6·§4.3]. P2 inference에서도 같은 원인이 여러 조각에서 반복 보고됐다 [DEV-P2; 정답 외 반례 검토].

**입력 전제와 abort형.** 무엇을 선언된 입력 전제로 인정하는지에 따라 컴포넌트 확인 수가 직접 바뀐다. 문서화된 n비트 가정을 전제로 인정하면 `BigLessThan` 후보는 컴포넌트 확인이 아니다. 인정하지 않으면 컴포넌트 확인이면서 맥락 배제 대상이다 [LIT-N2; §3.5]. 결함 위치를 모르는 조각에는 사전 속성과 전제가 없으므로, 결과를 본 뒤 쓰는 predicate는 사후 명세가 된다 [LIT-N2; §4.4]. 이 규칙은 **계획·미고정**이다.

**공정성.** 첫 반례 종료 때문에 원인 수의 비교는 분할에 유리할 수 있다. 설계 A의 실행기는 구현되지 않았다. 할당 소진은 실제 자원 사용의 동등성을 뜻하지 않는다. P2는 조합 8개를 동시에 실행했다 [LIT-N2; §4.1·§4.6, DEV-P2; 설정].

**오라클의 범위.** zk-email `FpMul`과 v2의 Tangle은 해당 설정에서 찾지 못한 경험적 미탐이다. 이를 실행 결과를 본 뒤 ‘탐지 범위 밖’으로 분류해 조건부 분석에서 빼면 순환 논리가 된다 [LIT-N2; §4.5, 계획; §2].

**검토 비용과 명세.** 검토 엔진의 재검사는 자동이지만 입력 계약과 predicate는 사람이 쓴다. 통제 실행의 사람 검토 시간은 계측하지 않았다 [검토 설계; §1, LEG-V1; 비용].

**적용성.** 지원 구문 밖의 구성, 외부 의존성의 식별과 설치, 테스트 entrypoint와 production entrypoint의 구분, 더 자를 수 없는 root 템플릿의 결함이 적용 범위를 제한한다 [T6A-DIAG; 남은 한계, DEV-P2; 발견 사항].

**자료 처리.** 기록·집계의 검증은 합성 메타데이터에 대한 구조 검증이다. 중첩 증거의 내용을 열어 확인하지 않는다 [AG-01; 수정 기록 §6].

이 근거로는 세 가지를 쓰지 않는다: 자동 분해나 그 구성요소가 ‘최초’라는 주장, 순위나 분해가 일반적으로 우위라는 주장, wrapper가 일반적으로 원본 의미를 보존한다는 입증.
