## 1단계 결론(요약)

circom 2.2.3의 `.sym`은 인스턴스 경로와 컴포넌트 번호를 주지만, `.sym`·C++·wasm 어디에도 템플릿 인자 값은 없다. circom은 인자 튜플이 같은 인스턴스를 하나의 템플릿 구현으로 합치므로 구현 이름으로도 값을 되살릴 수 없다. 반면 `--O0`는 `s === v` 제약을 순서대로, 중복까지 남긴다. 그래서 값을 컴파일러가 계산하게 하고 제약으로 읽는 방식을 택했다. miiz 승인 사항: 진단 사본은 인스턴스 탐색에만 쓴다. 배열 인자는 정규 인코딩(차원 + 행 우선 값, 0..p-1 십진)의 SHA-256로 키를 만들고 전체 값은 `instance-args.json`에 둔다. 스칼라는 p/2 초과 값을 음수로 쓴다(일대일).

## 구현

- **`src/instance_capture.rs`(새 파일):** include 닫힘을 훑어 템플릿·함수·인스턴스화 위치(이름 있는 컴포넌트, 컴포넌트 배열, 익명 컴포넌트)를 찾는다. 템플릿마다 표지 신호를, 스칼라 파라미터마다 `__zkfdo_p<i> === param`을 넣는다. 위치마다 실행 표지, 컴포넌트 index, 배열 인자의 차원·지문(Horner)·전체 값(첫 실행과 지문이 바뀐 실행에만)을 넣는다. 캡처 신호는 `<-- 0` 뒤에 `===`로 묶는다. 삽입은 줄바꿈을 넣지 않아 줄 번호가 유지되고, 익명 컴포넌트의 byte offset은 원본으로 되돌린다. 배열 파라미터는 인덱싱·전달 관계로 추론하고, circom이 삽입 문장을 거부하면(예: T2046) 그 문장을 배열로 바꿔 최대 4회 다시 컴파일한다. R1CS·`.sym`은 스트리밍으로 읽는다.
- **main의 배열 인자:** 템플릿 안의 위치가 넘기지 않으므로 `component main` 문장의 정수·16진·음수 리터럴(중첩 배열 포함)에서 읽고 mod p로 줄인다. 리터럴이 아니면(`1 + 2`, 함수 호출) `array parameter … of the main component is not captured: …` 사유로 미지원 처리하고 그 아래 인스턴스는 부모 인자 미캡처 사유를 받는다. 어느 파라미터를 리터럴에서 읽었는지 `main_literal_parameters`에 남긴다. 측정에서는 rarimo 3건(`A`, `B`, `P`)만 해당했다.
- **`src/targets.rs`:** `targets --instance-capture`가 해석기 확장 뒤 캡처를 돌린다. 캡처가 되면 컴파일러 결과를 고르고, 호출 위치(부모 키, 컴포넌트 이름, 줄)마다 두 방법의 자식 키를 비교해 `slot_differences`·한쪽에만 있는 키로 남긴다. 각 대상에 `instance_source`(`compiler`/`interpreter`)와 `methods_agree`를 붙인다. 해석기 미지원 사유는 `interpreter_unsupported`로 옮겨 보존한다. 캡처가 실패하면 해석기 결과를 쓰되 대상마다 `interpreter`로 표시하고 실패 사유를 `capture_failure`에 남긴다(조용한 대체 없음).
- **`src/corpus.rs`:** manifest 대상에 `instance_capture`가 있으면 준비 단계 점검도 캡처에서 만들고, 해석기 점검과의 차이를 `instance_inspection`에 남긴다.
- **CLI:** `zkfDO capture [--verify-neutrality]`.
- **테스트:** `tests/instance_capture_test.rs` 8개(fixture 값·중립성, 해석기 완전 fixture에서 키·조각 동일, 음수 스칼라 키, 배열 리터럴 래퍼 점검, 캡처 실패 표시, main 리터럴 값이 circom 계산값과 같음, 리터럴 아닌 main 인자의 미지원 사유, `var` 선언 속 익명 컴포넌트), `tests/fixtures/instance_capture/`, `tests/f01_discovery_test.py` 5개.
- **스크립트:** `scripts/measure_f01_discovery.py`, `summarize_f01_discovery.py`, `f01_neutrality.py`, `f01_cleanup_artifacts.py`.

### main 리터럴 캡처

작은 회로에서 main 배열 `[-1, 0x10, 0xff, p+1]`을 넣고, 같은 배열을 지역 변수 복사본으로 자식에 넘겨(진단 사본이 위치에서 컴파일러 값을 캡처) 비교했다. 리터럴에서 읽은 값 `[p-1, 16, 255, 1]`이 컴파일러 캡처 값과 같고, 원소 하나를 스칼라로 받은 자식도 `255`다. `[1 + 2, 4, 5, 6]`과 함수 호출 `FOUR()`는 main 인스턴스를 미지원으로 남기고 사유에 해당 식을 적는다. 이 경우에도 배열에 의존하지 않는 자식은 컴파일러 값을 받는다. 셋 다 중립성 동일이다.

### 회귀: C-03 준비 성공 881건

| 결과 | 건수 |
|---|---:|
| F-01 준비 성공 | 881 |

**불일치 1건(F-01이 맞음):** erhant/circom101 `circuits/test/comparators/sign.circom`. `Sign()`은 `var half = 1 / 2; CompConstant(half - 1)`이다. circom의 `/`는 체 나눗셈이므로 `half = (p+1)/2`, 인자는 `(p-1)/2 = 10944121435919637611123202872628637544274182200208017171849102093287904247808`이다. 컴파일러 캡처 값이 이것과 같다. C-03 해석기는 `/`를 정수 나눗셈으로 계산해 `CompConstant(-1)`을 냈고, 그 래퍼는 컴파일되지만 실제 회로와 다른 인스턴스였다. 이에 따라 `CompConstant` 아래 `Num2Bits(135)` 위치도 부모 키만 바뀌었다(자식 키 동일).

**해석기 표시 6건과 보충 측정:** 모두 erhant/circom101 배열 테스트다. 최종 측정 중 `var eq = IsEqual()(…)`처럼 `var` 선언 안의 익명 컴포넌트를 중괄호로 감싸 `eq`가 범위를 벗어나는 결함을 찾았다(진단 사본 T2021, 원본은 컴파일됨). 측정은 그대로 두었고, 이 6건은 해석기 결과로 표시되어 C-03과 같았다. `var`를 선언으로 다루도록 고친 바이너리(`f8c9f64d…`, 별도 잠금)로 6건만 `runs/f01-2026-10-03/supplement-var-scope/`에 다시 돌린 결과 6/6 캡처 완전, 6/6 C-03과 동일, 준비 성공이다. 본문 표의 수치는 주 측정(`39bf0048…`) 기준이다.

## 후속 제안

1. 래퍼 include 닫힘: 래퍼가 템플릿 정의 파일만이 아니라 원본 entrypoint의 include 닫힘(entrypoint 자신 제외)을 include하면 T2021·TAC01 43 entrypoint가 풀릴 수 있다. 컴파일 단위 키의 의존 파일이 바뀌므로 회귀 확인이 필요하다.
2. 태그 입력: 태그 없는 입력을 받아 태그 입력에 넘기는 얇은 상위 템플릿이 가능한지 circom 규칙을 먼저 확인한다(34 entrypoint).
3. 준비 상한: 1,000 단위 이상 entrypoint는 300초 안에 끝나지 않는다. 상한을 바꿀지, 단위 병렬 컴파일을 할지 정해야 한다.
4. main의 리터럴 아닌 배열 인자: 측정에는 없었지만, 필요하면 main 템플릿 안에서 원소별로 컴파일러 값을 캡처하는 방식으로 넓힐 수 있다.
