# A-02 실제 공통 실행과 S-02 후보 의미 검토 인계

2026-10-02 · 담당 miiz · `engine-clamp-handoff-v1` · 상태: **두 작업 미착수**. [A-01 부분 결과](../reports/n4-1-policy-a-2026-10-02/REPORT.md)는 가상 예산 모델과 고정 정상 자식의 자원 계측을 검증했지만 zkFuzz 실행은 통째 0/1·분할 0/21이다. [S-01](../reports/n4-1-p2-candidate-review-2026-10-02/REPORT.md)은 P2의 지정된 `Subtract` 후보 한 개를 컴포넌트 수준 일반 TCCT 위반 및 기존 unconstrained multiplier 원인으로 확인했다. 이는 controlled-v1.1과 같은 원인·R1CS이며 새 고유 원인, entrypoint 또는 프로젝트 결함, 통째 대비 우위가 아니다. 두 고정 결과를 수정하지 않는다.

## 실제 비교의 설정 보정

[이전 인계](next_policy_a_handoff_2026-10-02.md)는 양쪽 시도 상한을 30초로 적었으나 실제 엔진은 그 조건으로 실행되지 않았다. [P2의 사전 설정](../reports/dev-rq1-pilot-2026-09-29/pilot-config.json)은 통째 한 호출 최대 600초, 분할 조각당 최대 30초, 방식별 캠페인 총 600초다. 통째 회로는 당시 600초에도 한 세대를 완료하지 못했다. 통째를 30초마다 끊으면 기준선의 진행 가능성을 훼손할 수 있으므로 **A-02의 주 개발 비교**는 방식별 총 600초, 통째 시도 최대 남은 600초, 분할 시도 최대 30초로 한다. 이는 같은 총할당·공통 실행기·결과에 무관한 잔여 예산 규칙을 적용하되 시도 상한은 방식별로 사전 명시하는 설계다. 동일한 시도 상한이나 P2와 동등한 환경이라는 주장은 하지 않는다. 양쪽 30초 조건은 별도 민감도 분석이 필요할 때만 새 범위로 판단한다.

대상은 기존 개발용 P2 `inference-main` production entrypoint와 P2 small-first block 1의 **21개 프로젝트 조각 전체**다. 한 쌍만 실행하며 새 공개 프로젝트·held-out 평가 자료를 열지 않는다. P2는 여러 lane을 동시 실행했으므로 새 순차 한 쌍의 raw 시간과 그대로 합치지 않는다. 실행 순서·환경 부하·cache·준비·컴파일 비용을 기록하고 결과가 달라도 보존한다. 후보 위치 일치는 원인 확인이 아니다.

## 구현 담당 프롬프트: A-02

AGENTS.md, reports/START_HERE.md, docs/plan_revision_2026-10-01.md, docs/scope_decision_accepted_2026-10-01.md, 이 인계, 기존 A-01 SCOPE/REPORT와 P2 설정·manifest를 읽어라. 계획 표의 A-02 행만 시작·종료 상태로 갱신한다. 기존 A-01 문서·run·코드 해시를 사후 변경하지 말고, 새 `reports/n4-1-policy-a-engine-2026-10-02/SCOPE.md`에 실제 개발 실행의 대상 1/21, 원본 revision·artifacts·도구 hash, 사전 순서·seed, 총예산, 방식별 시도 상한, 종료/재시작·잔여 규칙, 비용 경계, 실패·중단 기준을 **실행 전에** 고정한다.

1. 통째와 분할에 동일한 실제 프로세스 실행·계측 함수와 캠페인 상태기를 사용하라. 기존 P2의 통째 직접 호출과 현재 `experiment run`의 한 번씩 실행을 그대로 공정한 A안이라고 부르지 않는다. 캠페인 단조시계는 첫 시도 dispatch 직전에 시작하고, 첫 프로세스 시작 offset도 따로 남긴다. startup·재시작·정리 시간을 600초 캠페인 예산에 포함하고 준비·컴파일·검토는 별도로 계측한다. 후보/미발견에 따라 순서나 종료를 바꾸지 않는다. 한 target의 후보가 빨리 나와도 고정 규칙의 다음 시도로 진행하며 총예산을 target마다 복제하지 않는다.
2. 주 실행은 방식별 총 600초로, 통째 시도 상한은 남은 예산까지 최대 600초, 분할 시도 상한은 30초로 사전 고정한다. P2 small-first의 21개 ID·순서를 모두 보존한다. 초기 seed는 P2 block 1의 `2026092931`; 이후 pass/재시작 seed 규칙은 결과와 무관하게 SCOPE에 정확히 정의한다. 21개를 다 돈 뒤 남은 예산의 순환, 장애 때의 진행/중단, 외부 취소, 한 단위의 전체 분모와 미시작 이유도 미리 정의한다. 실행 순서와 동시성도 먼저 고정한다.
3. 시도별 할당·실제 wall·후보 log 관측 시각/zkFuzz 내부 시각의 다른 의미·시작/종료·timeout·spawn/저장/회수 실패·잔여 예산을 원시 경로와 hash에 연결하라. 실제 CPU와 peak memory는 측정 범위를 명시해 기록하고 프로세스 트리 계측이 불가능하면 값 대신 `unknown`과 이유를 남겨라. 측정 실패가 실제 엔진 실행 자체를 무기한 막지는 않지만, 자원 동등성 관문을 통과했다고 쓰면 안 된다. 자식/후손이 회수되지 않거나 ledger 저장에 실패하면 성공으로 처리하지 않는다.
4. 실제 실행 전에 결정적 가짜 자식으로 같은 상태기의 후보 즉시 반환·미발견·timeout·spawn 실패·취소·중복 후보·잔여 예산을 검사한다. 구조 검사가 통과하면 위 한 쌍을 실제 zkFuzz로 실행한다. 결과가 차단되면 정확한 명령 단계와 사유, 1/21 분모를 남기고 종료한다. 모델 검사만 다시 늘려 실제 실행 완료로 바꾸지 않는다.
5. 새 REPORT와 값 없는 evidence에 가상 모델과 **실측 캠페인**을 분리하고, 준비+실행+검토 총비용의 현재 측정 범위를 적어라. 원시 후보/로그/컴파일 산출물은 ignored `runs/`에 둔다. S-01 판정을 새 후보에 복사하지 말고 새 후보의 일반 TCCT·원인 귀속은 미검토로 남겨라. 코드 변경 뒤 필수 fmt·clippy·cargo test와 필요한 의미 있는 회귀 검사를 수행한다. 구현 결과는 현행 안내·논문 근거 색인과 일치시키되 S-02 담당의 파일/행은 수정하지 않는다. N4-1 전체·N5를 자동 완료하지 않고 commit/push/PR은 하지 않는다.
